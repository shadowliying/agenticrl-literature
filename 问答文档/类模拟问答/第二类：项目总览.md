**第二类：项目总览与整体架构类问题**

这一类问题考的不是你会不会背模块名，而是你有没有“系统视角”。  
面试官问这一类，本质上在看 4 件事：

1. 你是不是能从全局解释系统，而不是只会讲某个局部技术点。
2. 你知不知道每个模块解决的是哪一种业务问题。
3. 你能不能讲清楚“为什么这样拆”，而不是只会说“为了模块化”。
4. 如果面试官追问“换一种拆法会怎样”，你能不能讲出 trade-off。

这一类一旦答得好，后面你讲检索、Validator、RL、Memory 都会显得更可信。  
因为面试官会先相信你不是“堆模块”，而是在做一个有明确问题分工的系统。

---

## 一、这一类的学习目标

你学完这一类，至少要做到：

- 能画出系统的核心模块关系
- 能说清 `Orchestrator / Retrieval / Validator / Synthesis / Memory` 各自负责什么
- 能解释为什么不是一个大模型一步到位
- 能解释为什么 `Validator` 必须独立
- 能解释为什么 `Memory` 是能力层，不是独立 Agent
- 能把架构设计和业务难点一一对应起来

---

## 二、先建立这一类的总理解

你不要把系统架构理解成“几个模块拼在一起”。

你应该把它理解成这样一条逻辑链：

- 用户的问题本身是复杂科研问题
- 所以系统不能一步生成
- 那么必须先做规划，再做证据获取，再判断证据够不够，最后才能回答
- 因此天然会拆成：
  - 决策层
  - 检索层
  - 验证层
  - 生成层
  - 记忆支撑层

也就是说，这个架构不是“为了像 Multi-Agent 而设计成 Multi-Agent”，  
而是因为业务问题本身就包含了不同类型的任务，所以系统才被拆成这些角色。

你后面回答时，一定尽量用这句话做总领：

> 我这个架构不是从模型能力出发去拆的，而是从科研问答的任务链路出发去拆的。因为这类任务天然包含规划、证据获取、证据判定和答案组织四类不同问题，所以我把它们拆成了不同模块。

---

## 三、文档里这一类问题的标准答案

---

### 1. 为什么采用 Orchestrator-Worker 架构？

这是这一类最核心的问题。  
你如果只答“因为方便解耦”，是不够的。  
一定要从业务链路来讲。

**标准答法：**

我采用 `Orchestrator-Worker` 架构，核心原因是科研问答不是一个单步任务，而是一条多阶段决策链路。  
在这条链路里，不同步骤解决的问题类型完全不同：

- 有的步骤解决“下一步该做什么”
- 有的步骤解决“去哪里找证据”
- 有的步骤解决“当前证据是否足够”
- 有的步骤解决“如何把证据组织成最终回答”

这些问题混在一个单体 Agent 里，会导致两个问题。

第一，职责混乱。  
同一个模型既要做规划、又要做检索判断、又要做回答生成，很容易在证据不足时直接开始回答，因为它天然偏向生成，而不是偏向“停下来判断自己该不该说”。

第二，可控性差。  
科研问答最怕的不是完全不会答，而是“部分知道就开始答”。如果所有能力都混在一个 Agent 里，很难明确知道当前错在规划、检索、验证还是生成。

所以我把系统拆成一个 `Orchestrator` 和多个 Worker 模块。  
`Orchestrator` 负责全局规划和动作决策，相当于系统的大脑；其他模块负责执行特定任务，比如检索、验证和生成。这样做的好处是，决策逻辑和执行逻辑是分开的，后面无论做强化学习、加规则、做评测还是定位 bad case，都会更清晰。

**你回答时一定要带出来的点：**
- 不是为了“多 Agent 看起来高级”
- 而是因为任务链路天然不同质
- `Orchestrator` 解决的是“做什么”
- Worker 解决的是“怎么做”
- 这样更可控，也更适合后面做 RL

**如果面试官追问“为什么一定要有中心化的 Orchestrator？”**

你可以补一句：

因为科研问答里最关键的问题之一是“什么时候继续检索、什么时候停止、什么时候换方向”。这本质上是全局决策，不适合分散在每个执行模块里各自做。用一个中心化的 Orchestrator，能保证系统始终围绕当前目标做动作选择，而不是各个模块局部最优。

---

### 2. 为什么核心模块是 Orchestrator、Retrieval、Validator、Synthesis、Memory Layer？

这个问题考的是你有没有清晰的模块边界。  
你不能只背名字，必须说出每个模块对应的业务功能。

**标准答法：**

我最后把系统稳定在这五部分，是因为它们刚好对应科研问答里的五种核心问题。

第一部分是 `Orchestrator`。  
它负责把用户问题转成结构化任务，并且在执行过程中决定下一步做什么。  
科研问题经常不是一次检索就能结束，所以系统必须有一个全局决策模块，来决定是继续搜、补证据、重规划还是进入答案生成。

第二部分是 `Retrieval`。  
它负责召回候选文档、做精排、抽证据片段。  
科研问题的证据往往分散在多篇资料里，所以 Retrieval 的目标不是直接回答，而是尽可能提供高质量候选证据。

第三部分是 `Validator`。  
它负责判断当前证据是否足够回答问题。  
这一部分是整个系统和普通 RAG 最大的区别之一，因为科研问答最怕“相关但不充分”，所以必须独立判断证据链是否完整，而不是把这个任务隐含交给生成模块。

第四部分是 `Synthesis`。  
它负责在证据充分的前提下，把已有证据组织成最终答案。  
换句话说，Synthesis 不是去“找证据”，而是去“表达结论”。这让回答阶段更加稳定，也避免了生成模块一边找证据一边组织答案时混在一起。

第五部分是 `Memory Layer`。  
它不是独立 Agent，而是一个支撑层。  
它主要服务三个目标：支持多轮追问、复用相似检索结果、追踪科研实体和指代关系。对科研问答来说，这三个需求都很常见，但它们本质上不是“高层决策”，所以我把它们作为能力层来设计。

**最关键的一句话：**

这五个模块不是拍脑袋列出来的，而是分别对应：
- 决策问题
- 证据获取问题
- 证据判定问题
- 答案组织问题
- 跨轮连续性问题

**你回答时最好补一个业务例子：**

比如用户问“比较 BERT 和 RoBERTa 的预训练差异，并解释为什么去掉 NSP”。  
`Orchestrator` 要先判断这是一个“比较 + 原因分析”的复杂任务；  
`Retrieval` 去找模型改动、训练策略、实验结果等候选证据；  
`Validator` 判断当前证据是否同时覆盖了“差异”和“原因”；  
如果够了，`Synthesis` 再把这些证据组织成结构化回答；  
如果用户下一轮追问“那它为什么效果更好”，`Memory` 可以帮助系统延续上下文，不必从零开始。

### 3. 为什么不是一个大模型一步到位？

这是面试官最爱问的架构追问之一。  
回答这个问题时，千万不要只说“因为大模型会幻觉”。  
那太浅。  
你要从“任务类型不一致”来讲。

**标准答法：**

不是不用大模型，而是不能把所有事情都交给一个模型在一次生成里完成。  
原因主要有三点。

第一，科研问答包含的是不同类型的问题。  
“做规划”“做检索”“判证据是否充分”“组织最终表达”这几件事的目标函数其实不一样。  
比如生成模块天然倾向于“给出一个流畅答案”，但验证模块的目标是“宁可不答，也不能证据不足时强答”。这两种行为偏好本身就是冲突的。

第二，一步到位的系统不容易控制。  
如果一个大模型既负责检索理解，又负责证据判断，又负责最终回答，那你很难知道错误到底出在哪。  
科研问答不是只追求一个 final text，而是追求“证据链正确”。所以必须把中间步骤显式化，才能做判断和约束。

第三，一步到位不利于优化。  
比如我后面要用 GRPO 优化的是动作决策，那最自然的训练对象就是 Orchestrator；  
如果所有能力都混在一起，你很难只优化“什么时候继续检索、什么时候停止”这类序贯决策能力。

所以我不是不用大模型，而是让大模型分别在更合适的位置发挥作用。  
比如 Orchestrator 用来做规划与动作选择，Synthesis 用来做答案组织，但“证据是否足够”要单独拿出来，这样整个系统才可控、可训练、可评测。

**一句简洁但很强的总结：**

单体模型更像“直接出结果”，而我这个系统更像“先把问题做对，再把答案说好”。

---

### 4. 为什么 Validator 必须独立出来？

这个问题非常重要。  
你后面很多深挖题，都会回到这里。

**标准答法：**

Validator 必须独立出来，是因为在科研问答里，“有相关内容”不等于“能严谨回答”。  
如果把验证逻辑隐含在生成模块内部，系统会天然偏向“尽量输出一个合理答案”，而不是“严格检查证据够不够”。

独立做 Validator，有三个明显价值。

第一，它把“回答资格”从“回答表达”里分离出来。  
也就是说，系统先判断“现在有没有资格回答”，再讨论“怎么回答”。  
科研场景里，这一步非常关键。

第二，它能把证据缺口显式化。  
比如当前问题缺的是“原因槽位”“实验支持槽位”还是“来源一致性”，只有独立 Validator 才能结构化输出这些信息，并反馈给后续流程做继续检索或重规划。

第三，它能让系统更可控。  
如果没有独立 Validator，很多时候回答模块会把局部相关信息组织得很流畅，但其实证据链是不完整的。独立 Validator 相当于一个“放行门”，不达标就不让进入生成阶段。

**一个业务例子：**

比如用户问“RoBERTa 为什么去掉 NSP”。  
如果系统只搜到“RoBERTa 移除了 NSP 任务”，这说明信息相关，但还不能回答“为什么”。  
如果没有 Validator，生成模块很可能会根据已有常识补一个看起来合理的解释。  
但独立 Validator 会指出：当前“原因槽位”没有被足够证据覆盖，所以不能放行。

**一句话总结：**

我把 Validator 独立出来，本质上是为了防止系统在“证据不完整时说得很像对的”。

---

### 5. 为什么 Memory 是能力层，不是独立 Agent？

这是很常见的“系统边界”问题。  
你回答时一定要说清“是否做高层决策”这个标准。

**标准答法：**

我没有把 Memory 做成独立 Agent，核心原因是 Memory 的职责不是决策，而是支撑。  
它负责的是 recall 和 write，也就是把历史有价值的信息在合适的时候取出来，或者在任务结束后写回去。  
这和 Orchestrator 那种“当前应该做什么”的策略决策，是两类完全不同的能力。

如果把 Memory 做成独立 Agent，会带来两个问题。

第一，职责会和 Orchestrator、Retrieval 重叠。  
比如当前要不要用历史信息，本质上还是 Orchestrator 的流程控制问题；而具体去 recall 哪些历史内容，更像 Memory 层的能力提供。如果 Memory 也变成一个决策 Agent，就会出现谁在决定流程、谁在提供能力不清楚的问题。

第二，系统会更复杂，但收益不大。  
Memory 的核心任务不是“推理”，而是“存取和辅助召回”。  
所以把它做成能力层更合理，也更符合工程实现：其他模块按需调用它，而不是让它自己参与高层编排。

**一个很好的总结口径：**

Orchestrator 决定“要不要用记忆”，Memory 决定“能提供什么记忆”。  
前者是策略，后者是能力，所以 Memory 更适合作为 Layer，而不是 Agent。

---

### 6. 多个模块之间是怎么协作的？

这个问题本质上是在考你能不能把架构说成“流程”，而不是说成几个孤立框。

**标准答法：**

它们的协作关系可以理解成一条受控闭环。

用户问题进来之后，首先由 `Orchestrator` 输出结构化计划，并确定当前是一个什么类型的问题，比如定义类、比较类、统计类，接下来需要哪些信息槽位。  
然后系统会做一次 `Memory Recall`，补充历史上下文、相似问题缓存或实体信息。  
之后由 `Retrieval` 负责召回候选文档、做精排并抽取证据片段。  
这些证据不会直接进入答案生成，而是先交给 `Validator` 做结构化评分。如果 Validator 判断证据不足，会明确告诉系统缺哪些信息、是继续检索还是重规划。  
当证据达标后，系统再进入 `Synthesis`，基于经过验证的证据生成最终答案；如果问题本身需要统计、表格或图形，还会由 Synthesis 触发代码工具。  
最后在任务结束时，把高价值信息写回 `Memory`，为下一轮追问或相似问题复用做准备。

**这里你一定要突出这句话：**

模块之间不是流水线串联，而是一个“检索-验证-反馈-再决策”的闭环。  
这也是它和普通“搜一下再生成”的链路最大的区别。

---

## 四、这一类问题背后的核心逻辑

第二类你一定要形成这条认知链：

`科研问答是复杂任务`
-> `复杂任务里包含不同性质的子问题`
-> `不同性质的问题不能混在一个模块里做`
-> `所以要拆出决策、检索、验证、生成、记忆`
-> `这种拆法能让系统更可控、更能优化、更容易做 RL 和评测`

记住一句话：

> 这个架构不是为了炫技，而是为了把“能不能回答”和“怎么回答”分开。

这句话对这一类题非常有杀伤力。

## 五、这一类的高频面试问题补充（含答案）

下面这些问题是第二类里很容易继续往下深挖的题。

---

### 1. 为什么 Orchestrator 不直接自己做检索和回答，还要调其他模块？

**答案：**

因为 Orchestrator 的核心职责是做全局决策，而不是做局部执行。  
如果它既要规划、又要检索、又要验证、又要生成，那么系统会退化回一个单体 Agent，职责边界会重新模糊。  
我把 Orchestrator 保持在“决定下一步动作”的位置，是为了让它更适合作为策略层，也方便后面用 RL 只优化决策能力，而不是把所有能力混着一起学。

---

### 2. 为什么 Synthesis 不能和 Retrieval 合并？

**答案：**

因为 Retrieval 的目标是“获取尽量好的证据”，Synthesis 的目标是“把已验证证据组织成答案”。  
前者追求的是证据质量和覆盖，后者追求的是表达组织和最终可读性。  
如果合并，系统很容易在证据还没充分时就开始组织答案，导致“边找边编”。把它们拆开，能保证生成只发生在证据通过验证之后。

---

### 3. 为什么不把 Validator 和 Synthesis 合并成一个“回答模块”？

**答案：**

因为 Validator 的目标是保守和严格，Synthesis 的目标是完整和流畅，这两个目标函数是冲突的。  
Validator 更像一个 gatekeeper，它判断系统有没有资格回答；Synthesis 才是负责真正说答案的人。  
如果把两者合并，生成倾向会压过验证倾向，系统会更容易在证据不足时也给出一个看起来完整的回答。

---

### 4. 为什么模块数量控制在这几个，而不是拆得更细？

**答案：**

模块不是越多越好。  
我的原则是：只有当一个子问题的目标函数明显不同，且拆出来能显著提升可控性或可优化性时，才值得独立成模块。  
像规划、检索、验证、生成，这四类问题边界非常清晰，所以值得分开；但如果再拆得过细，比如把各种 recall、cache、entity tracking 都做成独立 Agent，系统复杂度会明显上升，但实际收益不一定成比例，所以我把它们收敛为 Memory Layer。

---

### 5. 为什么把 Memory 放在旁路，而不是放在主流程中心？

**答案：**

因为 Memory 的价值是辅助，而不是主导。  
它会影响流程，但不应该接管流程。  
主流程中心应该是围绕“当前问题是否被充分回答”来运转，所以核心闭环仍然是 Orchestrator -> Retrieval -> Validator -> Synthesis。  
Memory 更适合作为旁路支撑：在需要的时候补充背景、复用缓存、延续上下文，而不是成为每次都主导流程的中心节点。

---

### 6. 你的架构和普通“搜索增强生成”最大的区别是什么？

**答案：**

最大的区别是我把“证据是否足够”独立成了一个中间判断层。  
普通搜索增强生成很多时候是“检索 -> 拼上下文 -> 生成”，而我的架构是“规划 -> 检索 -> 验证 -> 决策 -> 生成”。  
也就是说，它不是只增强生成，而是在生成前先控制证据资格。

---

### 7. 为什么这个架构天然适合后面做强化学习？

**答案：**

因为 Orchestrator 的职责是“根据当前状态选择下一步动作”，这是一个非常标准的序贯决策问题。  
如果架构里没有明确的决策层，那后面 RL 很难有清晰的训练对象。  
正因为我把决策和执行拆开了，所以后面可以专门优化 Orchestrator，而不是把 RL 强行套在整个系统上。

---

### 8. 如果面试官说“你这个还是像 pipeline，不像真正的 agent system”，你怎么回答？

**答案：**

我会说，这套系统不是简单的固定 pipeline，因为它不是按固定顺序一步走到底，而是一个带反馈的闭环。  
关键在于 `Validator` 的输出会影响下一步动作：证据不足时可以继续检索、重规划，而不是固定进入生成。  
所以它虽然有清晰的模块边界，但执行过程是动态决策驱动的，不是死板流水线。

---

## 六、这一类你现在最该背熟的 10 句话

1. 我这个架构不是为了多 Agent 而多 Agent，而是从科研问答任务链路反推出来的。  
2. 科研问答天然包含规划、检索、验证、生成四类不同问题，所以不能混成一个单体模块。  
3. Orchestrator 负责“下一步做什么”，它是系统的策略层。  
4. Retrieval 负责“去哪里找证据、抽什么证据”，它不负责判断能不能回答。  
5. Validator 负责“当前证据是否足够回答”，这是系统和普通 RAG 的核心差别。  
6. Synthesis 负责“基于已验证证据组织答案”，它不承担证据资格判断。  
7. Memory 负责 recall / write，是能力层，不做高层策略决策。  
8. 这个架构最大的价值，是把“能不能回答”和“怎么回答”分开。  
9. 如果不拆出 Validator，系统最容易出现“证据不够但答案说得很像对的”问题。  
10. 这种拆法也让后面 RL 的训练对象更清晰，因为 Orchestrator 天然对应序贯决策。

## 七、这一类怎么练

你现在可以按下面顺序练：

1. 先用 1 分钟回答：`为什么采用 Orchestrator-Worker 架构？`
2. 再用 2 分钟回答：`五个核心模块分别负责什么？`
3. 再练：`为什么不是一个大模型一步到位？`
4. 再练：`为什么 Validator 必须独立出来？`
5. 最后练：`模块之间是怎么协作形成闭环的？`

你练的时候，一定不要只背模块名。  
每次都强迫自己说出一句“因为业务里会出现什么问题，所以我才这样拆”。

下一轮如果你继续，我就按这个顺序写 **第三类：检索类问题**，还是保持同样结构：

- 先讲这一类在考什么
- 再逐条讲文档里的问题答案
- 最后补充高频面试题和标准答案
