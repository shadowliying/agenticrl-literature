# 第三类补充：调取全文、Replan、StateMachine 与召回融合

这一部分补的是检索类问题里最容易被面试官继续追问的几个点：

- 调取全文到底是不是通过 MCP 做的
- 谁来判断什么时候要读全文
- 读全文和 `replan` 是什么关系
- StateMachine 判断下一步时，是看自然语言条件，还是看结构化代码规则
- 多路召回结果拿回来之后，到底怎么融合

---

## 1. 调取全文本身是谁执行的

全文读取本身是通过 **MCP 工具层** 完成的。

也就是说：

- `RetrievalAgent` 不自己实现网页正文抓取
- 它通过 MCP 去调用正文解析工具，例如 `url_parser` 或 reader 类工具
- Agent 负责做决策，工具负责做执行

一句话记忆：

> Agent 决定“要不要读全文”，MCP 工具负责“把全文拿回来”。

---

## 2. 谁来判断什么时候要调取全文

这个判断不是 MCP 工具自己做的，也不是一句自然语言 prompt 临场拍脑袋决定的。

更准确的分工是：

- `Orchestrator`：在一开始输出结构化 Plan，提前定义好后续可能的检索分支
- `Validator`：在摘要级证据出来后，输出结构化评分和缺失信息
- `StateMachine / Plan 规则`：根据结构化字段判断下一步走向
- `RetrievalAgent`：执行“继续摘要检索”或者“调取全文”

所以更准确的说法是：

> 是否进入全文，不是工具判断，也不是每一步重新让 Orchestrator 临场发挥，而是第一次 Plan 中就预埋了条件分支；执行到 Validate 之后，再由 StateMachine 根据 Validator 的结构化结果命中“全文展开”分支。

---

## 3. 调取全文和 Replan 的区别

这两个概念非常容易混。

### 3.1 调取全文

调取全文通常是 **原 Plan 内部的分支执行**，说明：

- 当前检索方向大体是对的
- 当前候选文档本身也相关
- 问题不是“方向错了”，而是“证据深度还不够”

典型场景：

- `relevance` 很高，但 `coverage` 不够
- `support_strength` 偏低，只有概述，没有实验或细节支持
- `missing_slots` 包含 `reason`、`experiment_support` 这类细粒度槽位
- 摘要之间没有严重冲突，但摘要不足以支撑完整回答

这时应该在原 Plan 内把下一步升级成“对高价值文档调取全文”。

### 3.2 Replan

`replan` 是 **原 Plan 失效后重新生成计划**，通常表示：

- 当前检索路径本身有问题
- 连续几轮 `info_gain` 很低
- 关键槽位长期补不上
- 候选来源明显偏题
- 来源冲突严重，需要换检索路线

一句话区分：

> 调取全文 = 原计划内的加深检索  
> Replan = 原计划方向错了，要换路

---

## 4. 更准确的执行链路

你可以把这条链直接用于面试表达：

```text
Question
  -> Orchestrator 生成 Plan
  -> Retrieval 做摘要级检索
  -> Validator 输出结构化评分
  -> StateMachine / Plan规则判断：
       - 如果证据足够 -> Synthesis
       - 如果高相关但缺关键槽位 -> Read Full Text
       - 如果方向错了/长期低增益 -> Replan
```

这个口径的重点是：

- Orchestrator 不是每一步都重新输出一个全新 Plan
- 正常情况下，后续是沿着第一次 Plan 里的条件分支往下执行
- 只有原 Plan 不再适合时，才会重新调用 Orchestrator 做 `replan`

---

## 5. 初始 Plan 里如何表达“按需全文展开”

更合理的做法，不是让 Plan 只写一句“必要时读全文”，而是把它写成结构化分支。

下面是一个更像真实系统的示例：

```json
{
  "goal": "比较 BERT 和 RoBERTa 的预训练差异，并解释 RoBERTa 去掉 NSP 的原因及实验支持",
  "steps": [
    {
      "step_id": "S1",
      "action": "RETRIEVE_SUMMARY",
      "metadata": {
        "required_slots": ["entity", "difference", "reason", "experiment_support"],
        "top_k": 5
      }
    },
    {
      "step_id": "S2",
      "action": "VALIDATE",
      "metadata": {
        "sufficiency_threshold": 0.75,
        "replan_threshold": 0.60
      },
      "transitions": [
        {
          "condition": "sufficiency_score >= 0.75",
          "next_step": "S5"
        },
        {
          "condition": "relevance >= 0.80 && missing_slots contains any ['reason', 'experiment_support']",
          "next_step": "S3"
        },
        {
          "condition": "0.60 <= sufficiency_score < 0.75",
          "next_step": "S4"
        },
        {
          "condition": "sufficiency_score < 0.60 || info_gain_low_for_multiple_rounds == true",
          "next_step": "REPLAN"
        }
      ]
    },
    {
      "step_id": "S3",
      "action": "RETRIEVE_FULL_TEXT",
      "metadata": {
        "via_mcp_tool": "url_parser",
        "max_docs": 3,
        "focus_slots": ["reason", "experiment_support"]
      }
    },
    {
      "step_id": "S4",
      "action": "RETRIEVE_MORE",
      "metadata": {
        "query_hint_from_validator": true
      }
    },
    {
      "step_id": "S5",
      "action": "SYNTHESIS"
    }
  ]
}
```

这段结构说明：

- `S3 = 调取全文`
- `REPLAN = 重新生成计划`
- 它们不是一回事

## 6. Validator 输出如何触发“读全文”

读全文的关键不是自然语言描述，而是 `Validator` 的结构化输出。

例如：

```json
{
  "sufficiency": false,
  "sufficiency_score": 0.66,
  "coverage": 0.62,
  "relevance": 0.88,
  "support_strength": 0.43,
  "consistency": 0.92,
  "source_quality": 0.81,
  "freshness": 0.76,
  "info_gain": 0.58,
  "missing_slots": [
    "reason",
    "experiment_support"
  ],
  "conflicts": [],
  "selected_doc_ids_for_full_text": [
    "doc_2",
    "doc_4"
  ],
  "suggested_action": "read_full_text",
  "suggested_reason": "high_relevance_but_insufficient_support"
}
```

这个结果的含义是：

- `relevance` 很高，说明方向是对的
- `coverage` 和 `support_strength` 不够，说明摘要碰到了主题，但没有碰到关键细节
- `missing_slots` 明确告诉系统缺的是 `reason` 和 `experiment_support`
- 所以这一步更适合调取全文，而不是直接 `replan`

更像真实系统的解释方式是：

> 高相关但低覆盖、低支持强度，通常意味着“方向对了，但证据还不够深”，这时应优先做全文展开。

## 7. StateMachine 是怎么判断下一步的

这里要区分 **展示层** 和 **执行层**。

### 7.1 展示层

为了方便面试和文档表达，我们可以把条件写成人类可读形式：

```json
{
  "condition": "relevance >= 0.80 && missing_slots contains any ['reason', 'experiment_support']",
  "next_step": "S3"
}
```

但真正执行时，不应该依赖自然语言字符串临场解释。

### 7.2 执行层

真正落地时，StateMachine 读的是结构化字段，然后用代码规则判断。

也就是说，StateMachine 的输入更像一个 `context dict`：

```python
context = {
    "state": "VALIDATE",
    "sufficiency_score": 0.66,
    "relevance": 0.88,
    "coverage": 0.62,
    "support_strength": 0.43,
    "missing_slots": ["reason", "experiment_support"],
    "conflicts": [],
    "conflict_ratio": 0.0,
    "info_gain": 0.58,
    "low_info_gain_rounds": 0,
    "has_high_quality_source": True,
    "full_text_allowed": True
}
```

然后代码做规则判断：

```python
if context["sufficiency_score"] >= 0.75:
    next_step = "SYNTHESIS"
elif (
    context["relevance"] >= 0.80
    and context["full_text_allowed"]
    and set(context["missing_slots"]) & {"reason", "experiment_support"}
):
    next_step = "RETRIEVE_FULL_TEXT"
elif 0.60 <= context["sufficiency_score"] < 0.75:
    next_step = "RETRIEVE_MORE"
else:
    next_step = "REPLAN"
```

所以 StateMachine 不是去“理解自然语言条件”，而是去读取：

- 数值型字段：`sufficiency_score`、`relevance`、`coverage`、`support_strength`
- 列表型字段：`missing_slots`、`conflicts`
- 布尔型字段：`full_text_allowed`、`has_high_quality_source`

一句话记忆：

> 展示层：字符串条件  
> 执行层：字典字段 + 代码规则

---

## 8. `contains any` 这种条件在代码里怎么落地

像下面这种人类可读条件：

```text
missing_slots contains any ['reason', 'experiment_support']
```

在真正实现里，更合理的是做集合交集判断：

```python
target_slots = {"reason", "experiment_support"}
missing_slots = set(context.get("missing_slots", []))

if missing_slots & target_slots:
    next_step = "RETRIEVE_FULL_TEXT"
```

也就是说：

- 文档里可以写成 `contains any`
- 代码里应该落成 `set intersection`

这比“直接解析自然语言字符串”更像真正的工程实现。

## 9. 召回结果怎么融合

这个点在检索类问题里很重要，而且很容易被追问。  
如果只说“做了多路召回和 rerank”，面试官很可能会继续问：

> 多路召回拿回来之后，你是直接拼起来，还是做了融合？

更合理、也更像真实系统的说法是：

> 多路召回的结果不会直接拼接，而是先做 doc 级去重、snippet 级归并、分数归一化、rerank 重排，再按 entity 和 slot 做聚合，最后形成 evidence bundle 交给 Validator。

也就是说，真正的链路更像：

```text
multi-recall
  -> doc 去重
  -> snippet 归并
  -> score normalization
  -> rerank
  -> slot/entity 聚合
  -> evidence bundle
  -> Validator
```

### 9.1 为什么不能直接把召回结果拼起来

因为多路召回通常会带来下面几类问题：

- 同一篇文档被不同 query 或不同召回器重复命中
- 同一个结论被多个 snippet 重复表达
- dense / lexical / cache 通道的分数尺度不一致
- 某些结果主题相关，但并不支持当前缺失槽位
- 摘要和全文可能都命中同一篇文档，但价值不同

如果不做融合，后面会出现两个典型问题：

1. `Validator` 会看到一堆重复证据，误以为信息很多  
2. `Synthesis` 更容易把重复描述和噪声一起带进去  

所以“融合”不是锦上添花，而是检索闭环里很关键的一步。

### 9.2 多路召回一般来自哪些入口

在这个项目口径里，可以统一讲成：

- 原始 query 的召回
- query rewrite 后的召回
- keyword / lexical 检索
- dense retrieval 检索
- semantic cache 命中的召回

也就是说，召回阶段本来就不是单一路径，所以后面一定需要融合。

### 9.3 第一步：doc 级去重

先把明显重复的文档合并掉。  
去重键一般可以是：

- `doc_id`
- `url`
- `paper_id`
- 规范化标题

比如同一篇 arXiv 论文被不同 query 或不同通道重复命中，这时应该先合并成一个 doc 节点，而不是让它在后面重复参与评分。

### 9.4 第二步：snippet 级归并

即使 doc 去重之后，snippet 也还是可能重复。  
这一步通常会：

- 去掉高相似重复片段
- 合并同一 doc 的相邻片段
- 优先保留更完整、更有支持力的版本

它的目标是避免同一条证据在后面“虚增权重”。

### 9.5 第三步：分数归一化

不同召回通道的分数不可直接比较。  
例如：

- dense retrieval 相似度
- BM25 分数
- cache hit 相似度
- reranker 分数

这些分值范围和语义都不一样，所以融合前要先做归一化或者 rank-based 映射，让它们变得可比较。

一句话记忆：

> 多路召回不是直接比谁的分值大，而是先把分数变成同一语义尺度。

### 9.6 第四步：rerank 重排

归一化之后，还不能直接交给 Validator。  
因为召回只解决“找到了候选”，没解决“哪些候选最值得保留”。

所以后面要做 rerank。  
这里不是只看一般相关性，而是更看：

- 当前 query intent
- 当前缺失槽位
- 证据是否真的有支持力

比如当前缺的是 `reason` 和 `experiment_support`，那仅仅说明“RoBERTa 去掉了 NSP”的摘要虽然相关，但不应该排在最前；带有 ablation 结果和原因解释的片段，对当前问题更有支撑价值。

### 9.7 第五步：按 entity 和 slot 聚合

这是最贴近你这个项目的融合方式。  
最终不应该只得到一个 top-k 文档列表，而应该进一步组织成：

- 哪些 evidence 在支持哪个 entity
- 哪些 evidence 在覆盖哪个 slot

例如：

```json
{
  "entity_groups": {
    "BERT": ["snippet_1", "snippet_2"],
    "RoBERTa": ["snippet_3", "snippet_4"]
  },
  "slot_groups": {
    "difference": ["snippet_2", "snippet_3"],
    "reason": ["snippet_5"],
    "experiment_support": ["snippet_6", "snippet_7"]
  }
}
```

这样 `Validator` 才能真正判断：

- 哪些槽位已经覆盖
- 哪些槽位还缺
- 哪个实体的证据已经足够

### 9.8 如果摘要和全文都命中同一篇文档，怎么融合

更稳的说法不是二选一，而是保留两层表示：

- 摘要负责高层 overview 和初步相关性
- 全文片段负责 `reason`、`experiment_support` 这类关键槽位的强支撑

例如：

```json
{
  "doc_id": "doc_2",
  "summary_evidence": ["RoBERTa removes NSP and changes training strategy."],
  "full_text_evidence": [
    {
      "slot": "reason",
      "text": "NSP did not consistently improve downstream performance."
    },
    {
      "slot": "experiment_support",
      "text": "Ablation results showed removing NSP did not hurt performance."
    }
  ]
}
```

这样后面：

- `coverage` 可以看摘要 + 全文联合覆盖
- `support_strength` 更偏向全文证据

### 9.10 面试时最稳的标准回答

> 多路召回的结果我不会直接拼接，而是先做 doc 级去重、snippet 级归并和分数归一化，再经过 rerank 把真正和当前 query 及缺失槽位最相关的证据提到前面。重排之后还会按 entity 和 slot 做聚合，形成一个 evidence bundle，再交给 Validator，而不是直接丢给生成模块。这样做的好处是，Validator 看到的不是一堆无序结果，而是已经融合好的“哪些来源支持哪个槽位”的证据集合。对于同一篇文档的摘要和全文，我通常会保留两层表示：摘要负责 overview，全片段负责 reason、experiment_support 这类关键槽位的强支撑。

## 10. 面试时最稳的标准回答

### 10.1 谁来判断什么时候读全文

> 全文读取本身是通过 MCP 工具层完成的，不是 Agent 自己硬抓网页。至于什么时候调全文，不是工具自己判断，也不是纯自然语言 prompt 临时决定，而是由第一次 Orchestrator 输出的结构化 Plan 预埋条件分支，再由 Validator 的结构化反馈和 StateMachine 的规则判断共同驱动。如果当前摘要证据高相关但关键槽位缺失，或者支持强度不足，那系统就会在原 Plan 内升级成全文展开；只有在方向明显错了、连续低信息增益或者当前计划失效时，才会 replan。

### 10.2 调全文和 Replan 的关系

> 读全文通常不是 replan，而是原 Plan 内的加深检索动作。只有当 Validator 的反馈说明当前检索方向本身有问题，比如关键槽位长期补不上、信息增益持续很低、或者来源严重冲突时，系统才重新调用 Orchestrator 做 replan。简单说，调全文是原计划内的 deeper retrieval，replan 是重新换路线。

### 10.3 StateMachine 怎么判断条件

> StateMachine 真正执行时不是去理解自然语言条件，而是读取 Validator 输出的结构化字段，再走代码规则判断。像 `sufficiency_score`、`relevance` 这种是数值比较，`missing_slots contains any [...]` 在实现上就是列表或集合交集判断，`conflicts` 则可以看冲突列表或冲突比例。所以展示时我会把条件写成人类可读字符串，但真正落地时底层是 `context dict + rule function` 的方式执行。

---

## 11. 一句话记忆版

- 调全文 = 原 Plan 内的分支执行
- Replan = 原 Plan 失效后重新生成 Plan
- MCP 负责执行全文读取，不负责决定何时读取
- StateMachine 看结构化字段做代码判断，不看自然语言现场理解
- 多路召回结果先融合成 evidence bundle，再交给 Validator，不直接丢给生成模块
