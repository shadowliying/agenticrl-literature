**第七类：Memory 与 Context 类问题**

这一类在面试里非常容易被低估，但实际上很能拉开差距。  
因为很多人会说“我们加了 memory 提升多轮能力”，但一追问就会开始含糊：

- `memory` 和 `context` 到底有什么区别
- 为什么不是直接把历史对话拼进上下文就行
- 为什么要分三层
- 谁来读 memory，谁来写 memory
- 什么该写，什么不该写
- 记错了怎么办，过期了怎么办，污染了怎么办

如果你这一类讲得清楚，面试官会觉得你不是只会搭一个 Agent 流程，而是真的考虑了系统在多轮、长链路、重复问题、实体追踪这些业务场景下怎么稳定工作。

---

## 一、这一类问题到底在考什么

面试官主要在看 7 件事：

1. 你是否真正理解 `Memory` 和 `Context` 的区别  
2. 你能不能解释为什么科研问答场景必须做 memory  
3. 你知不知道为什么 memory 不应该是独立高层 Agent  
4. 你会不会讲三层记忆分别解决什么业务问题  
5. 你能不能讲清 recall / write 的时机和策略  
6. 你有没有考虑 memory pollution、staleness、错误传播  
7. 你能不能把 memory 设计和实体追踪、多轮追问、成本控制挂钩  

---

## 二、这一类的学习目标

你学完这一类，至少要做到：

- 能清楚区分 `Context` 和 `Memory`
- 能解释为什么科研问答场景需要三层记忆
- 能说清为什么 Memory Layer 不是独立 Agent
- 能说清 pre-plan recall 和 post-plan recall 的区别
- 能说清 entity memory 是怎么支持多轮追问的
- 能说清语义缓存为什么能降成本
- 能解释 memory write 的筛选标准
- 能回答记忆污染、过期、冲突怎么处理

---

## 三、先建立一个总理解

这一类最核心的一句话是：

> Context 是当前轮模型实际看到的输入窗口，Memory 是系统在窗口之外长期保存、可按需召回的结构化历史。

也就是说：

- `Context` 更像“这次推理时桌面上摊开的资料”
- `Memory` 更像“档案室里的资料库”

两者不是一个东西。

如果你只靠 Context，不做 Memory，会有三个直接问题：

1. 多轮一长，上下文窗口不够  
2. 重复问类似问题时，每次都要重新检索  
3. 代词、省略、实体别名在多轮里很容易丢失  

所以科研问答场景里，Memory 不是锦上添花，而是为了解决：

- 多轮连续性
- 检索降本
- 实体跟踪
- 长链路状态保持

---

## 四、Memory 和 Context 到底有什么区别

这是这一类第一高频题。

**标准答法：**

`Context` 是当前这一轮真正送进模型的即时输入，它强调的是“这次推理立即可见的信息”；  
`Memory` 是系统在对话窗口之外长期保存的历史信息仓库，它强调的是“过去有价值的信息可以被后续检索和复用”。

两者区别主要有四点。

### 1. 生命周期不同
- `Context` 只对当前这次推理生效
- `Memory` 会跨轮、跨任务持续存在

### 2. 存储范围不同
- `Context` 受窗口大小限制
- `Memory` 不受单次上下文窗口限制

### 3. 访问方式不同
- `Context` 是直接输入
- `Memory` 是先 recall，再有选择地装配进 context

### 4. 信息质量要求不同
- `Context` 可以是当前临时过程信息
- `Memory` 应该更偏高价值、高复用、经过筛选的信息

一句话总结：

> Context 是“当前给模型看的”，Memory 是“系统长期记住的”。

---

## 五、为什么不直接把历史对话全塞进 Context

这个问题一定会被问。

**标准答法：**

因为把历史全塞进 Context 只能解决非常短期的问题，解决不了真正的系统级问题。

第一，窗口限制。  
科研问答经常涉及长链路检索和多轮追问，历史一长，全部塞进 context 根本不现实。

第二，噪声问题。  
不是所有历史内容都值得继续带入当前轮。  
如果把所有历史都塞进来，会把大量低价值过程信息一起带进来，反而干扰当前判断。

第三，结构化复用能力差。  
历史对话原文通常是非结构化的，而真正有价值的 memory 往往是结构化信息，比如：
- 上轮已经确定的实体
- 曾经检索过的高质量证据摘要
- 某个 query 的缓存结果

第四，无法做长期复用。  
如果用户过几天问一个高度相似的问题，仅靠上一轮 context 已经没意义了，但 memory 还能继续发挥作用。

所以我不会把 memory 设计成“历史对话搬运工”，而是把它设计成：
- 有筛选
- 可结构化
- 可长期复用
- 可按需 recall
的能力层。

---

## 六、为什么科研问答场景特别需要 Memory

你不能只说“为了支持多轮对话”，那太浅。  
你要贴业务。

**标准答法：**

科研问答比普通聊天更需要 Memory，主要是因为这类问题天然有长期依赖和结构化依赖。

### 1. 多轮追问很常见
比如：
- 第一轮：`介绍一下 BERT 的预训练任务`
- 第二轮：`那它为什么后来被 RoBERTa 改掉了部分设计`
- 第三轮：`这个改动有没有实验支持`

这里的“它”“这个改动”如果没有 memory，很容易丢。

### 2. 同一主题会反复出现相似检索
比如用户会反复问：
- `BERT 的预训练方法是什么`
- `BERT pretraining 的核心设计是什么`
- `BERT 的 MLM 和 NSP 是怎么定义的`

如果每次都从头搜索，成本会很高。  
这正是语义缓存存在的意义。

### 3. 科研对象强依赖实体追踪
科研问答里有大量：
- 模型名
- 论文名
- 数据集名
- benchmark 名
- 作者名
- 方法别名

这些都属于实体。  
一旦实体追踪断掉，后面的 reasoning 很容易错。

### 4. 有些问题是长期主题型，不是一轮结束
比如：
- 某个方向的综述
- 某个 benchmark 的长期跟踪
- 某个方法家族的连续对比

这种任务天然适合把高价值中间结果沉淀进 memory，而不是每轮都重做。

一句话总结：

> 科研问答里的 Memory，不只是为了“记住聊天内容”，而是为了“记住可以持续复用的研究状态”。

---

## 七、为什么 Memory 不是独立 Agent，而是 Memory Layer

这是很高频的问题，你前面已经建立了基础，这里要讲得更系统。

**标准答法：**

我把 Memory 设计成能力层，而不是独立 Agent，核心原因是它不做高层策略决策。

Memory 负责的是两类事：
- recall：在合适的时候把有价值的历史拿出来
- write：在任务结束后把高价值信息写回去

但它不负责决定：
- 下一步要不要检索
- 要不要 replan
- 什么时候进入 synthesis

这些决定仍然应该由 Orchestrator 和 StateMachine 控制。  
如果让 Memory 自己变成一个高层 Agent，会带来两个问题：

### 1. 职责和 Orchestrator 重叠
谁来决定“要不要用记忆”？  
如果 Memory 也是决策者，那它和 Orchestrator 的边界就会模糊。

### 2. 系统复杂度明显上升
Memory 的核心任务本质上不是推理，而是存取、召回和结构化管理。  
把它做成 Layer 更自然，也更符合工程实现。

一句话总结：

> Orchestrator 决定“要不要用记忆”，Memory 决定“能提供什么记忆”；前者是策略，后者是能力。

---

## 八、三层记忆分别是什么，为什么要分三层

这是这一类最核心的问题之一。

我建议统一口径就是你简历里的那套：

- 短期会话记忆
- 语义缓存
- 实体知识记忆

---

### 1. 短期会话记忆
它解决的是：**当前会话里的多轮连续性问题**。

典型场景：
- 用户上一轮说了 `RoBERTa`
- 下一轮说“它为什么效果更好”
- 当前 query 本身没有显式实体

如果没有短期会话记忆，系统要么猜，要么重新问用户，都会很差。

它通常记什么：
- 近期 query 摘要
- 当前会话中的核心实体
- 当前任务主题
- 上轮结论摘要
- 已经确认过的比较对象

一句话理解：
> 短期会话记忆解决“这一轮的它是谁”。

---

### 2. 语义缓存
它解决的是：**重复或相似问题的检索成本问题**。

典型场景：
- 用户反复问 BERT 预训练相关问题
- 不同表达其实在问同一件事
- 历史已经检索过高质量 evidence

如果每次都重新搜，API 成本和时延都会上去。  
所以语义缓存的作用是：
- 按 query embedding 或主题相似度找相似历史问题
- 复用之前的高质量证据摘要或检索结果

它通常记什么：
- query embedding
- query canonical form
- top evidence summary
- source list
- freshness
- cache hit statistics

一句话理解：
> 语义缓存解决“这个问题以前其实已经搜过了”。

---

### 3. 实体知识记忆
它解决的是：**实体追踪、别名归一化和指代消解问题**。

典型场景：
- `BERT`
- `Bidirectional Encoder Representations from Transformers`
- 多轮里的“它”
- 某篇论文简称
- 数据集别名

这些其实都可能指向同一个实体节点。  
如果不做实体知识记忆，系统在多轮和复杂科研语境里很容易断链。

它通常记什么：
- canonical entity
- aliases
- entity type
- related papers / methods
- latest known attributes
- confidence / freshness

一句话理解：
> 实体知识记忆解决“不同说法是不是在说同一个东西”。

---

## 九、为什么不能做成一个统一大 Memory 就够了

这个问题很容易被问到。

**标准答法：**

因为这三类问题本质上不是同一个问题：

- 短期会话记忆，关注的是当前对话连续性
- 语义缓存，关注的是相似 query 的检索复用
- 实体知识记忆，关注的是对象级长期稳定表示

如果混成一个统一 memory，会有三个问题：

### 1. 召回目标混乱
当前 query 是在找“上一轮主题”，还是在找“相似问题缓存”，还是在做“实体消解”？  
如果统一在一个池子里，召回噪声会很大。

### 2. 更新策略不同
- 短期会话记忆适合快写快过期
- 语义缓存适合按命中和 freshness 更新
- 实体记忆适合保守更新、高置信写入

### 3. 过期机制不同
- 会话记忆天然短生命周期
- 语义缓存看 query 热度和 freshness
- 实体记忆相对更长期，但也要做属性级过期控制

一句话总结：

> 三层记忆不是为了复杂而复杂，而是因为三类业务问题的写入、召回和过期逻辑都不同。

---

## 十、Memory 在流程里到底什么时候用

这一段一定要讲清楚，你前面已经问过类似问题。

我建议你统一成两个时机：

### 时机一：Pre-plan 轻量 Recall
发生在 Orchestrator 生成 Plan 之前。  
目的是帮助它正确理解问题。

这里主要用：
- 短期会话记忆
- 实体知识记忆

它解决：
- 代词消解
- 上轮主题继承
- 当前 query 的真实主体识别

比如：
- 用户问：`那它为什么效果更好`
- 在做 Plan 之前，系统先 recall 出“它 = RoBERTa”
- Orchestrator 才能正确生成 `required_slots` 和 `entities`

这一点非常关键。

---

### 时机二：Post-plan 任务级 Recall
发生在 Plan 之后、更偏 Retrieval 侧。  
目的是：
- 复用相似检索结果
- 给 Retrieval 补线索
- 降低重复搜索成本

这里主要用：
- 语义缓存
- 历史证据摘要
- 历史 query 的高质量 source list

所以你可以统一成一句话：

> Pre-plan recall 解决“问题理解”，post-plan recall 解决“检索增强”。

---

## 十一、Memory Write 是什么时候做的

这也是高频题。

最稳的口径是：

Memory write 不应该在每一步都无脑发生，而应该在以下几种时机做：

### 1. 任务结束后写回
这是主写回点。  
因为这时：
- 当前 query 已经基本完成
- 证据质量更可判断
- 不容易把中间噪声写进去

### 2. 某些高置信中间结论产生时
比如：
- 已经明确完成实体消解
- 已经确认高质量 canonical entity
- 已经命中高质量 cacheable result

这类也可以提前写，但要更保守。

### 3. 不建议在低置信中间步骤频繁写
因为这最容易造成 memory pollution。

一句话总结：

> recall 可以频繁做，write 要非常克制。

---

## 十二、什么信息应该写入 Memory，什么不该写

这题很重要，最像“真做过”的人会主动讲。

### 应该写入的
- 高置信实体映射
- 高质量 evidence 摘要
- 已验证的 query -> evidence 缓存
- 高复用主题摘要
- 稳定别名映射
- 高价值中间结论

### 不应该直接写入的
- 低置信猜测
- 冲突尚未解决的信息
- 纯临时过程信息
- 明显时间敏感、但 freshness 不确定的信息
- 证据不足的中间判断

一句话总结：

> Memory 写入标准不是“有信息就写”，而是“高置信、高复用、可长期受益才写”。

---

## 十三、可以写成什么样的数据结构

这一类你最好也准备一些结构化 sample，不然容易讲得太虚。

### 1. 短期会话记忆 sample

## 十四、entity 和记忆是怎么连起来的

这一部分要和第四类 Validator 逻辑接起来。

你现在统一的讲法应该是：

- `entity` 是一个 slot type
- 具体 entity value 通常在 Plan 阶段就应该知道
- 这个值的来源有两种：
  - 当前问题直接抽取
  - Pre-plan memory recall 做指代消解

也就是说，用户如果说：
- `它为什么去掉 NSP`

系统不是到了 Validator 才知道 entity 是谁，  
而是在 Orchestrator 做 Plan 之前，通过短期会话记忆和实体记忆，先把“它”还原成 `RoBERTa`，然后再进入：
- `required_slots`
- `slot_values`
- `entities`

一句话总结：

> Memory 不是在事后补救 entity，而是在 Plan 前帮助系统把 entity 理解对。

## 十五、Memory Pollution 是什么，为什么危险

这是高频深挖题。

**标准答法：**

Memory pollution 指的是低质量、错误、冲突或临时性的内容被写进 memory，后续又被 recall 出来继续影响系统判断。

它危险在于：
- 一次错误可能跨轮传播
- 记忆污染比单轮 hallucination 更难发现
- 被污染的 memory 会影响 Orchestrator 的 Plan、Retrieval 的 query、Validator 的判断

科研问答里这尤其危险，因为一个错误的实体归一化、一个错误的结论摘要，后面可能被反复当成“已知事实”。

---

## 十六、怎么防止 Memory Pollution

你要讲成三层防线。

### 第一层：写入门槛
只有满足以下条件的信息才允许写入：
- 高置信
- 高复用
- 已验证
- 来源质量合格

### 第二层：类型隔离
不同 memory 层分开管理：
- 会话记忆不直接污染实体知识记忆
- 语义缓存不自动升级为长期实体事实

### 第三层：freshness 和 invalidation
- 时间敏感信息必须带 freshness
- 命中冲突时要允许失效或降权
- cache 不应该永久有效

一句话总结：

> Memory 最关键的不是“记得多”，而是“记得干净”。

---

## 十七、过期和冲突怎么处理

这是非常像工程落地的一问。

### 1. 对短期会话记忆
- 按会话生命周期自然衰减
- 超过若干轮可降权或淘汰

### 2. 对语义缓存
- 看 freshness
- 看最近命中效果
- 如果命中后发现 Validator 总是不通过，可以降权或清除

### 3. 对实体知识记忆
- 不轻易全量删除
- 对属性级信息做 freshness 管理
- 对冲突属性保留多值并标记来源 / 置信度

如果面试官问“遇到冲突怎么办”，你最稳的说法是：

> 对实体知识记忆，冲突不应该被简单覆盖，而应该保留来源和置信度，必要时在 recall 时提示存在分歧，而不是把后写入的信息直接当成真相。

---

## 十八、为什么语义缓存能降成本

这题你简历里有成本下降 27%，很容易被追问。

**标准答法：**

语义缓存降本，主要来自两个方面。

### 1. 减少重复外部检索
很多科研 query 只是表达不同，但本质上在问同一件事。  
如果命中语义缓存，就不需要每次都重新走完整检索链路。

### 2. 减少无效深搜
如果缓存里已经有高质量摘要级 evidence，很多问题可以少走一次全文读取或少走几步补检索。

所以语义缓存不是简单的“字符串完全一致缓存”，而是：
- 允许相似 query 命中
- 复用历史高质量 evidence summary
- 但仍然接受 Validator 和 freshness 的再次检查

一句话总结：

> 缓存不是替代检索，而是让系统避免在相似问题上反复付同样的检索成本。

---

## 十九、Memory 的实际业务问题会有哪些

这一段你最好会讲几个“坑”。

### 1. 代词消解失败
用户说“它”“这个模型”“前一个方法”，如果 pre-plan recall 没做好，Plan 一开始就错。

### 2. 语义缓存误命中
两个 query 表面相似，但真正问的槽位不同，如果缓存粗暴复用，会把旧 evidence 硬套到新问题上。

### 3. 实体别名没归一
同一实体多个名字没合并，导致 recall 断裂。

### 4. 旧信息过期
尤其是时间敏感问题，如果 cache 或 entity attribute 太旧，会误导回答。

### 5. Memory 写入过宽
如果中间过程信息大量写入，系统会越来越“健忘地混乱”，不是越来越聪明。

## 二十、你可以直接背的第七类核心回答

如果面试官问：

> 你这个 Memory 到底是怎么设计的？为什么不直接用 Context？

你可以直接答：

> 我这里会严格区分 Memory 和 Context。Context 是当前这一轮真正送进模型的输入窗口，Memory 是系统在窗口之外长期保存、可按需召回的结构化历史。科研问答场景里只靠 Context 不够，因为这类任务多轮追问多、实体指代多、相似检索反复出现，而且上下文窗口有限，所以我把 Memory 做成一个旁路能力层，而不是简单把历史对话全塞进上下文。  
> 具体设计上我用了三层记忆。第一层是短期会话记忆，主要解决多轮追问里的话题延续和代词消解；第二层是语义缓存，主要复用相似 query 的高质量 evidence，降低重复检索成本；第三层是实体知识记忆，主要做实体归一化、别名映射和跨轮实体追踪。  
> Memory 不是独立 Agent，因为它不做高层策略决策，只负责 recall 和 write。更合理的流程是，Orchestrator 在生成 Plan 之前先做一次轻量 memory recall，用来还原当前 query 的主体，比如把“它”还原成 `RoBERTa`；Plan 之后 Retrieval 侧再做任务级 recall，利用语义缓存和历史证据做检索增强。写入时也不会什么都写，而是只写高置信、高复用、经过验证的信息，避免 memory pollution。这样设计既能解决多轮连续性，又能真正降低检索成本，同时不会让错误记忆不断传播。

## 二十一、这一类的高频追问补充（含答案）

### 1. 为什么 Memory 不直接参与最终决策？
**答案：**  
因为 Memory 的本质是信息供给层，不是策略层。它负责提供历史信息，但不应该接管“下一步做什么”的控制权，否则会和 Orchestrator 职责重叠。

### 2. 为什么语义缓存不能直接代替检索？
**答案：**  
因为缓存只能复用相似历史，不保证当前问题和历史问题完全等价，也不保证历史信息仍然新鲜。所以缓存更像候选加速器，而不是检索替代品，最终仍然需要 Validator 和 freshness 校验。

### 3. 为什么 entity memory 在科研问答里比普通聊天更重要？
**答案：**  
因为科研问答里实体密度很高，而且实体往往有别名、简称、论文名、模型名、作者名、数据集名等多种表达。只靠表面字符串很容易断链，多轮中更容易因为代词或省略出错。

### 4. 如果 memory 里有错误信息怎么办？
**答案：**  
首先要尽量通过写入门槛降低错误进入 memory 的概率；其次 memory 要有 freshness、confidence 和 invalidation 机制；最后 recall 出来的 memory 也不应该被当成绝对真相，而是仍然接受当前轮验证。

### 5. 为什么不把所有中间 evidence 都写进 memory？
**答案：**  
因为中间 evidence 大量是临时过程信息，写入会严重污染 memory。memory 应该保存的是“未来仍然值得复用的信息”，而不是“这次任务里曾经出现过的所有内容”。

### 6. 多轮里用户说“它”，系统到底怎么知道是谁？
**答案：**  
在更合理的流程里，Orchestrator 做 Plan 前会先做一次轻量 memory recall，从短期会话记忆和实体记忆里恢复最近主题实体，再把它写进 plan 的 `entities` 或 `slot_values`，后面 Validator 和 Retrieval 再围绕这个实体展开。

### 7. 为什么记忆要有 freshness？
**答案：**  
因为不是所有科研信息都同样稳定。经典论文事实可能长期稳定，但趋势、排行榜、最新结果、项目现状这类信息会变。没有 freshness，系统会把旧 cache 当新事实用。

### 8. 你怎么判断某条信息值不值得写入 memory？
**答案：**  
我主要看三件事：置信度够不够、未来复用价值高不高、来源质量是否过关。高置信、高复用、来源可靠的信息才值得写，纯临时过程信息和未解决冲突信息不直接写。

## 二十二、这一类你现在最该背熟的 12 句话

1. Context 是当前给模型看的，Memory 是系统长期保存、按需召回的。  
2. 科研问答不能只靠 Context，因为它有多轮追问、实体追踪和重复检索问题。  
3. 我把 Memory 做成能力层，而不是独立 Agent。  
4. Memory 不负责“下一步做什么”，它负责“能提供什么历史信息”。  
5. 短期会话记忆解决多轮连续性。  
6. 语义缓存解决相似 query 的重复检索成本。  
7. 实体知识记忆解决别名归一化、指代消解和跨轮实体追踪。  
8. Pre-plan recall 解决问题理解，post-plan recall 解决检索增强。  
9. recall 可以频繁做，write 必须克制。  
10. memory 写入标准是高置信、高复用、来源可靠。  
11. memory 最怕的不是记得少，而是记错了还不断传播。  
12. 所以 freshness、confidence、invalidation 和类型隔离都很重要。
