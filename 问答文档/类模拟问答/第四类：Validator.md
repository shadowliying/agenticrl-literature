下面这版是可以直接替换你现在“第四类：Validator”的加强版口径。我按“业务动机 -> 评分怎么来 -> 权重为什么这样设 -> 阈值怎么定 -> bad case 怎么解释”来写，尽量贴近面试深挖。

**第四类：Validator 与证据充分性类问题**
这一类是整个项目里最能体现你“不是在做普通 RAG”的部分。前面讲架构、检索、Memory，面试官可能还会觉得你是在讲一个复杂版搜索系统；但只要你把 Validator 讲透，项目的核心差异就立起来了。

Validator 在这个系统里不是一个附属打分模块，而是“回答资格控制器”。它要回答的不是“这些证据看起来相关吗”，而是“这批证据现在有没有资格支撑一次严谨回答”。

---

**1. 为什么科研问答里必须有 Validator**
科研问答和普通搜索问答最大的区别，不是问题更长，而是“答案合格”的标准更高。普通问答里，只要答案大致贴题、事实没明显错，很多时候就能接受；但科研问答里，用户常常问的是比较、归因、趋势、实验支持、方法差异，这类问题天然带多个信息槽位。只覆盖一部分，即使语言上很流畅，也不能算合格。

比如用户问：“RoBERTa 为什么去掉 NSP？这个改动有没有实验支持？”  
如果系统搜到一句“RoBERTa removed NSP”，这只能说明信息相关，但完全不能支撑“为什么”和“有没有实验支持”这两个关键点。没有 Validator，生成模块很容易把这一点已知事实扩展成一段貌似合理的解释；有了 Validator，系统会明确知道：当前只覆盖了“改动是什么”，没有覆盖“原因”和“实验支持”，所以不能放行。

一句话总结：
Validator 不是判断“能不能生成”，而是判断“现在有没有资格生成”。

---

**2. 为什么 Validator 不能只是 bool**
如果 Validator 只返回 `true/false`，系统最多只能知道“现在能答”或者“现在不能答”，但不知道：
- 缺的是哪一类信息
- 当前离可回答还差多少
- 是应该继续检索，还是应该重规划
- 风险来自缺槽位、来源冲突、证据太弱，还是时效不足

科研问答里的“不足”不是单一类型问题。  
有时候是方向对了，但只差一两个细节槽位，这时继续检索即可；有时候是连续几轮都在重复低增益信息，这时应该 replan；还有时候是信息看起来齐了，但来源之间强冲突，这时不能硬答。  
所以 Validator 必须输出结构化结果，而不是一个简单布尔值。

最小可用输出至少应包含：
- `sufficiency_score`
- `missing_slots`
- `conflicts`
- `suggested_action`

你在面试里可以这样说：
“bool 只能做拦截，结构化 Validator 才能驱动下一步动作。”

---

**3. sufficiency_score 是怎么得到的**
这一部分你一定要讲细，因为这是最容易被面试官追问的点。

我的设计思路不是直接拍一个综合分，而是先把“什么叫足够回答”拆成几个可以观测的维度，再做加权融合。因为科研问答里失败模式很稳定，基本就是：
- 关键点没覆盖
- 相关但不对题
- 证据有，但支撑力弱
- 多来源冲突
- 来源不可靠
- 信息过时
- 一直在重复搜索，没有新信息

所以我把 `sufficiency_score` 拆成七个维度：

1. `coverage`
含义：问题要求的关键槽位有没有被覆盖。  
这是核心维度。  
计算方式是：先根据问题类型和 Plan 规则定义 `required_slots`，再判断当前证据覆盖了几个槽位。  
公式可以写成：
```text
coverage = 1 - missing_slots_count / total_required_slots
```

2. `relevance`
含义：证据是不是在直接回答当前问题，而不是只是泛泛相关。  
实现上可以用关键词命中、轻量语义相似度或 reranker 分数归一化来做。  
规则版里可以简化为“问题关键词在证据中命中的比例”。

3. `support_strength`
含义：证据够不够“硬”。  
比如只有概述性描述和有明确实验结果、数字、对比结论，这两种支持力是完全不同的。  
轻量实现里，可以用“平均证据长度 + 是否包含数字或明确结论词”来估计。  
文档和代码里用了一个简单近似：
```text
base = min(1, avg_len / 200)
if has_number:
    base += 0.2
```
再裁剪到 `[0,1]`。

4. `consistency`
含义：多来源之间是否冲突。  
如果冲突高，系统就不应该轻易放行。  
公式可以写成：
```text
consistency = 1 - conflict_ratio
```

5. `source_quality`
含义：来源是否可靠。  
论文原文、官方文档、权威综述和普通博客不能一视同仁。  
如果有来源评分，直接取均值；没有评分时可给中性默认值，比如 `0.5`。

6. `freshness`
含义：证据是否满足当前问题的时效要求。  
例如用户问近三年趋势，如果大部分材料都很旧，这一维就要扣分。

7. `info_gain`
含义：这一轮检索有没有真的带来新信息。  
如果新证据大多是重复内容，就说明继续沿当前路径搜索的价值在下降。  
简单实现可以用：
```text
info_gain = new_snippets_count / current_snippets_count
```
或者和历史片段做去重后计算。

最终综合分是：
```text
sufficiency_score =
  0.35 * coverage
+ 0.20 * relevance
+ 0.15 * support_strength
+ 0.10 * consistency
+ 0.10 * source_quality
+ 0.05 * freshness
+ 0.05 * info_gain
```

---

**4. 为什么权重这样设计**
这里不能只说“经验调的”，要把权重和业务风险对应起来。

`coverage = 0.35` 最高，是因为科研问答里最常见、最致命的错误不是语言不流畅，而是关键点没答全。  
如果用户问“差异 + 原因 + 实验支持”，结果你只覆盖了“差异”，那这个答案在业务上就是失败。所以 coverage 决定“回答有没有骨架”，权重必须最高。

`relevance = 0.20` 放第二，是因为有些证据虽然覆盖了某些槽位，但实际上和当前问题不够贴，可能只是主题相关。  
这一维是防止“覆盖了，但没答在点上”。

`support_strength = 0.15` 也很重要，因为科研问答不能只靠泛描述。  
你要的是可引用、可支撑、可落到实验或事实的证据，而不是一句概括性描述。

`consistency = 0.10` 和 `source_quality = 0.10` 是质量修正项。  
它们不如 coverage 核心，因为前提仍然是“先答全”；但如果来源冲突大、来源不可靠，也绝不能视而不见。

`freshness = 0.05` 和 `info_gain = 0.05` 权重更低，因为它们更多是控制项，而不是回答骨架本身。  
`freshness` 主要在时效敏感问题里非常关键；`info_gain` 更多服务于过程控制，防止无效重复检索。

你可以把这套逻辑概括成一句话：
“权重不是按模型习惯设的，而是按业务损失排序设的。没答全的损失最大，所以 coverage 最高；答偏和证据弱是第二梯队；来源、时效和重复搜索是修正项。”

---

**5. 这些权重是怎么调出来的**
这是你要讲得“像真实做过”的地方。最稳的口径不是说“我做了复杂超参搜索”，而是说你经历了一个“业务规则 -> bad case -> 验证集校准”的过程。

你可以这样讲：

第一步，我先不急着上综合分，而是先做 bad case 分类。  
把一批典型科研问题跑出来，看系统失败主要集中在哪。最后发现，最常见的不是“完全搜不到”，而是：
- 搜到部分相关信息，但缺关键槽位
- 方向是对的，但证据支撑不够硬
- 摘要看着相关，但没法直接回答为什么
- 多来源有轻微冲突
- 连续几轮检索都没新信息

第二步，把这些失败模式映射成维度。  
于是形成了 coverage、relevance、support_strength、consistency、source_quality、freshness、info_gain 这七个指标。

第三步，先给一套偏业务直觉的初始权重。  
初始原则很简单：先保证“答全”，再保证“答准、答稳”，最后再考虑时效和过程控制。  
所以第一版权重就是以 coverage 为最高。

第四步，在验证集上做校准。  
做法不是盯一个数学最优，而是看不同权重下，`sufficiency_score` 和人工判断“是否真的可回答”之间的对应关系。  
如果发现很多“明显不能答”的样本分数仍然高，那就说明 coverage 或 support_strength 权重不够；  
如果发现很多“其实已经可以答”的样本分数老是上不去，那就说明某些修正项过重了。

第五步，固定到一版可解释、稳定的公式。  
最终我更看重的是这套分数能不能稳定区分：
- 明显可答
- 可补一点再答
- 当前方向不对
而不是在小数点后追求一个理论最优。

这套说法很稳，因为它不像吹得太大，又显得你确实有校准过程。

---

**6. 为什么阈值是 0.75 和 0.60**
这部分必须讲成“三段式控制”，不要讲成“两个神秘数字”。

我的设计里，Validator 不是只分“够”和“不够”，而是三种状态：

1. `sufficiency_score >= 0.75`
表示当前证据基本具备稳定回答条件。  
通常意味着关键槽位覆盖较完整，继续检索带来的边际收益已经开始下降。  
这时系统可以放行进入 `SYNTHESIS`。

2. `0.60 <= sufficiency_score < 0.75`
表示处在灰区。  
说明已经有一定证据基础，但还不够稳。  
这一段里最合理的动作通常不是直接回答，也不是立刻 replan，而是继续补检索，尤其去补 `missing_slots` 指向的缺口。

3. `sufficiency_score < 0.60`
表示当前状态不是“再搜一点就好”，而是大概率方向、证据质量或问题拆解本身有明显问题。  
这时继续沿原路径检索收益很低，应该考虑 `REPLAN`。

你可以把这两个阈值的本质讲成：
- `0.75` 是放行阈值
- `0.60` 是重规划阈值
- 中间区间是补证据区间

---

**7. 这两个阈值为什么不是 0.8 和 0.5**
面试官常会故意问这种问题，看你是不是拍脑袋。

最稳的回答方式是：

这些阈值不是理论上唯一正确的数字，而是业务规则和验证集表现共同决定的工作点。  
我调的时候主要看三个指标：
- 回答准确性 / 完整性
- 平均检索步数
- 无效 replan 频率

如果放行阈值设得太高，比如 0.8 以上，系统会变得过于保守，很多已经基本可回答的问题还要继续搜，导致检索成本上升、时延增加。  
如果放行阈值设得太低，比如 0.65 左右，系统又容易在证据不够时过早进入生成。

同理，replan 阈值如果太高，会导致系统动不动就换路线，稳定性变差；如果太低，又会让系统在错误方向上停留太久。

最终 `0.75 / 0.60` 这组阈值比较符合三件事的平衡：
- 足够严格，能拦住证据不足的回答
- 不至于过于保守，避免无意义深搜
- 能把“补检索”和“换方向”区分开

一句话口径：
“这个阈值不是数学推导出来的唯一解，而是业务准确率、搜索成本和流程稳定性三者平衡后的结果。”

---

**8. 硬门槛为什么必要**
单看综合分有一个天然风险：不同维度之间会互相补偿。  
但科研问答里有些错误是不能被补偿的。

比如：
- 关键槽位缺失
- 冲突比例太高
- 高风险问题但来源质量很差
- 时间敏感问题但证据明显过旧
- 证据数量连最小要求都没达到

这些情况如果只看综合分，很可能出现一种错误：其他维度分数把它“抬上去了”，但从业务角度它仍然不应该放行。  
所以我在综合评分之外加了硬门槛。  
综合分负责描述“程度”，硬门槛负责守住“底线”。

你可以这样说：
“规则管底线，分数管细粒度状态。科研场景里两者都不能少。”

---

**9. 一个完整的评分示例**
这个例子你面试里很有用，因为它能把抽象公式落到真实问题。

问题：
“比较 BERT 和 RoBERTa 的预训练差异，并解释 RoBERTa 去掉 NSP 的原因及实验支持。”

假设当前 Validator 拿到的摘要级证据状态是：
- `required_slots = ["entity", "difference", "reason", "experiment_support"]`
- 当前覆盖了 `entity` 和 `difference`
- 缺失 `reason` 和 `experiment_support`
- `missing_slots = 2`
- `relevance = 0.88`
- `support_strength = 0.43`
- `consistency = 0.92`
- `source_quality = 0.81`
- `freshness = 0.76`
- `info_gain = 0.58`

那么：
```text
coverage = 1 - 2/4 = 0.5
```

综合分大概是：
```text
0.35*0.50 +
0.20*0.88 +
0.15*0.43 +
0.10*0.92 +
0.10*0.81 +
0.05*0.76 +
0.05*0.58
≈ 0.656
```

也就是大约 `0.66`。  
这说明：
- 方向对，因为 `relevance` 高
- 证据不够深，因为 `coverage` 和 `support_strength` 偏低
- 当前最合理动作不是 synthesis
- 也未必立刻 replan
- 更合适的是继续补“原因”和“实验支持”，必要时升级到全文读取

这就是一个非常真实的“高相关但不充分”的案例。

---

**10. 如果 sufficiency_score 很高，但最后答案还是错了，怎么解释**
这是很成熟的一问。

如果 Validator 分很高，但最终答案仍然错，通常问题会出在三层之一：

第一，槽位定义层。  
也就是我们以为问题只要求这些槽位，但实际上定义不够细，导致 coverage 虽然高，但“答全”的定义本身就不完整。

第二，证据映射层。  
可能某些证据被误判为覆盖了某个槽位，形成了“伪覆盖”。

第三，生成整合层。  
Validator 放行的是“证据够了”，但 Synthesis 在组织答案时仍可能丢失限制条件、误合并冲突信息，或者表达上过度概括。

所以高分不等于全系统绝对正确，它只说明“当前证据状态达到了放行标准”。  
如果后面错了，就要回头看是槽位定义问题、证据映射问题，还是生成问题。

这个回答很重要，因为它体现你不是盲信打分系统。

**11. 你可以直接拿去用的第四类面试口径**
如果面试官问：“你这个 Validator 到底是怎么设计出来的？”

你可以直接答：

> 我不是先拍一个综合分公式，而是先分析科研问答里最常见的 bad case。最后发现最常见的问题是关键槽位没覆盖、证据弱但看起来相关、多来源轻冲突、以及连续检索没有新信息。所以我把 sufficiency 拆成 coverage、relevance、support_strength、consistency、source_quality、freshness、info_gain 七个维度。权重上 coverage 最高，因为科研问答最致命的错误不是表达不好，而是关键问题没答全。然后我在验证集上看这套分数和人工判断“是否具备回答资格”的对应关系，最后把阈值定成 0.75 放行、0.60 replan，中间区间继续补检索。再加上关键槽位缺失、冲突过高、来源不可靠这些硬门槛，保证系统不会被平均分掩盖掉致命问题。这样 Validator 就既能做可解释放行，也能给后续检索和 RL 提供结构化反馈。  

---

**12. 第四类你现在最该背的核心句**
- Validator 不是在判断“像不像答案”，而是在判断“有没有资格回答”。
- 相关性只是必要条件，充分性才是放行条件。
- sufficiency_score 不是直接拍出来的，而是从 bad case 反推成七个维度。
- coverage 权重最高，因为科研问答最常见的失败是关键点没答全。
- 0.75 / 0.60 本质上是放行区、补证据区和重规划区的三段式控制。
- 硬门槛存在，是为了防止综合分掩盖致命缺陷。
- 分数高但答案错，不一定是 Validator 无效，也可能是槽位定义、证据映射或生成整合出了问题。

---

**13. 权重调优时到底看什么指标**
这里非常容易被问细。更稳的口径不是“看 Judge 分和一些硬指标”，而是：

- **第一部分：答案级指标**
- **第二部分：过程级指标**

### 13.1 答案级指标（主指标）

这部分决定一套权重最终好不好，核心看的是**最终答案质量**，不是向量相似度，也不是单条 evidence 的 embedding 分数。

建议统一讲成：

- `Completion Rate`
- `Key-Point Coverage`
- 人工抽样准确性 / 完整性
- `LLM-as-Judge` 的答案质量评分

这四个指标的意义分别是：

- `Completion Rate`：最终有没有把问题完成掉
- `Key-Point Coverage`：答案有没有覆盖用户真正关心的关键点
- 人工抽样：防止指标看起来不错，但实际答案不可靠
- `LLM-as-Judge`：用于大规模快速比较不同权重配置

一句话记忆：

> 调权重时，主指标看的是最终答案是否答对、答全，而不是向量相似度。

### 13.2 过程级指标（辅助指标）

这部分不直接说明答案质量，但能反映这套权重会不会把系统带偏。

常用的辅助指标包括：

- 平均检索步数
- `replan` 频率
- 低分硬答比例
- 高分误答样本数
- `sufficiency_score` 分布是否健康
- 平均全文读取次数
- 重复检索比例 / 低信息增益轮次

这些指标的作用是帮助判断：

- 系统是不是过于保守
- 系统是不是过于激进
- 是否容易误放行
- 是否会把检索成本拉高

更准确的总结是：

> 调权重时先看答案级质量，再看过程行为是否稳定、是否省成本。

### 13.3 实际调权重时怎么选

一个比较稳的说法是：

- 如果两套权重下答案级指标差异明显，优先保留答案质量更高的那套
- 如果答案级指标差不多，再比较过程级指标：
  - 谁的检索步数更低
  - 谁的 `replan` 更稳
  - 谁的高分误答更少
  - 谁的低分硬答更少

也就是说，过程指标更像**二次筛选器**。

---

**14. `support_strength`、`consistency`、`slot` 到底怎么来**
这一部分如果不讲清楚，面试官会觉得 Validator 只是“拍一个公式”。

### 14.1 `support_strength` 是怎么得来的

`support_strength` 的本质不是“文本越长越好”，而是：

> 当前 evidence 是否足够具体、足够可引用、足够支撑回答。

当前轻量规则版里，采用的是一个可执行近似：

- 先看证据片段平均长度
- 再看是否包含数字、指标、年份等强支持信号

近似公式是：

```text
base = min(1, avg_len / 200)
if has_number:
    base += 0.2
```

为什么这样做：

- 平均长度太短，通常意味着只是主题提及或泛描述
- 包含数字、年份、指标、实验值时，往往说明 evidence 更接近“能支撑结论的事实片段”

面试里更完整的口径可以说成：

> 轻量版里我先用平均片段长度和数字/指标特征去近似 support strength，因为实验类、对比类科研问题里，真正有支撑力的证据往往不是一句泛描述，而是带模型名、数据集、年份、指标或实验结论的片段。后续如果继续增强，这一维还可以加入“是否包含实验术语、是否为原文结论句、是否被多源支持”等特征。

### 14.2 `consistency` 里的冲突怎么判断

当前 Validator 里，`consistency` 本身不是从零发现冲突，而是接收上游传入的 `conflicts` 列表，再量化成：

```text
conflict_ratio = len(conflicts) / len(evidence_snippets)
consistency = 1 - conflict_ratio
```

也就是说，当前 `Validator` 更像“冲突处理器”，不是完整的“冲突发现器”。

更完整的系统口径应该是：

1. 先把 evidence 映射成结构化 claim  
   例如：`(entity, slot, value)`

2. 再看同一个实体、同一个槽位、同一个时间范围下，不同来源给出的值是否冲突

3. 数值型冲突可以设置容忍度，小范围误差不算真正冲突

所以更完整的表达是：

> `consistency` 不是简单看两篇文档有没有不同说法，而是先把 evidence 映射成实体-槽位-取值，再判断同一语义位点上的结论是否冲突。当前 Validator 中是消费上游的冲突结果并量化成 `conflict_ratio`，更完整的冲突发现会放在 evidence mapping 或 claim extraction 阶段完成。

### 14.3 槽位 `slot` 是谁生成的

最稳的统一说法是：

> 槽位优先由 Orchestrator 在 Plan 中显式定义；如果 Plan 没给，Validator 再用规则做 fallback 推断。

也就是说：

- **优先路径**：Orchestrator 在生成 Plan 时，写出 `required_slots`
- **后备路径**：如果上游没写，Validator 再根据问题文本规则推断

例如问题：

```text
比较 BERT 和 RoBERTa 的预训练差异，并解释为什么去掉 NSP
```

理想的 Plan 应该显式写出：

```json
{
  "required_slots": ["entity", "difference", "reason", "experiment_support"]
}
```

如果没有显式给，Validator 才根据：

- “比较 / 差异” -> `comparison` / `difference`
- “为什么” -> `reason`
- 抽到实体 -> `entity`

做规则兜底。

一句话记忆：

> `slot` 最好是 Plan 先定义，Validator 再兜底，不应该完全靠 Validate 阶段临时猜。

**15. `entity` 这个槽位到底是什么意思**
这一部分最容易混。你要严格区分：

- `entity` 作为一个**槽位类别**
- 具体的实体值作为**槽位取值**

### 15.1 `entity` 是槽位类别，不是具体值

当 Plan 写：

```json
"required_slots": ["entity", "difference", "reason"]
```

这里的意思不是“具体实体还不知道”，而是：

> 这个问题的答案必须明确围绕某些目标对象展开。

也就是说：

- `entity` 是一个槽位类型
- 它表示“必须回答在说谁”

### 15.2 具体 `entity` 值通常在 Plan 阶段就知道

比如问题：

```text
比较 BERT 和 RoBERTa 的预训练差异
```

那具体实体值其实一开始就有：

- `BERT`
- `RoBERTa`

所以更完整的 Plan 不应该只有：

```json
"required_slots": ["entity", "difference", "reason"]
```

还应该最好有：

```json
{
  "required_slots": ["entity", "difference", "reason"],
  "slot_values": {
    "entity": ["BERT", "RoBERTa"]
  }
}
```

换句话说：

- `required_slots` 说的是“要覆盖哪些维度”
- `slot_values` 说的是“这些维度里具体是什么”

### 15.3 如果当前问句里没有显式 entity 怎么办

比如用户说：

```text
它为什么去掉 NSP？
```

这时实体值不是在 Validate 阶段才“凭空知道”，而是应该在进入 Plan 前就通过上下文补出来。

这就涉及到 **pre-plan memory recall**。

---

**16. Orchestrator 做 Plan 前，要不要先看 Memory**
更合理的设计是：**要，而且要做轻量级 recall**。

原因很简单：

- 如果用户当前问题里用了“它”“这个模型”“前一个方法”这种代词
- Orchestrator 如果在做 Plan 前完全不看 memory
- 那它连当前问题到底围绕谁都不稳定

所以更稳的设计是把 Memory 分成两个使用时机：

### 16.1 Plan 前的轻量 Memory Recall

服务对象：Orchestrator  
目标：帮助问题理解和实体还原

主要使用：

- 短期会话记忆
- 实体记忆
- 少量高相关历史上下文

它主要解决：

- 代词消解
- 话题承接
- entity 确认

### 16.2 Plan 后的任务级 Memory Recall

服务对象：Retrieval  
目标：做语义缓存复用和检索增强

主要使用：

- 语义缓存
- 历史 evidence 摘要
- 过往检索结果

它主要解决：

- 减少重复检索
- query rewrite 补线索
- 降低 API 成本

所以一个很好的统一口径是：

> Memory 在系统里不是只在回答后写回，实际上有两个关键使用时机。第一个是 Plan 前的轻量 recall，主要给 Orchestrator 做问题理解和实体还原；第二个是 Plan 后的任务级 recall，主要给 Retrieval 侧做语义缓存复用和检索增强。

**17. `entity` 覆盖是怎么判断的**

当前轻量规则版里，判断方式比较直接：

1. 从问题里抽出实体
2. 看 evidence 里有没有这些实体的显式 mention

本质上就是：

```python
any(entity in evidence_text for entity in entities)
```

所以当前版的 `entity` coverage，本质是：

- entity extraction
- mention matching

但更完整的系统口径应该是：

> 轻量版里 `entity` 覆盖主要通过问题实体抽取和 evidence 中的显式 mention 匹配完成；更完整的系统里，这一步会建立在实体归一化和指代消解之后。也就是说，不只是看 evidence 里有没有字面出现 `BERT`，还要看别名、全称、缩写，以及多轮对话里的代词是否被统一到了同一个实体节点上。

例如：

- `BERT`
- `Bidirectional Encoder Representations from Transformers`
- “它”

在完整系统里都应该能最终映射到同一个 canonical entity。

**18. 这一部分你可以直接背的综合回答**

> 调 Validator 权重时，我会把评估分成两部分：第一部分是答案级指标，包括 Completion Rate、Key-Point Coverage、LLM-as-Judge 和人工抽样，这些决定最终答案质量；第二部分是过程级指标，包括平均检索步数、replan 频率、低分硬答比例、高分误答样本数等，这些反映这套权重会不会让系统过于保守或过于激进。  
> 至于 slots，本质上优先由 Orchestrator 在 Plan 里给出 `required_slots`，如果上游没写，Validator 再根据问题关键词和实体做 fallback 推断。`entity` 这里要区分 slot type 和 slot value：`entity` 在 Plan 里首先是一个槽位类别，表示这个问题必须明确回答“在说谁”；具体实体值通常在 Plan 阶段就通过问题解析抽出来，比如 `BERT`、`RoBERTa`。如果当前问句里没有显式实体，比如用户说“它为什么去掉 NSP”，那系统会先在 Orchestrator 生成 Plan 前做一次轻量 memory recall，用短期会话记忆和 entity memory 把“它”还原成 `RoBERTa`。Validator 判断 `entity` 是否覆盖时，轻量版主要看 evidence 里有没有显式 mention，更完整的版本则会结合实体别名归一化和指代消解。
