**第五类：强化学习总框架类问题（重写版）**

这一类不能只讲“为什么要做 RL”，还必须讲清楚：

- 这个任务为什么能建模成 RL
- `SFT` 具体怎么做
- `GRPO` 具体怎么跑
- 数据长什么样、怎么收集
- 训练时会遇到什么真实问题
- 这些问题和业务场景怎么对应

如果这一类只停留在“我用了 SFT + GRPO 优化 Orchestrator”，面试官基本一定会追问穿。

---

## 一、这一类问题到底在考什么

面试官在这一类里主要看 7 件事：

1. 你有没有把系统真正抽象成“序贯决策问题”
2. 你知不知道训练对象是谁，为什么是它
3. 你能不能讲清 `SFT` 和 `GRPO` 各自解决什么问题
4. 你会不会讲训练数据长什么样
5. 你知不知道 rollout、reward、group、advantage 这些基本概念
6. 你是否考虑过训练中的真实问题，比如策略坍塌、奖励稀疏、格式漂移
7. 你能不能把 RL 和业务收益挂钩，而不是只讲算法名词

---

## 二、你先要有的基础知识框架

这一类面试前，你脑子里必须有下面几个基础概念。

### 1. MDP
你不用背教科书，但要能讲成项目语言：

- `S`：当前状态  
  当前问题、当前 plan、已有 evidence、`missing_slots`、`sufficiency_score`、历史动作、memory recall 等
- `A`：动作  
  继续检索、继续补检索、升级全文、进入 synthesis、触发 replan、必要时代码执行
- `R`：奖励  
  不是只看最终答案，还看充分性、信息增益、效率
- `P`：状态转移  
  由检索结果、Validator 输出、StateMachine 一起推动
- `Episode End`：轨迹终止  
  回答完成、达到最大步数、或者进入失败终止条件

### 2. Policy
这个项目里的 policy 不是“写答案的风格”，而是：

> 在当前状态下，系统下一步选什么动作

### 3. Trajectory
一条轨迹就是一次完整的问答过程，例如：

- 先摘要检索
- 再验证
- 再读全文
- 再验证
- 再进入 synthesis

### 4. Advantage
你不用讲太数学，但要知道它的直觉：

> 这个动作 / 这条轨迹，相比同组其他轨迹到底好多少

### 5. 为什么是高层动作，不是底层 API
这一点很关键：

- RL 不优化“调用哪个 HTTP 参数”
- RL 优化的是“继续搜 / 读全文 / replan / synthesize”这种高层动作

因为如果动作空间太细，训练会很难，也不利于解释。

---

## 三、为什么这个任务适合 RL，不只是适合 Prompt

这类问题你不能只说“因为它是多步任务”。  
要讲得更像真实决策问题。

科研问答里，系统每一步都面临一个高层选择：

- 当前证据够了吗
- 不够的话，是继续摘要检索还是读全文
- 当前方向还对不对
- 现在回答会不会太早
- 需不需要 replan

这些选择不是一次性决定的，而是会随着状态变化不断更新。  
所以这不是静态分类，而是连续决策。

而且这些动作之间有长期依赖：

- 现在多搜一步，也许会多花一点成本，但可能避免后面一次错误回答
- 现在过早回答，也许当前省了一步，但长期看会降低完成率
- 现在不 replan，也许短期省事，但可能导致后面一直低增益绕圈

所以这个问题天然带有“长期收益”和“状态依赖”，这正是 RL 的适用场景。

一句话版：

> 这个项目适合 RL，不是因为它用了 Agent，而是因为它的核心问题是“当前状态下下一步怎么选”，而不是“单次生成一段文本”。

---

## 四、为什么训练对象是 Orchestrator，而不是 Synthesis

这一题你一定要答具体。

### 核心原因
当前系统最大的瓶颈不是“不会把答案写顺”，而是：

- 什么时候继续搜
- 什么时候停
- 什么时候读全文
- 什么时候 replan
- 什么时候允许进入 synthesis

这些都属于高层决策问题，所以训练对象应该是 `Orchestrator`。

### 为什么不是 Synthesis
因为 `Synthesis` 更偏条件生成：

- 输入已经通过验证的证据
- 输出组织好的最终回答

它当然重要，但它的前提是“证据已经够了”。  
而当前项目最容易出错的地方，不是在表达层，而是在证据和动作层。

### 更稳的说法
你可以直接背：

> 我这里 RL 优化的不是答案表面质量，而是 Orchestrator 的高层策略层。因为系统当前最关键的问题是“什么时候检索、什么时候补证据、什么时候停止”，不是“最后一句话怎么润色”。

## 五、SFT 具体是怎么做的

这一部分你前面说得对，不能只讲“先 SFT 再 GRPO”，必须讲怎么做。

### 1. SFT 的目的
SFT 在这个项目里主要解决 3 件事：

1. 输出格式稳定  
让 Orchestrator 能稳定输出结构化 Plan / 结构化动作信息，而不是一会儿自然语言、一会儿半结构化 JSON

2. 基本行为对齐  
比如复杂问题先检索，不是直接回答；有比较关系就要包含 comparison / difference 槽位；有原因问题就要考虑 `reason`

3. 冷启动  
让模型先学会“像这个系统一样工作”，再进入 RL 阶段做策略优化

### 2. SFT 样本长什么样
最简单的统一口径，是按“指令 + 输入状态 + 输出结构”来讲。

你可以用这种格式：

```json
{
  "instruction": "根据当前问题和上下文，输出结构化 Plan",
  "input": {
    "question": "比较 BERT 和 RoBERTa 的预训练差异，并解释为什么去掉 NSP",
    "memory_summary": "上一轮已经讨论过 BERT 预训练任务",
    "context_constraints": [
      "答案必须有证据支撑",
      "必要时允许全文展开"
    ]
  },
  "output": {
    "goal": "回答预训练差异、原因及实验支持",
    "required_slots": ["entity", "difference", "reason", "experiment_support"],
    "steps": [
      "RETRIEVE_SUMMARY",
      "VALIDATE",
      "RETRIEVE_FULL_TEXT_IF_NEEDED",
      "SYNTHESIS"
    ]
  }
}
```

如果训练的是“下一步动作决策”而不是完整 plan，也可以是：

```json
{
  "instruction": "根据当前状态决定下一步动作",
  "input": {
    "question": "RoBERTa 为什么去掉 NSP？",
    "sufficiency_score": 0.66,
    "relevance": 0.88,
    "missing_slots": ["reason", "experiment_support"],
    "support_strength": 0.43
  },
  "output": {
    "next_action": "RETRIEVE_FULL_TEXT",
    "reason": "高相关但关键槽位缺失，且支撑力度不足"
  }
}
```

### 3. SFT 数据怎么收集
这一步你要讲得像真实做过，建议这样组织：

SFT 数据主要来自三类来源：

1. **规则系统 / 初始系统跑出来的高质量轨迹**
- 先用已有规则、人工设定流程、或 baseline agent 跑一批 query
- 保留结果比较好的轨迹
- 这些轨迹天然贴近你的系统流程

2. **人工修订或筛选后的结构化样本**
- 对一批复杂 query 手工或半自动修订 Plan
- 保证 `required_slots`、分支逻辑、动作顺序比较稳

3. **问题改写与模板扩增**
- 同一类科研问题做表达改写
- 保留问题类型不变，增加表达多样性
- 防止模型只记住某一种问法

### 3.1 数据规模怎么讲更像真的做过

这一部分建议你直接讲具体数字，不要只说“收集了一些数据”。

我建议你统一讲成：

- RL 总数据量：`2500` 条
- 训练集：`2000`
- 验证集：`300`
- 测试集：`200`

来源构成可以讲成：

- `60%`：LLM 生成的科研检索问题
- `25%`：对已有问题做 query 改写和表达扩增
- `15%`：公开学术问答数据集适配后的样本

这一套数字和口径最大的好处是：

- 既具体
- 又和后面的数据类讲法一致
- 面试官继续追问时也能接得上

### 3.2 SFT 样本到底长什么样

SFT 样本你不要只给一个抽象 JSON，最好至少准备两种 sample。

#### Sample A：训练完整 Plan 输出

```json
{
  "instruction": "根据当前问题、上下文和约束，输出结构化 Plan",
  "input": {
    "question": "比较 BERT 和 RoBERTa 的预训练差异，并解释为什么 RoBERTa 去掉 NSP",
    "memory_summary": "上一轮已经讨论过 BERT 的 MLM 与 NSP 任务",
    "constraints": [
      "答案必须基于检索证据",
      "必要时允许升级到全文",
      "证据不足不能直接进入 synthesis"
    ]
  },
  "output": {
    "goal": "回答预训练差异、原因及实验支持",
    "required_slots": ["entity", "difference", "reason", "experiment_support"],
    "entities": ["BERT", "RoBERTa"],
    "steps": [
      "RETRIEVE_SUMMARY",
      "VALIDATE",
      "RETRIEVE_FULL_TEXT_IF_NEEDED",
      "VALIDATE",
      "SYNTHESIS"
    ],
    "thresholds": {
      "sufficiency_threshold": 0.75,
      "replan_threshold": 0.60
    }
  }
}
```

#### Sample B：训练状态到下一步动作

```json
{
  "instruction": "根据当前状态选择下一步动作",
  "input": {
    "question": "RoBERTa 为什么去掉 NSP？有没有实验支持？",
    "sufficiency_score": 0.66,
    "relevance": 0.88,
    "coverage": 0.50,
    "support_strength": 0.43,
    "missing_slots": ["reason", "experiment_support"],
    "info_gain": 0.58,
    "current_state": "VALIDATE"
  },
  "output": {
    "next_action": "RETRIEVE_FULL_TEXT",
    "reason": "高相关但关键槽位缺失，且摘要级证据支撑不足"
  }
}
```

这两个 sample 分别覆盖：

- 完整规划能力
- 单步决策能力

这样讲比只说“我做了 SFT 对齐结构化输出”强很多。

### 3.3 SFT 数据是怎么一步一步收集出来的

这一部分建议你讲得更流程化。

#### 路径一：规则系统 / baseline policy 自动生成

流程可以讲成：

1. 先准备一批科研问题  
   问题类型要覆盖：
   - 定义类
   - 比较类
   - 原因分析类
   - 实验支持类
   - 趋势统计类

2. 用 baseline policy 跑这些 query  
   baseline policy 可以是：
   - 人工写的规则 Orchestrator
   - 老版本系统
   - prompt-only 的初始 Orchestrator

3. 自动记录运行过程  
   记录：
   - question
   - 初始 context
   - plan
   - 每一步 state
   - 动作选择
   - validate 输出
   - 最终结果

4. 过滤掉明显坏样本  
   比如：
   - plan 结构不合法
   - 缺少关键步骤
   - 提前回答
   - evidence 明显不足却进入 synthesis

5. 保留高质量轨迹，转成 SFT 样本

#### 路径二：人工修订高价值样本

这个路径非常适合你讲“复杂问题样本是怎么做的”。

流程可以讲成：

1. 从失败案例和复杂 query 中挑样本  
   例如：
   - 方法差异 + 原因解释
   - benchmark 对比
   - 多轮追问 + 代词消解

2. 人工重写标准 Plan  
   重点修：
   - `required_slots`
   - 分支条件
   - 是否需要全文
   - 什么时候 replan

3. 如果需要，再人工标记“理想下一步动作”

4. 这些样本优先进入 SFT，因为它们最能教会模型复杂行为

#### 路径三：表达改写与模板扩增

这一路不是为了增加新知识，而是为了增强表达多样性。

例如原问题：

```text
比较 BERT 和 RoBERTa 的预训练差异，并解释为什么 RoBERTa 去掉 NSP。
```

改写成：

```text
从预训练目标和训练策略两个角度，对比 BERT 与 RoBERTa，并说明移除 NSP 的动机。
```

或者：

```text
请分析 RoBERTa 相比 BERT 在 pretraining 设计上的改动，尤其说明 NSP 被删除的原因和依据。
```

这样能防止模型只记住某个模板句式。

### 3.4 SFT 数据收集时的过滤规则

这里最好也讲细一点，看起来会更真实。

可以讲成：

- 过滤掉非科研问题
- 过滤掉问题过短、意图不清的样本
- 过滤掉输出 JSON 不合法或字段缺失的样本
- 过滤掉不包含关键槽位的 Plan
- 过滤掉“复杂问题却直接回答”的轨迹
- 对同质化问题做去重或表达聚类

一句话版：

> SFT 数据不是只要能跑出来就拿去训，而是要经过“结构合法性 + 行为合理性 + 任务多样性”三层过滤。

### 4. SFT 阶段实际会遇到的问题
这部分很重要，很多人不会讲。

#### 问题一：输出格式漂移
模型会：
- 漏字段
- JSON 不闭合
- `required_slots` 不稳定
- 把本该结构化输出的内容写成自然语言段落

解决：
- 加更强 schema 约束
- 先训练格式再训练内容
- 对训练样本做严格校验

#### 问题二：行为过于激进
模型学会了一种“快回答”的坏习惯：
- 问题一复杂，它还是想先答
- 没有明确体现“先检索、再验证”

解决：
- 在 SFT 数据里加入更多“证据不足不回答”的正例
- 明确教它输出包含检索和验证步骤的 plan

#### 问题三：问题类型覆盖不均
如果训练数据里定义类太多、复杂对比类太少，模型会在复杂任务上表现不稳。

解决：
- 调整任务分布
- 增加比较类、原因分析类、实验支持类样本

### 5. SFT 阶段你怎么判断做得差不多了
你可以讲几个很像真的指标：

- 结构化输出字段完整率
- JSON / schema 合法率
- plan 中关键槽位召回率
- 人工抽样看行为是否符合预期
- 在验证集上看“复杂问题先检索”的比例是否稳定

如果面试官继续追问“有没有更具体一点的标准”，你可以讲成下面这种工程口径：

- 结构化字段完整率稳定在 `95%+`
- JSON / schema 合法率稳定在 `95%+`
- `required_slots` 召回率稳定在 `90%` 左右
- 复杂问题样本里，“先检索再回答”的比例稳定在 `85%+`
- 人工抽样里，明显提前回答的 bad case 已经明显下降

你不用说这些数字是绝对标准，但可以说：

> 我不会等到 loss 完全收敛才停，而是看结构合法性、关键槽位召回和复杂问题行为是否已经稳定。如果这些行为指标已经进入平台期，说明 SFT 阶段基本完成任务，后面该进入 RL 做策略优化。

一句话总结：

> SFT 阶段的目标不是让模型最优，而是让它稳定、可控、符合系统格式和基本行为习惯。

## 六、GRPO 具体怎么做

这部分不能只说“用 GRPO 优化策略”，要讲流程。

### 1. GRPO 在这个项目里优化什么
GRPO 优化的是：

- 同一个 query 下，不同策略轨迹的相对优劣
- 让“更会补证据、更少误答、更少无效搜索”的轨迹概率更高

### 2. 一次训练迭代怎么跑
最稳的讲法是 5 步：

#### 第一步：给定一个 query
例如：
“比较 BERT 和 RoBERTa 的预训练差异，并解释为什么去掉 NSP”

#### 第二步：当前 policy 采样多条轨迹
比如采样 4 条：

- 轨迹 A：摘要检索 -> 验证 -> 直接回答
- 轨迹 B：摘要检索 -> 验证 -> 读全文 -> 验证 -> 回答
- 轨迹 C：摘要检索 -> 验证 -> 重复检索 -> 回答
- 轨迹 D：摘要检索 -> 验证 -> replan -> 再检索 -> 回答

#### 第三步：让环境执行这些轨迹
这里的环境不是游戏，而是你的系统环境：
- Retrieval
- Validator
- StateMachine
- Memory
- 工具调用结果

也就是每条轨迹都会真正走一遍系统流程，拿到：
- `sufficiency_score`
- `info_gain`
- 检索步数
- 最终答案质量
- 是否低分硬答

#### 第四步：计算 reward
你这里先不用展开太深，但要说明：
- 不是只看最终答案
- 还看 `sufficiency`、`info_gain`、`efficiency`
- 第六类再细讲 reward

#### 第五步：做组内相对比较并更新
GRPO 的核心是：
- 同一个 query 下的多条轨迹比较优劣
- 奖励更好的轨迹被强化
- 奖励差的轨迹被抑制

所以你可以概括成：

> GRPO 不是单独看一条轨迹绝对好不好，而是同组比较谁更优，然后调整策略，让模型更倾向于选出那类高质量轨迹。

## 七、GRPO 训练数据长什么样

你前面说得对，这部分虽然第八类会展开，但第五类也必须先讲一点。

### 1. RL 数据的最小单位不是“单句答案”，而是“轨迹”
比如：

```json
{
  "query": "比较 BERT 和 RoBERTa 的预训练差异，并解释为什么去掉 NSP",
  "initial_state": {
    "required_slots": ["entity", "difference", "reason", "experiment_support"]
  },
  "trajectory": [
    {
      "state": "RETRIEVE_SUMMARY",
      "action": "RETRIEVE_SUMMARY",
      "result": {
        "evidence_snippets": ["...", "..."]
      }
    },
    {
      "state": "VALIDATE",
      "action": "RETRIEVE_FULL_TEXT",
      "result": {
        "sufficiency_score": 0.66,
        "missing_slots": ["reason", "experiment_support"]
      }
    },
    {
      "state": "RETRIEVE_FULL_TEXT",
      "action": "SYNTHESIS",
      "result": {
        "sufficiency_score": 0.82
      }
    }
  ],
  "final_reward": 0.73
}
```

### 2. 这些轨迹怎么收集
你可以讲三种来源：

1. 现有系统 rollout 自动记录  
这最像 RL 场景，系统自己跑 query，把状态、动作、结果、reward 记下来

2. 规则系统 / baseline policy 生成初始轨迹  
用于冷启动和早期轨迹积累

3. 人工筛选高质量轨迹  
用于减少明显错误路径污染训练

### 2.1 轨迹到底记录哪些字段

你不能只说“记录轨迹”，最好说清楚一条轨迹里到底会记什么。

一个更完整的轨迹记录可以长这样：

```json
{
  "session_id": "rl_train_000138",
  "query_type": "comparison_reason_experiment",
  "query": "比较 BERT 和 RoBERTa 的预训练差异，并解释为什么 RoBERTa 去掉 NSP",
  "initial_plan": {
    "required_slots": ["entity", "difference", "reason", "experiment_support"],
    "entities": ["BERT", "RoBERTa"]
  },
  "trajectory": [
    {
      "step": 1,
      "state": {
        "stage": "RETRIEVE_SUMMARY",
        "sufficiency_score": 0.0,
        "missing_slots": ["entity", "difference", "reason", "experiment_support"]
      },
      "action": "RETRIEVE_SUMMARY",
      "result": {
        "retrieved_doc_ids": ["doc_1", "doc_2", "doc_3"],
        "evidence_snippets": [
          "RoBERTa removes the NSP objective ...",
          "BERT uses MLM and NSP ..."
        ]
      }
    },
    {
      "step": 2,
      "state": {
        "stage": "VALIDATE",
        "sufficiency_score": 0.66,
        "missing_slots": ["reason", "experiment_support"],
        "relevance": 0.88,
        "support_strength": 0.43
      },
      "action": "RETRIEVE_FULL_TEXT",
      "result": {
        "selected_doc_ids": ["doc_2"],
        "full_text_sections": ["method", "ablation"]
      }
    },
    {
      "step": 3,
      "state": {
        "stage": "VALIDATE",
        "sufficiency_score": 0.82,
        "missing_slots": []
      },
      "action": "SYNTHESIS",
      "result": {
        "final_answer": "..."
      }
    }
  ],
  "metrics": {
    "avg_info_gain": 0.54,
    "num_replans": 0,
    "num_search_steps": 2,
    "answer_quality": 0.81
  },
  "final_reward": 0.73
}
```

这类 sample 很重要，因为它能直接回答面试官：

- 轨迹不是一句话
- 轨迹里有状态、动作、结果、过程指标、最终 reward

### 2.2 轨迹路径 sample 也要能讲

你可以准备几种典型轨迹路径，不然 GRPO 很容易讲空。

#### 好路径 sample

```text
RETRIEVE_SUMMARY -> VALIDATE -> RETRIEVE_FULL_TEXT -> VALIDATE -> SYNTHESIS
```

适用场景：
- 高相关
- 摘要不够深
- 需要实验支持或原因细节

#### 低效路径 sample

```text
RETRIEVE_SUMMARY -> VALIDATE -> RETRIEVE_MORE -> VALIDATE -> RETRIEVE_MORE -> VALIDATE -> SYNTHESIS
```

问题：
- 一直在补摘要
- 但没有进入全文
- 容易导致低信息增益绕圈

#### 错误早答路径 sample

```text
RETRIEVE_SUMMARY -> VALIDATE -> SYNTHESIS
```

问题：
- `sufficiency_score` 还在灰区甚至偏低
- 但系统提前回答

#### 过度重规划路径 sample

```text
RETRIEVE_SUMMARY -> VALIDATE -> REPLAN -> RETRIEVE_SUMMARY -> VALIDATE -> REPLAN
```

问题：
- 说明策略过于激进
- 动不动推翻原路径

这几条路径非常适合你在面试里讲 GRPO 为什么有价值。

### 2.3 轨迹收集不是一锅端，而是分阶段积累

这一段建议你也讲出来：

#### 阶段一：先收 baseline 轨迹
- 用规则系统 / prompt policy 跑出第一批路径
- 目的：让模型先看到“什么是合理流程”

#### 阶段二：开始收 rollout 轨迹
- 用已做过 SFT 的 Orchestrator 跑 query
- 记录真实策略行为
- 目的：收集更接近当前 policy 的样本

#### 阶段三：人工筛选和回流
- 把高分误答、低分硬答、重复搜索、无效 replan 样本单独挑出来
- 一部分进入奖励调试
- 一部分进入后续 SFT / RL 数据增强

一句话总结：

> 轨迹不是一次性收齐，而是“baseline 冷启动 -> rollout 扩充 -> bad case 回流”逐步积累出来的。

### 3. 训练时真的每次都调真实搜索 API 吗
这是很容易被问到的实际问题。

更稳的回答是：

> 训练阶段如果每次都实时调用完整外部搜索 API，成本和波动会非常大，所以更实际的做法通常是缓存环境反馈、复用已记录轨迹，或者把一部分检索结果离线化。真正在线全链路 rollout 可以用于小规模高价值样本或阶段性评估，而不是把所有训练完全绑定在线 API。

这句非常像真实做过。

## 八、实际业务上手会遇到什么问题

这一类你必须讲几个“真实坑”，不然面试官会觉得你只懂概念。

### 1. 冷启动时模型容易“太爱回答”
即使问题很复杂，它还是倾向于：
- 先给一个貌似合理的答案
- 不愿意多走检索和验证流程

业务后果：
- Completion 看起来可能不低
- 但 `Key-Point Coverage` 和人工准确性很差

解决：
- SFT 里增加“证据不足先检索”的样本
- Reward 里加强 `sufficiency`
- 对低分硬答加惩罚

---

### 2. 复杂 query 上 Plan 不稳定
比如比较类问题，有时会漏掉“原因”或“实验支持”槽位。

业务后果：
- 后面即使检索做得不错，方向还是错的
- Validator 会不断发现缺槽位，但问题源头其实在 Plan

解决：
- SFT 阶段强化 `required_slots` 学习
- 对复杂 query 做更多高质量 plan 样本
- 用人工抽样看 Plan 是否稳定

---

### 3. 策略容易学成“重复搜索”
模型会发现：
- 多搜几次有时能提高一点 `info_gain`
- 但实际上在绕圈

业务后果：
- 检索步数上升
- API 成本爆炸
- 用户时延变差

解决：
- 第六类 reward 里加重复搜索惩罚
- 监控低信息增益轮次
- 必要时触发 replan 或 early stop

---

### 4. 组内轨迹差异太小，GRPO 学不到东西
如果同一个 query 下采样出的轨迹都差不多，reward 排序就没有信号。

业务后果：
- 训练很慢
- loss 看着正常，但策略没明显提升

解决：
- 增加采样温度
- 调整动作空间
- 改善 reward 区分度
- 选更有策略分歧的 query 进入训练

---

### 5. 训练环境和真实线上分布不一致
这也是非常现实的问题。

比如：
- 训练集里大多是论文方法对比
- 线上来了很多多轮追问、实体省略、模糊查询

业务后果：
- 离线 reward 看着不错
- 线上仍然容易出错

解决：
- 回流线上 bad case
- 强化多轮 query 和代词场景
- 用 memory 相关场景补数据

---

## 九、你可以直接背的第五类核心回答

如果面试官问：
“你这个强化学习到底是怎么做的？”

你可以直接答：

> 我这里不是把 RL 用在最终答案生成上，而是用在 Orchestrator 的高层策略层。因为这个系统最核心的问题不是怎么把答案写顺，而是当前状态下下一步到底该做什么，比如继续检索、读全文、进入 synthesis 还是 replan。具体训练上，我先做 SFT，让模型学会稳定输出结构化 Plan 和基本行为模式，比如复杂问题先检索、Plan 里显式包含 required_slots 和条件分支。SFT 数据一部分来自规则系统和 baseline policy 跑出来的高质量轨迹，一部分来自人工修订和问题改写，样本既可以是完整 Plan，也可以是状态到下一步动作的映射。然后再做 GRPO，用同一个 query 采样多条策略轨迹，让系统环境真实执行这些轨迹，拿到 sufficiency、info_gain、效率和最终答案质量，再做组内相对比较，强化更优轨迹。这样优化的不是回答措辞，而是“什么时候搜、什么时候补证据、什么时候停”的决策质量。实际训练里我主要会遇到几个问题，比如冷启动时模型太爱提前回答、复杂 query 上 Plan 不稳定、策略绕圈重复搜索、组内轨迹差异太小等，所以前期 SFT 质量和 reward 设计都非常关键。

## 十、这一类你现在最该背熟的 15 句话

1. 这个项目适合 RL，不是因为它用了 Agent，而是因为它是一个典型的序贯决策问题。  
2. 当前系统最需要优化的不是答案文风，而是高层动作选择。  
3. 所以训练对象是 Orchestrator，而不是 Synthesis。  
4. RL 优化的是“什么时候搜、什么时候停、什么时候换路”。  
5. SFT 的作用是先把结构化输出和基本行为模式对齐。  
6. 没有 SFT 的冷启动，RL 很容易学崩。  
7. SFT 样本可以是完整 Plan，也可以是状态到下一步动作的结构化映射。  
8. SFT 数据主要来自高质量轨迹、人工修订和问题改写。  
9. RL 阶段的数据最小单位不是单句答案，而是一条轨迹。  
10. GRPO 的核心是同一个 query 下多轨迹相对比较。  
11. 环境执行会返回 sufficiency、info_gain、效率和最终答案质量。  
12. RL 训练不一定每次都实时打外部搜索 API，实际会结合缓存和离线环境。  
13. 实际训练中最常见的问题包括提前回答、Plan 不稳定、重复搜索和轨迹差异太小。  
14. 规则负责底线，SFT 负责行为对齐，GRPO 负责策略优化。  
15. 这套 RL 的价值不在“更会说”，而在“更会做决策”。
