# 基于 SFT + GRPO 的 Orchestrator 训练实践说明

## 1. 训练目标

这个项目训练的核心对象不是最终答案生成模块，而是 **Orchestrator 的高层策略层**。  
也就是说，我要优化的不是“最后一句话怎么写得更好”，而是：

- 当前问题属于什么类型
- 需要哪些 `required_slots`
- 什么时候先做摘要检索
- 什么时候需要读全文
- 什么时候继续补检索
- 什么时候该 `replan`
- 什么时候证据已经足够，可以进入 `synthesis`

所以整个训练链路的目标，是把 Orchestrator 从“会按格式输出 plan”进一步提升到“会做更优策略选择”。

---

## 2. 训练总流程

整个训练分成两个阶段：

```text
Base Model
  -> LoRA 挂载
  -> SFT 对齐
  -> GRPO 策略优化
  -> 得到新的 Orchestrator Policy Model
```

更细一点是：

```text
Qwen2.5-7B-Instruct
  -> PEFT/LoRA
  -> SFT 数据（plan / state->action）
  -> SFT 训练
  -> 得到结构稳定的 Orchestrator
  -> 构建 RL 环境（Retrieval + Validator + StateMachine + Memory + MCP Tools）
  -> GRPO 采样多轨迹
  -> 计算 reward
  -> 组内相对优化
  -> 得到策略更优的 Orchestrator
```

---

## 3. 训练框架

这套训练链路我统一按下面这套框架讲：

- `PyTorch`
  负责底层训练和反向传播

- `Transformers`
  负责加载基座模型和 tokenizer

- `PEFT`
  负责 LoRA 参数高效微调

- `TRL`
  负责 RL 阶段的 trainer 抽象，尤其是 `GRPOTrainer`

- `Accelerate`
  负责多卡和训练流程调度

一句话口径：

> 底层是 `PyTorch + Transformers`，LoRA 用 `PEFT`，强化学习训练器走 `TRL`，多卡调度一般配 `Accelerate`。

---

## 4. 基座模型和微调方式

### 4.1 Base Model
我这里统一用：

- `Qwen2.5-7B-Instruct`

选择 7B 而不是更小或更大的原因很明确：

- 比 3B 一类模型更稳，足够支撑结构化 plan 和多步状态理解
- 比 14B 更省资源，适合在真实可租的 AutoDL 资源上跑 SFT + GRPO
- 对我这个项目来说，瓶颈不只是模型参数量，还在 retrieval、validate 和 rollout，所以 7B 是一个性价比比较高的平衡点

---

### 4.2 微调方式
我不做全量微调，而是做 **LoRA 微调**。

原因是：

- 目标是调策略层，不是重训整个模型语言能力
- LoRA 成本低
- 显存压力更小
- 更不容易出现大范围灾难性遗忘
- 也更适合 AutoDL 这种真实租卡场景

---

### 4.3 LoRA 关键参数
我统一按下面这套说：

- `r = 16`
- `alpha = 32`
- `dropout = 0.05`
- `target_modules = ["q_proj", "v_proj"]`

这些参数怎么理解：

#### `r=16`
LoRA 的低秩维度，决定 adapter 容量。  
太小学不动复杂策略差异，太大训练成本和波动上升，`16` 是比较稳的折中。

#### `alpha=32`
LoRA 的缩放系数。  
配合 `r=16`，更新强度比较适中，不会太弱也不会太激进。

#### `dropout=0.05`
防止 adapter 过拟合。  
尤其你这个项目的数据规模不是特别大，保留一个轻量 dropout 更稳。

#### `q_proj / v_proj`
先挂在注意力层，是因为策略层任务更依赖模型“看什么状态、怎么聚焦信息”，先调这类位置通常性价比更高。

## 5. 上下文长度和输入组成

### 5.1 统一上下文长度
我这边统一按：

- `max_seq_len = 4096`

来训练。

原因不是 base model 不能更长，而是这个项目里输入包含：

- 用户问题
- memory summary
- 当前 plan
- evidence summary
- validator 输出
- 当前状态字段

这些拼起来已经不短。  
`4096` 是一个比较合理的平衡点：

- 能覆盖关键状态
- 不会把训练显存和吞吐压得太夸张

---

### 5.2 实际输入控制
虽然配置是 `4096`，但实际训练我不会每条都硬塞满。  
更自然的控制是：

- 实际输入尽量控制在 `3000 ~ 3500 tokens`
- 给输出预留 `500 ~ 1000 tokens`

这样做有两个好处：

- 训练更稳定
- 避免把所有资源都吃在极端长样本上

### 6.1 平台

- `AutoDL`

### 6.2 GPU 口径
我后面统一资源口径为：

- 前期联调 / 小样本 sanity check：`1 张 A100-PCIE-40GB`
- 正式训练：`2 张 A100-PCIE-40GB`

这套口径最稳。

原因是：

- 你这个项目是 `7B + LoRA + 4096`
- 不是 70B 全量微调
- 但也不是特别轻的短文本 SFT
- `2 张 A100-PCIE-40GB` 对正式 SFT 和可行的 GRPO 实验是合理的

注意一句很重要的话：

> `2 张 40G` 不等于 `1 张 80G`，因为单卡显存上限还是 40G；所以我会用多卡 + 显存优化手段来跑，而不是把它讲成特别宽裕的资源。

## 7. 混合精度、显存优化和训练稳定性

这部分你面试里一定会被追问，所以我单独写清楚。

---

### 7.1 `bf16 / fp16`
这是 **混合精度训练**。

作用：

- 降显存
- 提升吞吐
- 加快训练

我的默认口径是：

- 优先 `bf16`
- 环境不支持再退到 `fp16`

为什么更偏 `bf16`：

- 大模型训练里通常更稳
- 数值范围更友好
- 对策略训练也更安全一些

一句话版：

> 我不会默认用 `fp32` 跑这类 7B 训练，基本都会开混合精度，能用 `bf16` 我就优先用 `bf16`。

---

### 7.2 `gradient checkpointing`
这本质上是：

> 用时间换显存

正常训练会保存很多中间激活，反向传播时直接用。  
但长序列时这些激活特别吃显存。

开了 checkpointing 之后：

- 前向不保存所有激活
- 反向时需要时再重算一遍

结果就是：

- 显存明显下降
- 训练速度会慢一点

对你这个项目来说特别值，因为：

- `4096` 长序列
- 状态输入不短
- 激活值比 LoRA 参数更容易成为显存瓶颈

---

### 7.3 `gradient accumulation`
这个本质上是：

> 用多次小 batch 累梯度，模拟大 batch

例如：

- `micro batch = 1`
- `grad_accum = 8`

那等效 batch 大概就是：

- `1 × 8 × GPU数`

如果是 2 张卡，那等效 batch 大概是：

- `1 × 8 × 2 = 16`

这样做的目的：

- 单步显存压力小
- 训练仍然保持一个相对稳定的等效 batch

---

### 7.4 量化怎么讲
这里一定要区分：

#### `bf16/fp16`
这是训练时低精度计算，不等于真正的量化训练。

#### 真正的量化
通常指：
- `8bit`
- `4bit`
- `QLoRA`

在你这个项目里，**主训练口径不是 QLoRA**，而是：

- `LoRA + bf16 + gradient checkpointing + grad accumulation`

因为对策略优化来说，我更优先保证稳定性。  
如果资源特别紧，SFT 阶段可以考虑 `QLoRA`，但不是主版本口径。

## 8. 实际训练参数建议

下面这套参数你后面可以统一讲，足够像真做过。

---

### 8.1 SFT 阶段

#### 模型配置
- base model: `Qwen2.5-7B-Instruct`
- LoRA: `r=16, alpha=32, dropout=0.05`
- target modules: `q_proj`, `v_proj`

#### 训练参数
- `max_seq_len = 4096`
- `learning_rate = 2e-5`
- `num_epochs = 1~2`
- `micro_batch_per_gpu = 1`
- `gradient_accumulation_steps = 8`
- `global effective batch ≈ 16`（2 卡下）
- precision: `bf16`
- `gradient_checkpointing = True`

这套为什么合理：

- 4096 长上下文下，单卡 40G 不适合把 micro batch 开大
- `micro_batch=1` 更稳
- 再用 `grad_accum=8` 把等效 batch 补回来
- `2e-5` 对 LoRA 微调是一个保守稳定值

---

### 8.2 GRPO 阶段

GRPO 比 SFT 更重，因为多了：

- rollout
- 多轨迹采样
- reward 计算
- 环境交互

所以 GRPO 阶段更偏向：

- `micro_batch_per_gpu = 1`
- `gradient_accumulation_steps = 8 或 16`
- rollout group size：`4`
- precision: `bf16`
- checkpointing: 开
- 同样维持 `4096` 上下文，但必要时会压缩 state 里的 evidence summary

一句话：

> GRPO 阶段不会盲目追大 group、大 batch，而是先保证每条轨迹和 reward 计算稳定，再慢慢放大。

## 9. SFT 数据是什么样

SFT 不是训普通 QA。  
它训的是 **结构化策略行为**。

我这里主要有两类样本：

### 9.1 `question -> plan`
输入：
- question
- memory summary
- constraints

输出：
- `question_type`
- `required_slots`
- `entities`
- `steps`
- `branch conditions`

### 9.2 `state -> next_action`
输入：
- 当前状态
- `sufficiency_score`
- `missing_slots`
- `relevance`
- `support_strength`
- `info_gain`

输出：
- `next_action`
- 可选：`reason`

这样模型学到的是：
- 先怎么规划
- 当前状态下应该做什么

---

## 10. SFT 训练流程

### 第一步：准备样本
来源包括：
- baseline rollout 的高质量轨迹
- 人工修订的复杂 query
- query 改写样本
- 公开科研问答数据适配后的样本

### 第二步：做样本校验
至少检查：
- instruction 是否为空
- output 是否为空
- schema 是否合法
- `required_slots` 是否完整

### 第三步：训练
本质上仍然是监督学习，目标是 next-token prediction，只不过输出目标是结构化 plan 或 action。

### 第四步：验证
我不会只看 loss，还会看：

- JSON / schema 合法率
- `required_slots` 是否稳定
- 复杂 query 是否能稳定先检索再验证
- plan 输出是否少漏 `reason` / `experiment_support`

---

## 11. GRPO 训练流程

### 第一步：拿一个 query
例如一个复杂科研问题。

### 第二步：采样多条轨迹
例如：
- 轨迹 A：摘要检索后过早回答
- 轨迹 B：摘要检索 -> validate -> 全文 -> answer
- 轨迹 C：摘要检索 -> 补检索 -> answer
- 轨迹 D：replan 后继续检索

### 第三步：环境执行
让系统环境真实跑：
- Retrieval
- Validator
- StateMachine
- Memory
- MCP Tools

### 第四步：算 reward
reward 不只看最终答案，而是结合：

- `R_quality`
- `R_sufficiency`
- `R_info_gain`
- `R_efficiency`
- `R_penalty`

### 第五步：GRPO 组内优化
对同一个 query 的多轨迹做相对比较，  
强化高质量路径，抑制坏路径。

---

## 12. Reward 两阶段口径

我统一讲成下面这套：

### Phase 1：过程强化
权重：
- `quality = 0.25`
- `sufficiency = 0.35`
- `info_gain = 0.25`
- `efficiency = 0.15`

目标：
- 先学会“证据够了再答”
- 避免重复搜索
- 不要过早回答

### Phase 2：质量平衡
权重：
- `quality = 0.40`
- `sufficiency = 0.25`
- `info_gain = 0.20`
- `efficiency = 0.15`

目标：
- 过程稳定后
- 再把最终回答质量拉起来

### 切换方式
最稳口径：

- 训练进度到 `60%`
- 或 `sufficiency_avg >= 0.75` 且 `info_gain_avg >= 0.5`

进入第二阶段

## 13. 训练过程中最容易遇到的问题

### 13.1 SFT 阶段
- 结构化输出漂移
- `required_slots` 漏写
- plan 过于模板化
- 复杂 query 上问题类型识别不稳定

### 13.2 GRPO 阶段
- 提前回答
- 重复搜索
- 过度 replan
- 动作分布塌缩
- 轨迹差异太小，学不到东西

---

## 14. 什么时候停训

这个不能只看 loss。

我主要看三层：

### 答案级指标
- Completion Rate
- Key-Point Coverage
- LLM-as-Judge
- 人工抽样

### 过程级指标
- 平均检索步数
- replan 频率
- 低分硬答比例
- 高分误答样本数

### 收益成本比
- 指标是否进入平台期
- 继续训练是否还值得花 GPU 钱

一句话：

> 停训不是看某一条曲线，而是看业务指标、过程指标和成本收益是否都进入平台期。

## 15. 训练完得到的新模型怎么用

训练完不是得到一个“完全新系统”，而是得到：

- `base model`
- `LoRA adapter`

部署时的做法是：

```text
加载 Qwen2.5-7B-Instruct
+ 挂载训练好的 LoRA adapter
= 新的 Orchestrator Policy Model
```

然后把这个模型接回原系统，主要负责：

- plan 生成
- 问题类型识别
- `required_slots`
- action selection
- replan decision

而不是替代：
- Retrieval
- Validator
- StateMachine
- MCP Tool Layer

## 16. 一段面试里可以直接背的完整训练回答

> 我这个项目的训练链路是 `PyTorch + Transformers + PEFT/LoRA + TRL`。基座模型选的是 `Qwen2.5-7B-Instruct`，因为我主要优化的是 Orchestrator 的高层策略，不需要全量重训整个模型，所以我用了 LoRA 做参数高效微调，参数配置是 `r=16, alpha=32, dropout=0.05`，主要挂在 `q_proj` 和 `v_proj` 上。训练上下文统一按 `4096 tokens` 配，因为输入里除了 question，还会带 memory summary、plan、evidence summary 和 validator signals。  
> 资源上我是在 AutoDL 上租 `A100-PCIE-40GB`，前期用单卡做环境联调和小样本 sanity check，正式训练统一用 `2 张 A100-PCIE-40GB`。为了在 40G 显存下稳定跑 `7B + LoRA + 4k context`，我会默认开 `bf16`、gradient checkpointing，把 micro batch 压到 `1`，再用 gradient accumulation 把等效 batch 补到 `16` 左右。  
> 训练分两阶段。第一阶段是 SFT，主要让 Orchestrator 学会稳定输出结构化 plan 和 state->action，不是去背最终答案；第二阶段是 GRPO，对同一个 query 采样多条轨迹，让 Retrieval、Validator、StateMachine 和工具层真实执行，再根据 quality、sufficiency、info_gain、efficiency 和 penalty 算 reward，做组内相对优化。reward 是两阶段设计，前期更强调 `sufficiency` 和 `info_gain`，后期再拉高 `quality`。训练完成后，我拿到的是 base model 加 LoRA adapter，再把它挂回 Orchestrator，作为新的策略模型接回原系统。
