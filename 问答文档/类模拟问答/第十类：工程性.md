**第十类：工程稳定性与系统鲁棒性类问题**

这一类会明显区分两种人：

- 一种是会讲“我们用了 Agent、用了 RL、用了检索”
- 另一种是真的想过“这套系统在线上怎么跑、工具怎么接、失败了怎么办、怎么保证不把环境搞坏”

你这类问题里，面试官其实在看的是：

- 你的系统是不是只是 prompt 串起来的 demo
- 还是一个有明确控制边界、工具边界、失败处理和可观测性的工程系统

这一类你特别要求了要把 `MCP`、`工具调用`、`代码沙盒执行`、`MCP 和 function calling 的区别` 讲细，我下面就按这个重点来写。

---

## 一、这一类问题到底在考什么

面试官主要在看 8 件事：

1. 你是否理解 Agent 系统为什么需要标准化工具接口  
2. 你能不能说清 `MCP` 在这个项目里到底解决什么问题  
3. 你知不知道系统到底调用了哪些工具，哪些是 MCP 暴露的，哪些是内部模块  
4. 你能不能讲清代码执行为什么不能直接裸跑  
5. 你是否考虑过超时、失败、重试、回退、权限边界  
6. 你知不知道 `MCP` 和 `function calling` 不是一回事  
7. 你能不能说清日志、轨迹、审计为什么重要  
8. 你是否真的有“线上系统视角”  

---

## 二、这一类的学习目标

你学完这一类，至少要做到：

- 能解释什么是 MCP
- 能解释为什么这个系统用 MCP
- 能说清系统调用了哪些工具
- 能说清哪些能力是工具，哪些能力是内部模块
- 能讲清代码沙盒怎么做安全执行
- 能讲清 MCP 和 function calling 的区别
- 能解释工具失败时系统怎么处理
- 能讲清为什么状态机、日志和轨迹回放是工程核心

---

## 三、先建立一个总理解

这一类最核心的一句话是：

> 这套系统不是“模型会不会调工具”的问题，而是“系统如何以可控、可审计、可扩展的方式接入外部能力”的问题。

也就是说，在这个项目里：

- Agent 决定“要不要用工具、用哪个工具、什么时候用”
- MCP 负责把工具变成统一可调用能力
- StateMachine 负责控制流程
- Sandbox / Executor 负责把高风险操作隔离起来
- 日志和轨迹负责让错误可回放、可分析、可训练回流

这才是一个真正能落地的 Agent 系统。

---

## 四、MCP 到底是什么，为什么这里要用 MCP

这个问题是第一高频题。

**标准答法：**

MCP 在这里可以理解成一个**标准化的 Agent-Tool 协议层**。  
它的价值不在于“又多了一个名词”，而在于把工具调用从“每个 Agent 各自硬编码接不同接口”变成了统一能力接入方式。

在这个项目里，我用 MCP 主要解决四个问题：

### 1. 工具接口标准化
不同工具本来接口形式差异很大：

- 搜索接口
- 网页 / PDF 正文解析
- 代码执行器
- 缓存 / memory 查询
- 结构化资源读取

如果每个 Agent 自己对接，会非常乱。  
MCP 的作用就是把这些工具统一成：
- 有 schema
- 有名字
- 有输入输出约束
- 可复用

### 2. Agent 与工具解耦
如果 RetrievalAgent、SynthesisAgent、Orchestrator 都直接绑死某个工具 SDK，后面很难替换。  
MCP 让 Agent 看到的是“能力”，而不是某个具体实现。

### 3. 工具可审计、可治理
MCP 接入后，工具调用就更容易做：
- 权限控制
- 调用日志
- 参数审计
- 失败统计

### 4. 扩展性更强
后面你要换搜索源、换 parser、换 executor，甚至加一个 citation 工具，都不用改整个 Agent 逻辑，只要按 MCP 协议接进来就行。

一句话总结：

> MCP 在这个项目里，本质上是“统一工具层接口 + 降耦 + 可审计 + 可扩展”的工程层设计。

---

## 五、这个系统到底调用了哪些工具

这里一定不要讲虚。  
你要能把“工具”和“内部模块”分开。

### 1. 通过 MCP 暴露给 Agent 的主要工具
你可以统一讲成下面几类。

#### 搜索工具
作用：
- 根据 query 检索候选网页、论文或资料来源
- 返回标题、摘要、URL、来源信息

典型用途：
- Retrieval 的第一步召回
- query rewrite 后的多路搜索

---

#### 正文解析工具
作用：
- 对高价值 URL、网页、PDF 做全文读取或正文抽取
- 返回结构化段落、章节、关键片段

典型用途：
- 摘要不足时读全文
- 抽实验支持、方法细节、ablation 结果

你前面已经建立过这套口径：
- 读全文本身通过 MCP 工具执行
- 何时读全文不是工具决定，而是 Plan + Validator + StateMachine 决定

---

#### 代码执行工具
作用：
- 执行 Python 或受限脚本
- 做统计、表格整理、画图、简单计算
- 返回结构化结果或图表文件

典型用途：
- 论文趋势统计
- benchmark 结果整理
- 表格生成、图形输出

---

#### Memory / Cache 查询工具
这块你可以讲得谨慎一点：

更稳的说法是：
- Memory Layer 本身是系统能力层
- 其中某些读写适配器可以通过 MCP 暴露为工具接口
- 但 memory 不等于一个“外部工具站点”

也就是说，你可以说：
> 短期会话 recall、语义缓存查询、实体记忆查询这类能力，在工程实现上可以通过 MCP 统一暴露成查询能力，但它们在系统定位上仍属于 Memory Layer，而不是独立决策模块。

---

### 2. 不一定通过 MCP 暴露，而更像内部模块的部分
这个区分你讲出来会很成熟。

#### Reranker
比如 `BGE-Reranker`  
它通常更像 Retrieval 内部调用的模型服务，而不是给 Orchestrator 直接用的“外部工具”。

#### Validator
Validator 是系统逻辑模块，不是外部工具。

#### StateMachine
它是控制流机制，不是工具。

一句话总结：

> 不是系统里所有能力都要做成 MCP 工具。真正适合做 MCP 的，是那些“跨模块复用、接口明确、可替换、可审计”的外部能力；像 Validator、StateMachine、Reranker 这种更偏系统内部逻辑或内部服务，不一定要暴露成 MCP 工具。

---

## 六、这个系统里工具调用大概是什么样的

你最好准备一个很像真实系统的例子。

例如用户问：

```text
统计扩散模型近五年的论文趋势，并按年份画图
```

更合理的系统链路是：

```text
Question
-> Orchestrator 生成 Plan
-> Retrieval 调搜索工具拿候选文献与网页
-> Validator 判断当前证据是否足够支撑“按年份统计”
-> 如果 metadata 还不够，继续检索或读正文
-> Synthesis 判断需要代码工具
-> 调用代码执行器生成统计表和趋势图
-> 返回文字结论 + 图表
```

这个例子很好，因为它同时体现了：
- 搜索工具
- 正文解析工具
- 代码执行工具
- Validator
- 结构化控制

## 七、代码沙盒安全执行到底是什么样的

这是你特别要求要讲细的部分。  
这题非常容易被问。

绝对不要只说：
“我们有个代码执行器，很安全。”  
这太空了。

更稳的讲法是：

> 代码工具不是让模型在宿主环境里直接执行任意代码，而是通过独立的受限执行环境做沙盒运行。

你可以把它拆成 6 个控制点。

---

### 1. 独立执行环境
代码不是在主服务进程里直接跑，而是在独立 executor 里运行。  
这样做的目的：
- 避免主进程被用户代码拖死
- 隔离风险
- 便于超时和资源回收

更成熟一点的表达是：
- 可以是独立进程
- 也可以是容器化 executor
- 核心目标是隔离，不让执行环境直接接触主服务

---

### 2. 文件系统限制
代码不应该随意读写宿主文件系统。  
更合理的做法是：
- 只给一个临时工作目录
- 白名单可读文件
- 输出文件写到指定 artifact 目录
- 任务结束后回收

这能防止：
- 乱读本地敏感文件
- 污染项目目录
- 写出不可控副作用

---

### 3. 网络权限限制
这是非常关键的一条。

代码执行时通常应当：
- 默认禁网
- 或只允许有限白名单访问

原因很简单：
- 不让生成代码自己去外网乱抓内容
- 避免外部依赖不可控
- 防止数据泄露和成本失控

你可以这样说：

> 在我的设计里，代码执行器更多承担“结构化处理和分析”职责，而不是再次代替检索系统做外部信息获取，所以网络权限默认应该受限。

---

### 4. 资源限制
执行环境必须限制：
- CPU 时间
- 内存
- 运行时长
- 输出大小
- 子进程数量

否则很容易出现：
- 死循环
- 大内存占用
- 过大输出
- fork 炸掉环境

这部分你可以用工程口径说：
- timeout
- memory cap
- stdout/stderr length cap
- process limit

---

### 5. 包和解释器限制
不能让模型随意 import 宿主环境里一堆未知包。  
更合理的做法是：
- 预装白名单包
- 明确允许运行的解释器版本
- 不允许动态安装外部依赖
- 不允许执行危险系统命令

这样工具才是“可控分析器”，不是“任意代码入口”。

---

### 6. 输出审计与结果回传
执行完之后，不是把一切原样扔回系统，而是：
- 捕获 stdout / stderr
- 捕获生成的图表或表格 artifact
- 返回结构化执行结果
- 记录日志

例如更像真实的返回可以是：

```json
{
  "status": "success",
  "stdout": "Generated yearly paper counts.",
  "artifacts": [
    "trend_plot.png",
    "paper_count.csv"
  ],
  "summary": {
    "years": [2021, 2022, 2023, 2024, 2025],
    "counts": [42, 67, 93, 121, 138]
  }
}
```

一句话总结：

> 代码沙盒的目标不是“让模型自由写代码”，而是“让模型在受限、可回收、可审计的环境里安全做分析”。

---

## 八、代码工具什么时候该调用，什么时候不该调用

这个问题很像产品和工程边界问题。

### 适合调用代码工具的场景
- 数量统计
- 表格整理
- 多来源结果汇总
- 趋势图 / 柱状图 / 简单可视化
- 规则明确的计算任务

### 不适合调用代码工具的场景
- 明明直接文本回答就够了
- 数据本身还没检索齐
- 问题本质上不是分析任务
- 只是想让代码再去外网搜信息

一句话总结：

> 代码工具应该用在“证据已经有了，但需要进一步结构化处理”的阶段，而不是用来替代检索。

## 九、MCP 和 function calling 到底有什么区别

这是非常高频、也非常容易说乱的一题。  
一定要讲清层次。

最稳的结论先说：

> `function calling` 是模型输出层的调用格式能力，`MCP` 是系统层的工具接入和调用协议。两者相关，但不是一回事。

你可以从 4 个维度讲。

---

### 1. 所在层次不同

#### Function Calling
它描述的是：
- 模型如何输出一个结构化函数调用请求
- 比如输出函数名和 JSON 参数

它更像“模型和调用方之间的一种格式约定”。

#### MCP
它描述的是：
- 工具如何注册
- schema 如何暴露
- 调用如何传输
- 返回如何统一
- 资源如何管理

它更像“系统和工具之间的协议层”。

一句话：
- function calling 偏模型输出层
- MCP 偏系统工具层

---

### 2. 关注点不同

#### Function Calling 关注
- 模型怎么把意图表达成函数调用
- 参数格式是不是对的

#### MCP 关注
- 工具怎么接入
- 工具怎么被发现
- 工具 schema 怎么统一
- 多工具如何治理
- 调用过程怎么审计

---

### 3. 绑定方式不同

#### Function Calling
通常比较绑定：
- 某个模型 API
- 某个厂商的工具调用机制

#### MCP
更强调：
- 工具层标准化
- 模型无关或相对低耦合
- 工具可替换、可共享、可复用

---

### 4. 关系是什么

最稳的说法不是对立，而是：

> Function calling 可以作为模型发起工具调用的一种方式，而 MCP 负责把这些工具以统一协议暴露和管理起来。

也就是说：
- 模型可以通过 function calling 决定“我要调哪个工具”
- 但真正工具怎么注册、怎么发现、怎么执行、怎么治理，是 MCP 管的

---

## 十、一个很稳的 MCP vs function calling 回答

如果面试官问：

> 你这里 MCP 和 function calling 有什么区别？

你可以直接答：

> 我会把它们放在两个层次理解。Function calling 主要解决的是模型输出层的问题，也就是模型怎么把“我要用工具”表达成一个结构化调用请求，比如函数名加 JSON 参数；MCP 解决的是系统层的问题，也就是工具如何被统一注册、暴露 schema、被 Agent 发现、调用、审计和替换。简单说，function calling 更像模型和调用方之间的格式能力，MCP 更像整个工具层的标准协议。在我的系统里，Agent 的工具能力统一按 MCP 暴露，这样搜索、正文解析、代码执行这些能力都可以一致接入；至于模型内部要不要用 function calling 形式来表达工具调用，那是更上层的实现细节，两者不是互斥关系。  

---

## 十一、工具失败了怎么办

这一类一定要讲失败处理，不然工程感不够。

### 1. 搜索工具失败
可能原因：
- 超时
- 返回空
- 结果质量低

处理：
- 重试有限次数
- query rewrite
- 降级到其他召回通道
- 多次失败后触发 replan 或保守回答

---

### 2. 正文解析失败
可能原因：
- PDF 解析失败
- 网页反爬
- 正文格式混乱

处理：
- 回退到摘要
- 尝试其他 parser
- 标记该来源可用性下降
- 不因为单一全文失败就整体崩掉

---

### 3. 代码执行失败
可能原因：
- timeout
- 包不可用
- 代码逻辑错误
- 数据格式异常

处理：
- 返回结构化失败原因
- 不直接把异常暴露成系统崩溃
- 必要时回到文本回答
- 高价值任务可允许一次修正重试

---

### 4. MCP 工具本身不可用
处理：
- 工具健康检查
- 熔断 / 降级
- 回退到轻量路径
- 日志打点，便于后续分析

一句话总结：

> 工程上最重要的不是“工具永远成功”，而是“工具失败时系统仍然可控”。

---

## 十二、状态机和结构化计划为什么重要

这一类和 MCP 是一套的。  
如果没有状态机和结构化计划，工具调用就很容易变成：

- prompt 里随便说一句“如果不够就继续搜”
- 然后模型每次临场发挥

这样的问题是：
- 行为不可控
- 很难复现
- 很难分析错误
- 很难做 RL 数据回流

而有了：
- Plan
- StateMachine
- Validator
- MCP tool layer

整个系统就变成：
- 决策清楚
- 执行清楚
- 失败清楚
- 回放清楚

一句话总结：

> MCP 解决“工具怎么统一接”，StateMachine 解决“工具什么时候接、按什么顺序接”。

---

## 十三、为什么日志和轨迹回放非常重要

这题你可以主动讲，会特别像真正做系统的人。

因为工具系统最怕这种问题：
- 某次调用失败了，但不知道失败在哪
- 某次回答错了，但不知道是检索错、Validate 错还是 code tool 错
- 某次 reward 很高，但实际上行为很差

所以必须记录：
- 当前 state
- 当前 action
- 工具调用参数
- 工具返回
- validator 输出
- 最终结果
- 错误码 / 异常信息

这样做的价值是：
- 能做 bad case 回放
- 能做 RL 数据回流
- 能定位工程瓶颈
- 能支撑线上排障

---

## 十四、这一类最像真实项目的坑

你可以主动讲几个。

### 1. 工具 schema 看起来统一，实际返回质量不统一
接口统一不代表内容质量统一，很多 parser 返回的结构仍然很脏。

### 2. 搜索和正文解析成功率不同步
搜索能命中，不代表正文能稳定解析出来。

### 3. 代码工具一旦权限放得太宽，风险很大
所以必须受限执行。

### 4. function calling 容易让人误以为“有了结构化输出就等于有了工具系统”
其实不是。  
结构化输出只是第一层，真正的工具治理还要靠 MCP 和运行时。

### 5. 线上 query 会诱导工具滥用
比如用户问一个简单定义题，系统却走了全文和代码执行。  
这时就说明 routing 或状态机有问题。

---

## 十五、你可以直接背的第十类核心回答

如果面试官问：

> 你这个系统工程上是怎么落地的？MCP、工具调用、代码执行这些是怎么做的？

你可以直接答：

> 我在工程上把系统拆成了决策层、工具层和执行层。决策层由 Orchestrator、Validator 和 StateMachine 控制，负责决定什么时候检索、什么时候读全文、什么时候 replan、什么时候进入代码执行；工具层通过 MCP 做标准化接入，把搜索、正文解析、代码执行等能力统一成有 schema 的可调用接口；执行层则负责真正跑工具和隔离高风险操作。  
> MCP 在这个项目里的核心价值不是一个新名词，而是让工具接入标准化、可审计、可替换，避免每个 Agent 各自硬编码不同工具接口。像搜索、网页正文解析、全文读取、代码执行这些能力都适合做成 MCP 工具；而 Validator、StateMachine、Reranker 更偏系统内部逻辑，不一定要作为 MCP 工具暴露。  
> 对代码执行这一块，我不会让模型直接在宿主环境里跑任意代码，而是通过独立的受限执行环境来做沙盒运行，限制文件系统、网络、CPU、内存、超时时间和可用依赖，把输出统一成结构化结果和 artifact 再回传。这样既能支持统计、表格整理和可视化，又不会让系统失控。  
> 至于 MCP 和 function calling，我会把它们放在不同层次理解：function calling 更像模型输出层的结构化调用格式，而 MCP 是系统层的工具协议和治理机制。简单说，function calling 解决“模型怎么表达要用工具”，MCP 解决“工具如何被统一接入、发现、调用和审计”。

## 十六、这一类的高频追问补充（含答案）

### 1. 为什么你这里需要 MCP，而不是直接在代码里写几个工具函数？
**答案：**  
因为直接写工具函数只能解决“能调”，解决不了“统一 schema、统一治理、统一审计、统一替换”。项目一旦工具多了，没有标准协议层会很快失控。

### 2. MCP 和插件系统有什么区别？
**答案：**  
插件系统更像实现方式，MCP 更像协议层。它强调的是工具如何标准化暴露和被 Agent 使用，而不是某个具体插件框架。

### 3. function calling 已经能传 JSON 了，为什么还不够？
**答案：**  
因为 JSON 输出只解决了“模型如何表达调用请求”，没有解决工具注册、发现、权限控制、调用审计、结果治理这些系统问题。

### 4. 为什么代码执行必须沙盒隔离？
**答案：**  
因为代码执行是系统里风险最高的能力之一。如果直接在宿主环境里跑，可能带来文件泄露、资源占满、网络滥用和系统崩溃风险。

### 5. 你的代码沙盒都限制了什么？
**答案：**  
至少限制文件系统访问范围、网络访问、CPU、内存、超时时间、输出长度、可用依赖和子进程能力，保证它是受控分析器，不是任意执行入口。

### 6. 为什么不是所有工具都走 MCP？
**答案：**  
因为有些能力更适合作为系统内部模块，比如 Validator、StateMachine、Reranker。MCP 更适合那些跨模块复用、接口清晰、需要统一治理的外部能力。

### 7. 工具失败时系统会不会直接挂掉？
**答案：**  
不应该。更合理的是有限重试、回退、降级、保守回答或触发 replan，而不是让单个工具失败把整个系统拖死。

### 8. 检索工具和代码工具哪个风险更高？
**答案：**  
代码工具风险更高，因为它涉及主动执行，所以必须更严格隔离；检索工具更多是外部依赖风险和结果质量风险。

## 十七、这一类你现在最该背熟的 12 句话

1. 这套系统不是“会不会调工具”，而是“怎么以可控方式接工具”。  
2. MCP 的核心价值是工具标准化、降耦、可审计和可扩展。  
3. Agent 决定要不要用工具，MCP 负责把工具统一暴露出来。  
4. 搜索、正文解析、代码执行最适合做成 MCP 工具。  
5. Validator、StateMachine、Reranker 更偏系统内部逻辑，不一定作为 MCP 工具暴露。  
6. 代码执行不能直接在宿主环境里裸跑。  
7. 沙盒执行的关键是独立环境、权限限制、资源限制和输出审计。  
8. 代码工具应该用于结构化分析，不应该代替检索系统去外网乱抓信息。  
9. function calling 是模型输出层能力，MCP 是系统层工具协议。  
10. function calling 解决“怎么表达调用”，MCP 解决“工具怎么接入和治理”。  
11. 工具失败不可避免，关键是系统失败时是否仍然可控。  
12. 状态机管流程，MCP 管工具接入，这两者一起才构成真正能落地的 Agent 系统。
