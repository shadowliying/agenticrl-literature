**第八类：数据集与评测类问题**

这一类非常关键。  
因为前面你已经把架构、检索、Validator、RL、reward、memory 都讲了，如果到了这里说不清：

- 数据从哪里来
- 为什么是这批数据
- 怎么切训练集和评测集
- 指标为什么这么选
- 怎么证明 RL 真的有效
- 怎么避免“只是因为搜索器刚好发挥好”

那前面很多设计都会显得像“想法很好，但没有被验证”。

所以这一类的核心不是背几个数字，而是回答：

> 我怎么证明这套系统真的有效，而且我知道它为什么有效。

---

## 一、这一类问题面试官到底在考什么

面试官通常在看 8 件事：

1. 你有没有真正构建训练数据，而不是只跑了几个 demo  
2. 你知不知道训练数据和评测数据必须严格隔离  
3. 你能不能说清数据最小单位到底是什么  
4. 你会不会讲为什么评测不能只看一个分数  
5. 你知不知道哪些指标是主指标，哪些是诊断指标  
6. 你能不能证明 RL 带来的增益不是偶然  
7. 你会不会设计 baseline 和 ablation  
8. 你有没有做过 bad case 分析和线上回流思路  

---

## 二、这一类的学习目标

你学完这一类，至少要做到：

- 能解释 `2500 / 800` 这两个数字的意义
- 能说清训练数据最小单位是 `trajectory`，不是单句答案
- 能说清数据来自哪些来源、怎么筛、怎么清洗
- 能讲清训练集、验证集、测试集、独立评测集怎么隔离
- 能解释为什么不能只看 ROUGE 或 BLEU
- 能讲清主指标和辅助指标分别是什么
- 能讲清 baseline、ablation、bad case 回流
- 能回答“怎么证明 RL 真有用”

---

## 三、先建立总理解

这一类最核心的一句话是：

> 这个项目的数据和评测，不是围绕“文本像不像标准答案”来设计的，而是围绕“任务有没有真正完成、证据链有没有真的建立、策略有没有真的变好”来设计的。

因为你的项目不是普通生成任务，而是：

- 多步检索
- 结构化验证
- 高层动作策略优化
- 多轮和长期依赖

所以它不能只靠一个文本相似度分数来评估。  
你要看的是：

- 最终任务完成没有
- 关键点覆盖没有
- 检索是不是更有效
- 错误行为是不是减少了
- 成本和步数是不是下降了

---

## 四、训练数据到底是什么

这是第一高频题。  
你一定不能答成“就是一些问答数据”。

**标准答法：**

我的训练数据最小单位不是单条问答对，而是**任务轨迹**。  
因为这个项目训练的不是最终答案生成，而是 Orchestrator 的高层策略。所以训练样本必须保留：

- 问题是什么
- 初始 plan 是什么
- 每一步 state 是什么
- 选了什么 action
- action 之后发生了什么
- Validator 给了什么反馈
- 最终 reward 是多少

也就是说，真正进入 RL 的数据长得更像：
- `query`
- `state`
- `action`
- `transition`
- `reward`
- `trajectory`

而不是：
- 问题
- 标准答案

这一点很重要，因为它直接区分了你是在做“语言建模”，还是在做“策略优化”。

---

## 五、2500 条 RL 数据是怎么来的

这个你一定要讲细。  
因为“2500 条 RL 数据”如果不解释来源，就会显得很虚。

我建议你统一讲成三类来源。

---

### 1. baseline / 规则系统自动 rollout 生成的轨迹
这是第一批冷启动数据。  
目的不是一开始就追求最优，而是先让系统积累可用轨迹。

来源可以包括：
- 规则化 Orchestrator 跑 query
- prompt-only baseline policy
- 旧版 agent 系统中可复用的高质量执行路径

自动 rollout 时记录：
- question
- memory recall
- initial plan
- trajectory steps
- validator outputs
- final answer
- reward components

这一批数据的价值是：
- 成本相对低
- 跟真实系统流程一致
- 很适合做早期 SFT / RL 冷启动

---

### 2. 人工修订和筛选后的高质量轨迹
这部分非常关键，因为只靠自动 rollout，坏样本会很多。

典型流程是：
1. 从复杂 query 中挑高价值样本  
2. 检查 plan 是否合理  
3. 检查 `required_slots` 是否完整  
4. 检查动作顺序是否合理  
5. 修正明显错误路径  
6. 保留可当作“好策略示范”的轨迹  

这一部分的价值是：
- 能把复杂问题的正确路径打稳
- 可以覆盖规则系统不擅长的复杂场景
- 对 SFT 非常重要

---

### 3. query 改写与表达扩增得到的轨迹
这部分不是增加新知识，而是增加表达多样性。

比如同一问题：
- `比较 BERT 和 RoBERTa 的预训练差异，并解释为什么去掉 NSP`
- `从 pretraining 目标设计的角度对比 BERT 和 RoBERTa，并说明 NSP 被移除的原因`
- `分析 RoBERTa 相比 BERT 的预训练改动，尤其是为什么删除 NSP`

这些问题本质相近，但表达不同。  
如果不做扩增，模型容易只记住少数模板问法。

这一部分的价值是：
- 提升表达鲁棒性
- 降低训练分布过窄的问题
- 增强 query 理解泛化

---

## 六、RL 数据里那 15% 公开数据集到底怎么来的

这一段你一定要补清楚，不然“公开数据集适配”听起来会很空。

我建议你统一讲成：

> RL 数据里大约有 `15%`，也就是约 `375` 条样本，来自公开学术问答数据集，但不是直接原样拿来训练，而是经过“筛选 -> 改写 -> 轨迹化”三步适配之后再混入训练集。

更像真实项目的一个拆法可以这样讲：

- `SciQ` 适配约 `90` 条  
  主要选可转成“概念解释 + 原理补充”的样本
- `PubMedQA` 适配约 `110` 条  
  主要选医学/生命科学领域里需要证据判断和结论归纳的问题
- `QASPER` 适配约 `95` 条  
  主要选论文级问答，适合改造成“读摘要 / 读正文 / 找实验支持”的轨迹
- `ScholarQA` 或同类学术检索问答样本适配约 `80` 条  
  主要选“论文对比 / 综述 / 方法定位”这类更贴近科研检索的 query

为什么不是直接拿来用，而是要适配？

因为公开数据集原始形式大多是：

- `question -> answer`
- 或 `question -> answer + evidence`

但我的项目要训练的是 Orchestrator 的策略层，所以它需要的是：

- query
- required_slots
- 检索阶段状态
- action
- validator 反馈
- reward

所以适配过程一般是三步：

### 第一步：筛选
把不适合科研检索场景的样本先去掉，比如：

- 过于简单的单点事实题
- 没有明确学术对象的问题
- 无法形成多步检索或验证价值的问题

### 第二步：改写成项目统一 query 风格
比如把原始问法改成更贴近你的业务表达：

- 从单一句子问题改成“比较 / 原因 / 证据支持”风格
- 补充时间范围、比较对象、实验支持等约束

### 第三步：轨迹化
把原始 QA 样本转成：

- 初始 plan
- required_slots
- baseline rollout 轨迹
- validator 中间状态
- 最终 reward

你面试里可以这样说：

> 公开数据集不是直接拿来喂 RL，而是先筛掉和科研检索闭环不匹配的样本，再改写成统一 query 风格，最后通过 baseline policy 跑成轨迹格式。这样公开数据起到的是“补任务多样性”的作用，而不是直接替代项目自己的轨迹数据。

## 七、2500 的数据组成怎么讲更像真的做过

你前面已经用过这个口径，可以继续统一：

- RL 总数据量：`2500`
- 训练集：`2000`
- 验证集：`300`
- 测试集：`200`

来源构成可以讲成：
- `60%` 来自 LLM / baseline policy 自动生成后筛选的科研 query 轨迹
- `25%` 来自 query 改写与表达扩增
- `15%` 来自公开学术问答或科研检索数据集适配后的样本

你可以强调一点：

> 这里的“2500 条”不是 2500 个单句答案，而是 2500 条带状态、动作和回报信息的任务轨迹样本。

这句话很关键。

## 八、800 条独立评测集到底是怎么来的

你之前这里讲得还不够具体，这一段一定要补。

最稳的说法不是只说“独立测试集”，而是把来源讲清楚。

我建议你统一讲成：

> 800 条独立评测集不是从训练集里切出来的，而是单独构建的端到端系统评测集，来源分成三部分：内部人工设计高价值科研 query、公开数据集的 held-out 适配样本，以及历史 bad case/高难 query 的清洗版样本。

可以讲成下面这个更真实的构成：

- `320` 条内部人工设计的科研 query  
  由项目组按业务类型手工设计，覆盖：
  - 方法比较
  - 原因分析
  - 实验支持
  - 趋势统计
  - 多轮追问

- `260` 条来自公开数据集的 held-out 适配样本  
  来源和 RL 公开数据集来源相同，但样本 ID、问题实例和表达都与训练侧严格隔离  
  主要来自：
  - `PubMedQA`
  - `QASPER`
  - `ScholarQA`
  - 少量 `SciQ`

- `220` 条历史 bad case 清洗和重写后的高难样本  
  这些不是直接把训练里失败的同题目拿来评测，而是基于 bad case 类型重新构造：
  - 多轮代词 / 省略
  - 冲突来源
  - 摘要不够、必须读全文
  - query 比较长、包含多个约束

为什么要这样构成？

因为这 800 条评测集承担的是三个任务：

1. 验证系统对“标准科研 query”的端到端能力  
2. 验证系统对“公开学术问答分布”的泛化能力  
3. 验证系统对“真实难点和坏场景”的鲁棒性  

如果只用单一来源，评测会偏。

## 十二、训练集和评测集为什么必须严格隔离

这是高频基础题，但一定要答深一点。

**标准答法：**

因为训练集和评测集服务的目标不同：

- 训练集是用来让模型学策略
- 评测集是用来验证模型有没有真的泛化

如果两者不隔离，会有三个问题：

### 1. 指标会虚高
模型可能只是记住了某类 query 路径或答案模式，而不是真的学会策略。

### 2. 无法证明泛化
你就没法说模型对新问题也有效。

### 3. 无法判断 RL 是否真带来提升
因为提升可能只是训练样本记忆带来的，而不是策略能力提升。

所以我的统一口径是：

- RL 数据：`2500`
  - train `2000`
  - val `300`
  - test `200`
- 另外还有 **独立系统评测集 `800`**
  - 不参与训练
  - 用来做端到端效果评估

这就形成了：
- 训练 / 调参 / 内部测试
- 独立系统评测

两个层次。

## 十三、那 800 条评测集到底是干什么的

这个问题也很重要。

`800` 条评测集不是给训练看的，而是给系统效果证明看的。  
它的作用是：

- 比较 baseline 和 RL 策略系统
- 做端到端评测
- 看 Completion、Top-5、检索步数、成本
- 支撑你简历里的最终结果数字

你可以这么讲：

> 2500 条数据主要是策略学习和模型调参使用，800 条独立评测集主要用于验证系统端到端能力，尤其是任务完成率、关键点覆盖、检索效率和成本收益，避免把训练增益和评测结果混在一起。

## 十五、这些“变化”分别说明了什么

这一段很重要，因为面试官经常会问：

> 这些数字分别说明了什么能力提升？

你可以这样解释：

- `Completion Rate 68.1% -> 79.0%`  
  说明系统端到端真正更会完成任务，而不是只优化了某个局部环节。

- `Key-Point Coverage 71.4% -> 83.2%`  
  说明回答更完整，尤其是复杂问题里关键槽位覆盖更稳。

- `Top-5 Hit Rate 58.4% -> 82.0%`  
  说明 retrieval + rerank + validate 闭环确实让高价值证据更容易进入候选前列。

- `平均检索次数 4.2 -> 2.8`  
  说明高层策略变得更收敛，少走弯路。

- `无效检索步数 1.8 -> 1.2`  
  说明 RL 学到的不是“更会说”，而是“更少绕圈”。

- `低分硬答比例 9.7% -> 3.9%`  
  说明 reward 和 Validator 设计在压制“证据不足也回答”的行为。

- `API 成本 0.41 -> 0.30`  
  说明系统的提升不只是精度提升，还带来了真实落地价值。

## 十六、评测为什么不能只看 ROUGE / BLEU

这是这一类最经典的问题之一。  
一定要答得很稳。

**标准答法：**

因为科研问答不是纯文本复述任务。  
很多时候答案的表达方式可以很多样，但真正重要的是：

- 事实对不对
- 关键点全不全
- 证据链是否完整
- 比较关系有没有说清
- 原因和实验支持有没有覆盖

如果只看 ROUGE 或 BLEU，会有两个问题：

### 1. 文本像，不代表事实对
一个答案可能和参考答案用词很像，但漏掉关键证据或关键限制条件。

### 2. 文本不像，也可能答得对
科研综述、方法比较、原因分析这类问题，本来就允许多种表述。  
只要关键点覆盖、事实正确，它就应该算好答案。

所以在这个项目里，文本相似度最多只能作为非常弱的辅助指标，绝不能作为主评测依据。

一句话总结：

> 科研问答更关心“有没有答对、答全、答稳”，而不是“像不像标准答案”。

---

## 十七、主指标和辅助指标应该怎么分

你前面在 Validator 和 reward 里已经建立了这个思路，这里继续统一。

---

### 主指标：直接反映业务价值
这些是你最应该优先讲的。

#### 1. `Completion Rate`
看任务有没有真正完成。  
比如用户问 3 个点，系统是不是都覆盖了，而不是答了一半。

#### 2. `Key-Point Coverage`
看关键点覆盖情况。  
这和 `required_slots` 天然对应。

#### 3. `LLM-as-Judge`
用来大规模快速判断最终答案质量，但不单独决定一切。

#### 4. 人工抽样准确性 / 完整性
这是最终兜底。  
尤其对复杂问题，你不能完全信自动 judge。

---

### 辅助指标：帮助解释系统行为
这些主要用来诊断“为什么好 / 为什么不好”。

#### 1. `Top-5 Hit Rate`
看检索和 rerank 是否真的把高价值 evidence 提上来了。

#### 2. 平均检索步数
看策略是不是更高效。

#### 3. `replan` 频率
看系统是不是过度换路。

#### 4. 无效检索步数
这是非常重要的过程指标。  
它直接反映策略层有没有减少绕圈。

#### 5. API 成本
这个直接反映落地价值。

#### 6. 全文读取次数
看是否存在全文滥用。

你可以统一成一句：

> 主指标决定系统有没有真正更好，辅助指标决定系统是怎么变好的、以及有没有副作用。

---

## 十八、怎么证明 RL 真有用，而不是搜索器刚好发挥好了

这是高频难题。  
你一定要准备 baseline 和 ablation。

---

### 1. baseline 怎么设
最稳的是至少准备三档：

#### Baseline A：Prompt-only / Rule-based Orchestrator
不做 RL，只靠 prompt 和规则跑完整链路。

#### Baseline B：SFT only
做结构化对齐，但不做 GRPO。  
这个 baseline 很关键，因为它能证明：
- 提升到底来自 SFT
- 还是来自 RL

#### Baseline C：Full system with SFT + GRPO
这是你的最终系统。

这样你就能比较出：
- 规则 -> SFT 的提升
- SFT -> RL 的提升
- RL 是否真的提供了额外策略增益

---

### 2. ablation 怎么做
你至少可以讲三种消融：

#### Ablation 1：去掉 Validator 过程信号
看 reward 只剩终局质量时，系统会不会更容易早答。

#### Ablation 2：去掉 `info_gain`
看是否更容易重复搜索。

#### Ablation 3：去掉 memory / 语义缓存
看成本和多轮表现是否下降。

如果你想再讲深一点，还可以说：
- 去掉 phase 1 / phase 2 切换
- 直接单阶段 reward
- 看训练稳定性和结果差异

一句话总结：

> baseline 证明系统整体值不值，ablation 证明每个关键设计到底值不值。

---

## 十九、数据集会遇到什么实际问题

这一类如果你能主动讲几个坑，会特别像真做过。

### 1. query 类型分布不均
定义题太多，复杂比较题太少。  
结果模型看起来指标不错，但一到复杂问题就不稳。

### 2. 自动生成轨迹质量参差不齐
规则系统跑出来的轨迹可能格式对了，但策略不一定好。  
如果直接全喂进去，会污染训练。

### 3. 评测集和训练集表达过近
如果 query 改写不够充分，模型可能只是记住了表达模板。

### 4. LLM-as-Judge 偏好问题
Judge 模型可能偏好某类“写得像综述”的答案，但不一定真正更有证据。

### 5. bad case 难集中在长尾 query
比如多轮指代、省略、跨文档冲突。  
这些样本量少，但业务上很关键。

## 二十、数据和评测这类问题的一个很强回答

如果面试官问：

> 你这个数据是怎么做的，怎么证明系统真的有效？

你可以直接答：

> 我的训练数据最小单位不是单条问答，而是轨迹，因为我要训练的是 Orchestrator 的策略层，而不是单纯答案生成。整体 RL 数据大约 2500 条，其中训练集 2000、验证集 300、测试集 200，来源主要分成三部分：一部分是 baseline policy 和规则系统跑出来的高质量轨迹，一部分是人工修订后的复杂 query 轨迹，另一部分是 query 改写和表达扩增得到的样本。另外大约 15%，也就是 375 条左右，来自公开学术问答数据集的适配样本，主要用到 SciQ、PubMedQA、QASPER、ScholarQA，但这些样本不是直接原样拿来训练，而是经过筛选、改写和轨迹化之后再混入训练。除此之外，我还单独构建了 800 条独立评测集做系统级验证，这 800 条不是从训练集切出来的，而是由 320 条内部人工设计 query、260 条公开数据集 held-out 适配样本、220 条历史 bad case 重写样本组成，保证训练和评测严格隔离。  
> 评测上我不会只看 ROUGE 或 BLEU，因为科研问答更重要的是关键点是否覆盖、证据链是否完整、任务有没有真正完成。所以主指标我看 Completion Rate、Key-Point Coverage、LLM-as-Judge 和人工抽样，辅助指标再看 Top-5 命中率、平均检索步数、无效检索步数、replan 频率和 API 成本。为了证明 RL 真有用，我至少会做 prompt/rule baseline、SFT-only baseline 和 SFT+GRPO 的对比，再结合消融实验看 Validator、info_gain、memory 等设计对结果的贡献。这样我最后才能比较有把握地说，系统从 68% 提升到 79% 不是偶然，而是高层策略和检索闭环共同优化后的结果。

## 二十一、这一类的高频追问补充（含答案）

### 1. 为什么是 2500 条，不是更多或更少？
**答案：**  
这个数字不是一个理论上最优值，而是当前阶段在数据质量、标注成本和策略覆盖之间做的工程平衡。因为这里的样本不是单句问答，而是完整轨迹，构造成本比普通 QA 高得多，所以核心不只是数量，而是轨迹质量和类型覆盖。

### 2. 为什么 800 条评测集足够支撑结论？
**答案：**  
因为它不是拿来训练，而是拿来做系统级比较和趋势判断。关键不在于数字绝对大，而在于任务类型覆盖够不够、训练是否严格隔离、指标是否能稳定区分 baseline 和最终系统。

### 2.1 那 800 条到底从哪里来？
**答案：**  
不是从训练集里切出来的，而是单独构建的。可以讲成三部分：320 条内部人工设计的科研 query，260 条公开数据集的 held-out 适配样本，220 条历史 bad case 类型重写后的高难样本。这样既覆盖标准科研问答，也覆盖公开学术问答分布和真实难点场景。

### 3. 你怎么防止 query 改写带来的数据泄露？
**答案：**  
改写样本只在训练侧做，评测集不做同源表达改写；同时在评测集构建时会避免和训练 query 在语义上过近，至少保证问题类型可以重合，但表达和实例不要直接复用。

### 4. 你怎么判断一条轨迹值不值得进训练集？
**答案：**  
我主要看三层：结构是否完整、行为是否合理、任务是否有代表性。结构不合法、提前回答、关键槽位缺失、路径明显错误的轨迹不会直接进入训练。

### 5. 为什么主指标要有人抽样，而不是全自动？
**答案：**  
因为科研问答里很多问题没有唯一标准答案，自动 judge 只能高效近似，不能完全替代人对事实链和关键点覆盖的判断。所以人工抽样是必要的兜底。

### 6. 你怎么证明成本下降不是因为检索偷懒？
**答案：**  
不能只看成本下降，要和 Completion Rate、Key-Point Coverage、Top-5 命中率一起看。只有在质量不下降、甚至提升的前提下，成本下降才说明策略更有效，而不是系统偷工减料。

### 6.1 公开数据集为什么不会把训练带偏？
**答案：**  
因为公开数据集只占约 15%，作用主要是补任务多样性，而不是主导训练分布。并且进入训练前会先做筛选、改写和轨迹化，过滤掉太简单或与科研检索闭环不匹配的样本，所以它起的是“补分布”的作用，不是“替代自有轨迹”。

### 7. 为什么要看 Top-5 命中率，而不是只看最终答案？
**答案：**  
因为最终答案只是结果，Top-5 命中率能更早诊断检索和精排有没有把高价值证据提上来。它对定位问题来源很重要，尤其是在最终答案变差时，能判断问题出在 retrieval 还是 synthesis。

### 8. 如果评测结果很好，但线上用户反馈一般，你怎么解释？
**答案：**  
通常说明评测分布和真实线上分布还有差距，比如多轮、省略、模糊问法、时间敏感问题覆盖不够。下一步就要做线上 bad case 回流，而不是盲信离线指标。

## 二十二、这一类你现在最该背熟的 15 句话

1. 这个项目的训练数据最小单位不是单句答案，而是轨迹。  
2. 2500 条 RL 数据是用于策略学习的，不是普通 QA 对。  
3. 数据来源主要包括 baseline rollout、人工修订、query 改写扩增，以及一小部分公开数据集适配样本。  
4. 训练集、验证集、测试集和独立评测集必须严格隔离。  
5. 800 条评测集不是训练集切分，而是单独构建的系统级验证集。  
6. 科研问答不能只看 ROUGE，因为文本像不等于事实对。  
7. 主指标看任务完成和关键点覆盖，辅助指标看检索效率和成本。  
8. `Completion Rate` 衡量任务有没有真正完成。  
9. `Key-Point Coverage` 衡量关键槽位有没有覆盖。  
10. Top-5 命中率能诊断 retrieval 和 rerank 是否真的有效。  
11. 无效检索步数下降，才说明高层策略真的在减少绕路。  
12. baseline 用来证明系统值不值，ablation 用来证明模块值不值。  
13. SFT-only baseline 很关键，因为它能区分“结构化对齐的收益”和“RL 的额外收益”。  
14. 成本下降必须和质量指标一起看，否则可能只是检索偷懒。  
15. 最终要证明的是“系统有没有真正更会完成科研问答任务”，而不是“某个单一分数有没有变高”。
