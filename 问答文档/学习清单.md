**学习总原则**
前期学习不要追求快，要追求“问题分类清楚、每类都能往下钻三层”。

你每一类问题，都要学到三层：
- 第一层：能说清“是什么”
- 第二层：能解释“为什么这样设计”
- 第三层：能回答“这个阈值/这个权重/这个模块为什么这么定，以及如果换一种方案会怎样”

你后面学习时，所有问题都尽量按下面这个模板去拆：
- 业务上为什么会有这个问题
- 系统为什么要这样设计
- 这个设计的关键参数或阈值怎么来的
- 如果不这样设计会出什么问题
- 线上或实验里怎么验证它真的有效

## 1. 业务理解类问题
这一类是最基础的，不懂业务，后面所有设计都会显得很空。

你要掌握的核心：
- 这个系统不是做“普通聊天问答”，而是做“科研文献检索与复杂科研问答”
- 真实任务不是简单 factoid，而是比较、归因、统计、演化分析、实验对比
- 科研场景的难点不是“搜不到”，而是“搜到一些相关内容，但证据不够完整、不够可靠、不够可回答”

你必须能举出的真实业务问题：
- 比较 BERT 和 RoBERTa 的预训练差异，并解释为什么去掉 NSP
- 统计扩散模型近五年的研究趋势，并按年份画图
- 对比两篇论文在数据集、实验指标、结论上的差异
- 解释某个方法为什么在某个 benchmark 上优于 baseline
- 总结某个方向过去三年的代表性工作，并分析技术演进路线

这类问题你必须理解的业务特点：
- 往往需要多跳检索，不是一篇文档就能回答
- 往往需要结构化抽取，例如时间、模型名、数据集名、指标值、结论
- 往往需要跨来源验证，不能只信一个摘要
- 有些问题需要代码辅助，例如计数、统计、表格整理、趋势图绘制
- 用户真正关心的不是“生成得像不像”，而是“事实链是否完整、对比是否严谨、来源是否可信”

面试官常问：
- 你的系统解决的业务问题到底是什么
- 为什么科研问答比普通 RAG 更难
- 典型用户会问什么样的问题
- 为什么这些问题不能直接让一个大模型自己回答

你要能回答到的深度：
- 不只是说“科研问题更复杂”
- 要能说出复杂在哪：检索跨度大、证据分散、问题包含多个约束、需要比较和归因、需要时效与来源质量控制

容易失分的点：
- 只会说“这是一个多 Agent + RL 项目”
- 说不出真实用户问题长什么样
- 把科研问答讲成通用聊天机器人

## 2. 项目总览与整体架构类问题
这一类问题考的是你是否真的掌控了全局。

你要掌握的核心：
- 为什么采用 Orchestrator-Worker 架构
- 为什么核心模块是 Orchestrator、Retrieval、Validator、Synthesis、Memory Layer
- 为什么不是一个大模型一步到位
- 为什么 Memory 是能力层，不是独立 Agent

你必须能讲清的职责划分：
- Orchestrator：做规划和动作决策，决定下一步做什么
- Retrieval：做召回、精排、证据抽取
- Validator：判断当前证据够不够回答问题
- Synthesis：基于充分证据组织最终答案，必要时调用代码
- Memory Layer：做 recall / write，支持多轮连续性、缓存复用、实体跟踪

你必须能解释“为什么这样拆”：
- 因为科研问答的核心瓶颈不是单次生成能力，而是“检索决策”和“证据充分性判断”
- 把决策、检索、验证、生成分开，可以让职责清晰，也方便单独优化
- Validator 独立出来，是为了防止系统拿到部分相关信息后就直接开始答
- Memory 不做策略决策，所以不适合做独立 Agent，否则职责会和 Orchestrator 重叠

面试官常问：
- 为什么不用一个大 Agent 统一完成
- 为什么要单独做 Validator
- 为什么 Memory 不是一个 Agent
- 多个模块之间怎么协作

你要能继续往下讲的细节：
- 这类任务中“证据是否足够”和“答案怎么表达”是两个不同问题，所以验证模块必须从生成模块中拆开
- 把 Orchestrator 作为 RL 训练主体，是因为它最接近序贯决策问题

容易失分的点：
- 只会背模块名，不会讲划分依据
- 说不清“哪个模块解决哪个业务问题”
- 一被问“为什么这样拆”就只会说“解耦、可扩展”，太空

## 3. 检索类问题
这一类是科研问答系统的基础盘，面试官会很爱追问。

你要掌握的核心：
- 为什么需要检索
- 为什么不能只做一次召回
- 为什么需要召回 + 精排 + 验证
- 什么时候只看摘要，什么时候要读全文
- 检索结果很多时如何控制噪声和成本

你必须理解的设计逻辑：
- 召回的目标是尽量找全候选证据
- 精排的目标是把最相关、最有支持力的证据往前提
- 验证的目标是判断这些证据是否足以支撑回答
- 这三步不是冗余，而是分别对应 recall、precision、answerability 三个不同问题

你必须能解释的细节：
- 为什么使用 BGE-Reranker
  你要能说：召回阶段更看覆盖，精排阶段更看语义对齐和细粒度相关性，科研问答里很多问题不是关键词匹配，而是方法、结论、对比关系的匹配
- 为什么不直接抓所有全文
  你要能说：全文抓取成本高、噪声大、对很多问题来说没有必要，而且容易把上下文打爆
- 什么时候要读全文
  你要能说：当摘要不足以支撑关键槽位，或者问题本身是实验设置、细节对比、方法差异分析这类“摘要不够”的任务时，就要继续读全文

你要掌握的业务例子：
- 如果用户问“BERT 和 RoBERTa 的预训练差异”，摘要可能够做初步判断
- 如果用户问“RoBERTa 为什么去掉 NSP，有没有实验支持”，摘要往往不够，需要更细的正文证据
- 如果用户问“扩散模型近五年论文趋势并画图”，需要的是结构化统计信息，不只是摘要文本

面试官常问：
- 为什么不能只靠召回结果回答
- 为什么需要 Reranker
- 什么时候决定打开全文
- 检索噪声怎么处理
- 搜索结果为空或很弱怎么办

你需要进一步学习的点：
- 查询改写
- 多查询召回
- 去重
- snippet 抽取
- 证据聚合
- 什么时候继续搜，什么时候换方向搜

容易失分的点：
- 只会说“用了 Reranker”
- 不知道为什么不是检索完直接生成
- 不知道摘要与全文的边界

## 4. Validator 与证据充分性类问题
这是你后面一定会被重点追问的一类，也是最能体现你是否真的懂业务的一类。

你要掌握的核心：
- 为什么科研问答里“相关”不等于“足够回答”
- 为什么 Validator 不能只是一个 bool
- 为什么要用结构化评分
- 为什么设置放行阈值、灰区和重规划阈值

你必须吃透的评分维度：
- coverage：关键槽位是否覆盖
- relevance：证据是否直接对应当前问题
- support_strength：证据是否明确、有支持力
- consistency：多个来源是否冲突
- source_quality：来源是否可信
- freshness：时效是否匹配
- info_gain：新一轮检索是否真的带来新信息

你必须理解的“槽位”概念：
- 科研问题通常天然带槽位
- 比如“比较 BERT 和 RoBERTa 的预训练差异，并解释为什么去掉 NSP”
  这个问题至少包含：实体、比较项、原因、可能还包含实验支持
- 如果只检索到了“RoBERTa 去掉了 NSP”，但没有检索到“为什么”和“实验表现”，那 coverage 就不完整

你必须理解的阈值设计：
- `sufficiency_score >= 0.75` 才进入生成
- `< 0.60` 触发 replan
- `0.60 ~ 0.75` 属于灰区，通常继续检索补证据

你必须会解释“为什么是这样分”：
- 0.75 以上通常代表关键槽位基本齐全，再继续搜的收益开始下降
- 0.60 以下往往意味着问题理解、检索方向或证据质量有根本问题，继续沿原路径搜下去收益不高
- 中间区间说明已有一定基础，但还不稳，继续搜是合理的

你必须理解“硬门槛”的意义：
- 关键槽位缺失，哪怕综合分看起来还可以，也不能放行
- 冲突严重时不能硬答
- 高风险任务没有高质量来源时不能放行
- 时间敏感问题但证据过旧时不能放行

面试官常问：
- 为什么要做 Validator
- 充分性评分为什么这样分维度
- 为什么 coverage 权重最高
- 为什么阈值是 0.75 和 0.60
- 如果分数很高但还是答错了，问题出在哪
- 如何处理来源冲突

这类问题你要学到的深度：
- 不是只背公式
- 要能解释每个维度为什么存在
- 要能讲清“这些阈值和权重不是拍脑袋，而是业务规则 + 验证集调出来的”

容易失分的点：
- 把 Validate 讲成“检索结果打个分”
- 不理解关键槽位覆盖
- 不知道阈值的业务含义

## 5. 强化学习总框架类问题
这一类问题考的是你是否真的理解“为什么这里要上 RL”。

你要掌握的核心：
- 为什么这个问题适合 RL
- 为什么训练对象是 Orchestrator，而不是 Synthesis
- 为什么采用 SFT + GRPO 两阶段
- 为什么不是纯规则或纯 prompt

你必须理解的逻辑：
- Orchestrator 面临的是一个典型的序贯决策问题：当前有一部分证据，下一步要不要继续搜，要不要 replan，要不要直接生成
- 这类决策不是一次性分类，而是随着状态变化不断更新
- 所以它比起内容生成，更像 policy learning

你必须掌握的 MDP 建模思路：
- State：问题、已检索证据、历史动作、验证结果、记忆召回信息等
- Action：检索、继续检索、重规划、生成、必要时代码执行
- Reward：证据充分性、信息增益、效率、最终答案质量
- Transition：由状态机推进
- Episode end：达到回答条件、到达最大步数、出现明确终止条件

你必须理解为什么是 SFT + GRPO：
- SFT 先把结构化输出和动作格式对齐，否则 RL 训练时动作空间会很乱
- GRPO 再在已有行为基础上优化策略选择
- 如果不先做 SFT，RL 很容易在早期因为输出格式不稳而学崩

面试官常问：
- 为什么这里要用 RL，不用规则
- 为什么训练 Orchestrator，不训练 Synthesis
- 为什么用 GRPO，不用 PPO
- SFT 和 RL 各自解决什么问题
- 这是不是只是把 RL 当噱头

你后面还要深入学的点：
- 为什么 GRPO 不需要 Critic
- Group ranking 的意义
- 为什么更适合 LLM 决策场景
- 训练时如何定义动作空间和轨迹

容易失分的点：
- 只会说“因为 RL 更智能”
- 说不出训练目标到底是什么
- 把 RL 讲成“让答案更好”，而不是“让决策更优”

## 6. Reward 设计、Reward Hacking、训练稳定性类问题
这是强化学习部分最难的一块，也是最能体现你是否真做过实验的一块。

你要掌握的核心：
- 为什么奖励不能只看最终答案质量
- 为什么需要过程奖励
- 为什么设计成两段式奖励
- reward hacking 会表现成什么样
- 什么时候停止训练，怎么判断训练是健康的

你必须理解的奖励组成：
- R_quality：最终答案质量
- R_sufficiency：证据充分性
- R_info_gain：信息增益
- R_efficiency：执行效率
- R_penalty：重复搜索、空搜索、低分硬答等惩罚

你必须理解为什么过程奖励重要：
- 科研问答任务链路长，如果只在 ANSWER 时给奖励，反馈会太远
- 模型会更倾向于直接回答，而不是先把证据补足
- 所以前期要更强调充分性和信息增益，让模型先学会“搜对、搜稳、别乱答”

你必须理解为什么是两段式：
- 第一阶段：过程强化，先稳住检索和验证行为
- 第二阶段：质量平衡，在行为稳定后提高最终答案质量的权重

你必须吃透的问题：
- 为什么第一阶段 `sufficiency` 权重最高
- 为什么第二阶段 `quality` 权重升高
- 如果一开始就把 `quality` 权重设很高会怎样
- 为什么 `info_gain` 不能太低，否则模型可能反复搜索
- 为什么 `efficiency` 不能太高，否则模型可能为了省步数而过早停止

你必须掌握 reward hacking 的典型表现：
- 为了刷过程奖励反复检索相似内容
- 低分也直接回答，试图赌终局质量分
- 倾向某一种动作，出现策略坍塌
- 把看起来“相关”的内容不断重复组织，实质上没有新信息

你必须知道怎么应对：
- 给重复检索惩罚
- 给低 sufficiency 强行回答惩罚
- 用硬门槛限制不合格证据直接放行
- 监控信息增益、动作分布、完成率，而不是只看 loss

你必须会回答“什么时候停止训练”：
你后面可以按工程口径来答：
- 当离线验证集上的关键指标进入平台期，比如完成率、无效检索步数、Top-5 证据命中率连续多轮评估没有明显提升
- 当 reward 上升但 bad case 不再减少时，说明模型可能开始学偏
- 当 entropy、动作分布、replan 频率等过程指标进入稳定区间
- 当继续训练带来的收益小于成本，或者已经开始出现过拟合和策略退化迹象

面试官常问：
- 你的奖励函数为什么这么设计
- 怎么避免 reward hacking
- 训练中什么现象说明模型学偏了
- 你怎么判断该停止训练
- 如果 reward 变高但线上效果不好怎么办

容易失分的点：
- 只会说“加几个 reward 相加”
- 不会讲每个 reward 的业务意义
- 说不清“何时停训”“何时说明模型开始乱学”

## 7. Memory 与 Context 类问题
这一类问题很容易被追问，而且很能体现系统感。

你要掌握的核心：
- Memory 和 Context 的区别
- 为什么 Memory 是能力层
- 三层记忆分别解决什么问题
- recall/write 在流程中的具体作用
- 记忆污染、过期、噪声怎么处理

你必须理解三层记忆：
- 短期会话记忆：支持多轮追问和上下文延续
- 语义缓存：复用相似问题的检索结果，降低成本
- 实体知识记忆：做实体追踪和指代消解

你必须能结合真实场景讲：
- 用户先问 “介绍一下 BERT 的预训练方法”，再问 “那它为什么去掉 NSP”
  这里如果没有实体记忆，很容易解析错“它”
- 用户问 “扩散模型近五年研究趋势”，之后追问 “那 2023 年拐点背后的原因是什么”
  如果没有短期会话记忆，后面追问会断上下文
- 用户反复问相似问题，语义缓存可以避免每次都重新调搜索接口

你必须理解 Memory 的风险：
- 写入过宽会污染记忆
- 旧信息可能过时
- recall 太宽会把噪声注入 context
- 不是所有中间结果都值得写入长期记忆

你必须理解写入原则：
- 写入高价值、高置信、可复用的信息
- 冲突信息不直接写长期记忆
- 时间敏感信息要带 freshness
- recall 进 context 的是摘要，不是整个 memory 库

面试官常问：
- Memory 和 Context 有什么区别
- 为什么不直接用上下文，不单做 Memory
- 为什么要分三层
- 语义缓存为什么能降成本
- 如何避免错误记忆不断传播

容易失分的点：
- 把 Memory 讲成简单缓存
- 不会区分短期记忆和长期知识
- 说不清 recall 和 context assembly 的关系

## 8. 数据集与评测类问题
这一类问题是用来证明你不是“只搭了个架子”。

你要掌握的核心：
- 数据从哪里来
- RL 数据和评测集为什么要严格隔离
- 离线评测看什么
- 为什么不能只看一个指标
- 如何证明系统不是表面上看起来更好，而是真的更有效

你必须掌握的数据口径：
- RL 训练数据：2500 条
- 系统评测集：800 条
- 训练与评测严格隔离
- 数据来自多种任务类型，不只是单一问答

你必须理解为什么这样设计：
- RL 数据是为了学策略
- 评测集是为了验证端到端效果
- 如果不隔离，就无法证明泛化能力
- 科研问答不能只看文本相似度，因为很多时候答案组织不同，但证据链是否完整才是关键

你必须掌握的核心指标：
- Completion Rate：是否真正完成任务
- Top-5 Hit：检索质量是否提升
- 平均检索次数 / 无效检索步数：策略是否更有效率
- API 成本：系统是否具备落地价值
- 人工评测或关键点覆盖：答案是否真的可靠

你必须能解释结果：
- 68% -> 79% 说明整体任务完成能力提升
- 无效检索步数下降 33% 说明决策层减少了绕路
- Top-5 到 82% 说明检索和精排有效
- 成本下降 27% 说明记忆和检索策略带来了实际收益

面试官常问：
- 你的训练数据是怎么来的
- 怎么防止数据泄露
- 为什么不能只看 ROUGE
- 怎么证明 RL 真有用
- 为什么要看 Top-5 而不是只看最终答案

容易失分的点：
- 只会背数字
- 不知道指标背后的业务意义
- 说不清为什么这些指标能证明有效

## 9. 业务落地与产品化类问题
这是很多人容易忽略的一类，但面试官很爱问，因为它能区分“会做实验”和“理解真实系统”的人。

你要掌握的核心：
- 真实用户为什么愿意用这个系统
- 这套系统在业务上带来的价值是什么
- 成本、延迟、准确性三者怎么平衡
- 什么时候要拒答或延迟回答
- 什么情况下必须引用来源或保证可追溯

你必须理解的落地点：
- 科研问答不是只要“回答像样”，而是要可信、可解释、可回溯
- 用户可能不是只要一句答案，而是要对比、统计、引用、可视化
- 因此系统必须支持证据链、来源质量控制、必要时代码分析

你必须理解的产品决策：
- 为什么不是所有问题都调用代码
- 为什么不是所有问题都深度检索到全文
- 为什么有时宁可多检索一步，也不能贸然生成
- 为什么成本下降 27% 很重要，因为科研型系统如果每次都深搜全文，几乎很难落地

面试官常问：
- 这个系统的真实落地价值是什么
- 如果用户问的是低价值问题，还值得跑完整链路吗
- 如何平衡准确率和响应成本
- 这个系统什么时候最有价值，什么时候不适合用

容易失分的点：
- 只会讲技术，不会讲用户价值
- 说不清“为什么这套系统值得做”
- 忽略成本和延迟问题

## 10. 工程稳定性与系统鲁棒性类问题
这一类是偏工程的，但很加分。

你要掌握的核心：
- MCP 的作用
- 状态机和结构化计划为什么重要
- 工具调用失败怎么办
- 检索为空、代码失败、证据冲突时怎么处理
- 为什么要有轨迹日志

你必须理解的逻辑：
- 结构化计划和状态机的价值，不只是“看起来高级”，而是让流程可解释、可回放、可控制
- 没有状态机，系统容易靠字符串和 prompt 松散拼接，行为不可控
- 没有轨迹日志，很难做 RL 数据回流、bad case 定位和策略分析

你必须掌握的异常场景：
- 检索为空
- 检索结果重复率高
- Validator 反复不给过
- replan 频繁触发
- 代码执行失败
- 来源冲突严重

面试官常问：
- 为什么要用状态机
- 工具调用失败怎么办
- 如果系统一直 replan 怎么处理
- 怎么做错误分析和 bad case 回流

容易失分的点：
- 只会讲 happy path
- 不会讲异常处理
- 不知道日志和轨迹为什么重要

## 11. 项目反思与开放问题类
这一类通常出现在后半程，是区分成熟度的关键。

你要掌握的核心：
- 当前系统最难的点是什么
- 当前系统最大的局限是什么
- 如果再做一次你会优先改什么
- 哪些部分是最容易失真的

你建议重点准备的反思方向：
- Validator 评分虽然能显著提升可控性，但规则和权重本身仍然需要持续调优
- Memory 带来成本优势，但也引入了污染和过期问题
- RL 能优化决策，但 reward 设计和训练稳定性本身是高门槛问题
- 科研问答很多时候没有单一标准答案，所以评测本身也是难点
- 一些问题天然不适合自动化深答，比如证据本身强冲突、或者要求极高的时效和准确性

面试官常问：
- 这个项目最大的挑战是什么
- 你觉得最容易出问题的模块是哪个
- 如果继续做下去你会优先改哪里
- 你觉得这套系统离真正落地还差什么

容易失分的点：
- 只会说“继续优化模型”
- 不会讲真实局限
- 一反思就变成空泛套话

## 14. 一个更适合你现在阶段的学习方法
你现在不要一上来就背答案，先按类别做“问题树”。

比如你学“Validator”时，不是只学公式，而是顺着这条线学：
- 业务上为什么需要 Validate
- 为什么不能 bool
- 为什么是这些维度
- 为什么 coverage 最重要
- 为什么阈值这样定
- 如果分数高但答案还是错，问题可能在哪
- 如果冲突很多怎么办
- 如果继续搜但信息增益一直很低怎么办

你学“Reward”时，也不是只背权重，而是顺着这条线学：
- 为什么不能只看终局质量
- 为什么要过程奖励
- 为什么是两阶段
- 为什么第一阶段 sufficiency 更高
- 为什么第二阶段 quality 更高
- reward hacking 怎么出现
- 怎么监控训练是否学偏
- 什么时候停训

这种学法，后面面试官越追问，你越不容易崩。
