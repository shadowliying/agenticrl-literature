# 数据集（用于项目问答与评估说明）

## 1. 数据集总览

本项目的数据分为两大类，严格隔离，避免数据泄露：

- RL 训练数据：2500 条（用于训练决策策略）
- 系统评估数据：800 条（独立测试集，仅用于评估）

核心评价指标与数据紧密关联：

- 任务完成率
- Top-5 命中率
- API 成本
- 响应时间

## 2. 数据分成哪几个部分

### 2.1 RL 训练相关数据（2500 条）

- 训练集：2000 条
- 验证集：300 条
- RL 测试集：200 条

用途说明：

- 训练集用于策略学习
- 验证集用于调参与早停
- RL 测试集用于离线验证策略效果

### 2.2 系统评估数据（800 条）

- 独立测试集，不参与任何训练
- 用于评估整个系统的端到端效果
- 与 RL 训练数据完全分开
- 不是从 RL 训练数据里随机切出来的，而是单独构建

## 3. 数据从哪里来（来源与比例）

本项目的数据主要来自三条路径：

- 数据来源一：LLM 生成（约 60%）
  说明：通过 DeepSeek API 生成科研检索问题，覆盖 NLP/CV、事实问答、对比分析、代码请求等类型。

- 数据来源二：Query 改写增强（约 25%）
  说明：对已有问题进行多样化改写，提高表达多样性和语义覆盖。

- 数据来源三：公开数据集（约 15%）
  说明：从 SciQ、PubMedQA、QASPER、ScholarQA 等数据集中筛选与适配。

更具体一点的口径可以这样讲：

- RL 训练数据总量：`2500`
  - 训练集：`2000`
  - 验证集：`300`
  - 测试集：`200`
- 公开数据集适配样本约 `375` 条，占 RL 数据约 `15%`
  - `SciQ` 约 `90`
  - `PubMedQA` 约 `110`
  - `QASPER` 约 `95`
  - `ScholarQA` 或同类学术问答样本约 `80`

- 系统独立评测集总量：`800`
  - 内部人工设计科研 query：`320`
  - 公开数据集 held-out 适配样本：`260`
  - 历史 bad case 类型重写的高难样本：`220`

## 4. 数据是怎么得来的（构建流程）

### 4.1 LLM 生成流程

- 设计 Prompt，要求覆盖不同类型与难度
- 生成后进行去重与格式校验
- 过滤过短、无问号或非问题文本

### 4.2 Query 改写流程

- 对已有问题做多版本改写
- 强调语义一致、表达多样
- 用于扩充训练分布

### 4.3 公开数据集适配

- 选择学术问答类数据集
- 转换为本项目统一格式
- 过滤过于简单或不相关样本

更完整的适配流程可以讲成三步：

1. 筛选  
   去掉过于简单、无法形成多步检索闭环、或者和科研文献检索场景不匹配的样本

2. 改写  
   把原始 `question -> answer` 形式改成更贴近项目风格的 query，例如补充比较对象、原因分析、实验支持、时间范围等约束

3. 轨迹化  
   不直接把公开数据集当成终局 QA 样本，而是用 baseline policy 跑成：
   - initial plan
   - required_slots
   - trajectory
   - validator outputs
   - reward

一句话版：

> 公开数据集的作用是补任务多样性，不是直接替代自有轨迹数据。

### 4.4 800 条系统评估数据是怎么构建的

这 800 条不是训练集切分，而是单独构建的端到端评测集，主要分三部分：

1. 内部人工设计高价值科研 query（`320` 条）
   覆盖：
   - 方法比较
   - 原因分析
   - 实验支持
   - 趋势统计
   - 多轮追问

2. 公开数据集 held-out 适配样本（`260` 条）
   来源仍然是：
   - `PubMedQA`
   - `QASPER`
   - `ScholarQA`
   - 少量 `SciQ`
   但样本实例、问题表达和训练侧严格隔离

3. 历史 bad case 类型重写后的高难样本（`220` 条）
   重点覆盖：
   - 多轮指代 / 省略
   - 来源冲突
   - 摘要不足、必须读全文
   - query 过长、约束较多

## 5. 数据标注格式（核心示例）

### 5.1 RL 训练数据格式（轨迹数据）

```json
{
  "session_id": "train_001",
  "query": "介绍一下 BERT 的预训练方法",
  "trajectory": [
    {
      "step": 1,
      "state": {
        "query": "介绍一下 BERT 的预训练方法",
        "search_count": 0,
        "result_quality": "无",
        "cache_hit": false
      },
      "action": "OptimizerAgent",
      "action_output": "生成搜索词：BERT pre-training MLM NSP",
      "reward": 0.0
    }
  ],
  "total_reward": 1.0,
  "total_steps": 3,
  "success": true
}
```

要点说明：

- 轨迹由系统自动记录，不需要人工逐步标注
- action 是 Orchestrator/Worker 触发的动作
- reward 用于策略训练

### 5.2 系统评估数据格式

```json
{
  "id": "eval_001",
  "source_group": "internal_curated",
  "query": "Transformer 的自注意力机制如何计算？",
  "query_type": "技术原理",
  "difficulty": "中等",
  "reference_answer": "通过 Q/K/V 计算注意力权重...",
  "key_points": ["Q/K/V 矩阵", "缩放点积", "softmax", "多头"],
  "expected_sources": ["Attention Is All You Need", "arxiv.org/abs/1706.03762"],
  "must_have_behaviors": ["优先摘要检索", "证据不足时不能直接 synthesis"]
}
```

要点说明：

- key_points 用于自动评估覆盖率
- expected_sources 用于检索质量评估
- source_group 用于区分评测集来源
- must_have_behaviors 用于高价值样本的过程约束评测

## 6. 数据质量控制（避免噪声与泄露）

- 去重与长度过滤：过短、过长、重复的问题直接剔除
- 格式过滤：非疑问句、非科研相关问题剔除
- 抽样人工检查：每 100 条抽检 10 条
- 多样性检测：用 BGE 向量聚类，检查类别覆盖
- 训练/评估严格分离：避免“看过测试集”

另外还会做两类更细的控制：

- 公开数据集适配去泄露
  - 训练侧和评测侧不用同一个原始样本 ID
  - 评测侧不用训练侧的表达改写版本

- 复杂 query 占比控制
  - 不让定义题占比过高
  - 保证比较、原因、实验支持、多轮问题都有足够覆盖

## 7. 必须掌握的知识点（面试常问）

- 训练数据和评估数据必须完全分开
- 评估指标要多维度，不能只看准确率
- 必须有基线对比与消融实验
- 轨迹数据可以通过系统日志自动收集
- 数据质量控制要有“过滤 + 抽检 + 多样性检查”组合
- 800 条评测集应该单独构建，而不是从训练集随便切分
- 公开数据集进入 RL 前要先做筛选、改写和轨迹化

## 9. 面试官可能会问的问题（含参考回答）

Q1：你的数据是怎么来的？
A：RL 数据里 60% 由 baseline rollout 和 LLM 生成后筛选得到，25% 由问题改写扩增，15% 来自公开数据集适配样本；评测集 800 条是单独构建的，不参与训练。

Q2：训练数据和评估数据怎么区分？
A：严格隔离。RL 训练 2500 条，评估 800 条完全独立，避免数据泄露。

Q3：轨迹数据是怎么标注的？
A：不人工标注，而是系统运行时自动记录状态、动作、奖励，形成轨迹样本。

Q4：如何保证 LLM 生成的数据质量？
A：做长度过滤、格式过滤、去重，并通过人工抽检和语义聚类检查多样性。

Q5：公开数据集怎么用到项目里？
A：先筛掉和科研检索闭环不匹配的样本，再改写成统一 query 风格，最后跑成轨迹格式再混入训练集，不是直接拿原始 QA 样本去训。

Q5.1：那 800 条评测集从哪里来？
A：不是从训练集切的，而是三部分单独构建：320 条内部人工设计科研 query、260 条公开数据集 held-out 适配样本、220 条历史 bad case 类型重写的高难样本。

Q6：评估时最重要的指标有哪些？
A：主看任务完成率、关键点覆盖率、LLM-as-Judge 和人工抽样；辅助看 Top-5、MRR、检索步数、replan 频率、响应时间和 API 成本。

Q7：如果面试官问你遇到的数据问题？
A：主要是 LLM 生成噪声、难度分布不均、不同来源风格差异大。解决方式是过滤、改写增强和聚类检查。

Q8：怎么证明 RL 比规则系统更好？
A：用规则基线做对比，并做消融实验，展示完成率和检索步数的提升。

Q9：如果评估分数很高但线上效果不好怎么办？
A：考虑分布偏移和测试集泄露，补充线上真实问题，增加人工评估与 A/B 测试。

Q10：你如何保证评估公平和可复现？
A：固定随机种子、记录数据版本、保存训练与评估配置，确保可复现实验。
