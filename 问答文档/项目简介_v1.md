# 项目简介（详细版）

> 说明：由于仓库规范要求新增文件以 `_v1` 结尾，本文件实际路径为 `问答文档/项目简介_v1.md`。

---

**1. 项目目标与定位**

本项目是一个面向科研文献检索的多 Agent 问答系统。核心目标是把“检索—验证—合成”流程结构化、可解释、可控，并用强化学习优化决策策略。系统以结构化 Plan 和状态机作为执行骨架，结合检索工具、验证规则与代码执行工具，完成复杂问答任务。

---

**2. 总体架构（模块视角）**

系统按“3 模块 + 记忆层 + 工具层”来理解最清晰：

1. 决策模块（Orchestrator）
- 负责生成结构化 Plan（见 `src/workflow/plan_schema_v1.py`）
- 是强化学习训练主体（SFT → GRPO）
- 决定“该做什么”，不直接控制执行跳转

2. 检索验证模块（Retrieval + Validate）
- Retrieval：检索/召回/精排，输出证据片段
- Validate：基于规则评估证据充分性，输出结构化评分
- 记忆与缓存（Memory Layer）在检索前后协助降本增效

3. 生成模块（Synthesis）
- 在证据充分时生成答案
- 需要计算/图表时调用代码执行工具

**Memory Layer（能力层）**
- 不作为独立 Agent
- 负责 Recall/Write，提升跨轮次稳定性

**工具层（MCP）**
- 统一工具调用接口
- 包含检索、网页解析、代码执行等工具

**4. 结构化 Plan（PlanSchema）**

Plan 是系统的“执行蓝图”，由 Orchestrator 输出。

**Plan 核心字段**
- `goal`：总体目标
- `steps[]`：步骤列表，每步包含 `step_id / action / inputs / outputs / success_rules / rollback_rules / metadata`
- `constraints`：约束
- `assumptions`：假设
- `created_at`：生成时间
- `version`：版本号

**Plan 示例（节选）**
```json
{
  "step_id": "S2",
  "action": "VALIDATE",
  "success_rules": [
    {"type": "sufficiency_score_ge", "value": 0.75}
  ],
  "rollback_rules": [
    {"type": "sufficiency_score_lt", "value": 0.60}
  ],
  "metadata": {
    "required_slots": ["time", "number", "comparison"],
    "min_snippets": 2,
    "sufficiency_threshold": 0.75,
    "replan_threshold": 0.60
  }
}
```

**中文解释**
- Plan 负责“规定规则”，例如必须覆盖哪些槽位、最少证据数、充分性阈值。
- Plan 不负责判断结果，判断交给 Validate。

---

**5. StateMachine 判断逻辑**

代码位置：`src/workflow/state_machine_v1.py`

核心规则（固定）：
- `sufficiency_score >= sufficiency_threshold` → 进入 `SYNTHESIS`
- `sufficiency_score < replan_threshold` → 进入 `REPLAN`
- 其他情况 → 回到 `RETRIEVE`

状态机只负责“下一步去哪”，不理解证据内容。

---

**6. Validate 规则设计（规则优先）**

代码位置：`src/agents/validator_agent_v1.py`

**输入**
- `evidence_snippets`：检索证据
- `plan_rules`：Plan 规则
- `context`：历史片段、冲突、来源评分、时效评分等

**关键规则**
1. 槽位覆盖（coverage）
- 根据 Plan 的 `required_slots` 检查证据中是否覆盖

2. 证据数量（min_snippets）
- 证据数不足直接判不足

3. 相关性、支持强度、一致性、信息增益
- 全部使用规则/统计计算

**综合评分公式**
```
sufficiency_score =
  0.35 * coverage
+ 0.20 * relevance
+ 0.15 * support_strength
+ 0.10 * consistency
+ 0.10 * source_quality
+ 0.05 * freshness
+ 0.05 * info_gain
```

**硬性门槛（触发直接不足）**
- 缺失关键槽位
- 冲突比例 > 0.4
- 证据数量 < min_snippets
- 高风险且来源质量不足
- 时间敏感且时效不足

**输出（结构化）**
- `sufficiency`（是否充分）
- `sufficiency_score`（评分）
- `missing_slots`（缺失槽位）
- `conflicts`（冲突列表）
- `suggested_action`（search_more / replan / synthesize）

**7. Memory Layer（能力层）**

代码位置：`src/memory/memory_layer_v1.py`

**定位**
- Memory 不是独立 Agent，而是“检索验证模块”的能力层。
- 作用是降低重复检索成本，并让后续问题能复用历史证据或结论。

**结构**
- `MemoryItem`：记忆条目，字段包含 `content / source / timestamp / tags / metadata`。
- `short_term`：短期记忆（当前会话/当前任务）。
- `long_term`：长期记忆（跨任务复用）。

**输入**
- `recall(query, top_k, scope)`：输入查询文本与范围（short/long/all）。
- `write(content, scope, source, tags, metadata)`：输入要写入的内容与标签。

**输出**
- `recall` 输出匹配的 `MemoryItem` 列表。
- `write` 输出写入的 `MemoryItem` 条目。

**规则（当前实现）**
- 回忆采用关键词匹配（query 在 content 中命中即入选）。
- 超过短期容量会淘汰最早条目。

**使用时机**
- 检索前做 `recall`，把命中的内容写入 `context["memory_recall"]`，作为检索补充线索。
- 答案生成后做 `write`，把最终结论写入长期记忆。

**与检索模块关系**
- Memory 的 recall 结果等价于“低成本召回”，可减少无效搜索。
- 记忆与缓存被视为检索流程的一部分，而不是独立步骤。

---

**8. MCP 工具层（调用范围）**

MCP 用于标准化工具调用，常见工具包括：
1. 检索工具（Search / Web）
2. 网页解析工具（正文抽取）
3. 代码执行工具（Python 计算/图表）

原则：MCP 负责“调用工具”，不参与判断逻辑。

1. SFT（LoRA）

2. GRPO（LoRA）

**10. 完整流程（输入输出全览）**

1. 用户问题 → Orchestrator 生成 Plan
- 输入：`question`
- 输出：`Plan`

2. 状态机驱动 → 进入检索
- 输入：`sufficiency_score / thresholds / step_count`
- 输出：`next_state`

3. 检索模块
- 输入：`query`
- 输出：`evidence_snippets / raw_docs`

4. Validate 规则评分
- 输入：`evidence_snippets + plan_rules`
- 输出：`sufficiency_score / missing_slots / suggested_action`

5. 状态机判断
- 输出：RETRIEVE / REPLAN / SYNTHESIS

6. 合成模块
- 输入：`evidence_snippets`
- 输出：`final_answer / need_code`

7. 代码执行（若 need_code）
- 输出：表格/图表/计算结果

8. 输出答案 + 写回记忆

---

**11. 结论（面试口径）**

一句话：Plan 定规则，Validate 验规则，State 决定下一步；Orchestrator 通过 SFT→GRPO 学会更优决策，MCP 统一工具调用，系统流程可解释、可控。
