# 记忆与上下文

## 1. 这部分在系统里的定位

在这个科研问答 Agent 系统里，Memory 和 Context 不是一回事，但它们经常一起出现。

- Context：是当前这一次模型调用时，真正送进大模型输入窗口里的内容。
- Memory：是系统在多轮任务、多次检索、多次执行之后保留下来的可复用信息。

一句话区分：

- Context 解决“这一次调用模型时，它眼前看到了什么”。
- Memory 解决“系统以前知道了什么，这次要不要拿出来用”。

所以，Memory 更像一个外部存储层，Context 更像一次调用时临时拼好的工作区。

---

## 2. 为什么这个系统一定要有 Memory

如果没有 Memory，这个系统会有几个明显问题：

- 同一个会话里反复检索同样的信息，成本高。
- 前面已经确认过的实体、术语、论文信息，后面还要重新查。
- 多轮问题之间没有连续性，系统每次都像“失忆”一样重新开始。
- 一些长任务里，模型上下文窗口放不下所有历史证据，必须把重要信息外存。

所以 Memory 的作用不是“让系统变聪明”这么抽象，而是解决几个很实际的问题：

- 降低重复检索成本
- 维持多轮一致性
- 缓解上下文窗口限制
- 给后续规划和检索提供先验线索

---

## 3. Context 是什么

### 3.1 基本定义

Context 指的是某一次调用大模型时，拼接到 Prompt 里的全部输入信息。

在这个项目里，一次典型的 Context 可能包括：

- 用户原始问题 `question`
- 当前结构化 Plan
- 当前步骤编号 `step_count`
- 历史检索摘要
- Memory recall 的结果
- 当前证据片段 `evidence_snippets`
- Validate 输出的结构化结果
- 阈值、槽位要求、任务约束

所以 Context 是“当前工作状态的快照”。

### 3.2 Context 的特点

- 它是临时的，不一定会永久保存。
- 它是面向当前这一步推理的。
- 它受到模型上下文窗口限制。
- 它可以来自多个来源：用户输入、Plan、Memory、检索结果、Validate 结果。

### 3.3 Context 的核心问题

Context 设计不好，系统就会出问题。常见问题有：

- 塞太多内容，导致上下文过长，成本高、噪声大。
- 塞太少内容，模型缺信息，容易乱答。
- 没有区分“长期有用信息”和“这一步必须看的信息”。
- 历史内容没压缩，导致模型注意力被无关信息占满。

---

## 4. Memory 是什么

### 4.1 基本定义

Memory 是系统外部保存的信息层。它不等于模型参数，也不等于一次 Prompt 的输入。

它的作用是：

- 把过去任务中有复用价值的信息保存下来
- 在新的步骤开始前，按需 recall 回来
- 把 recall 回来的结果拼入当前 context

### 4.2 在这个项目里的定位

这个项目里，Memory 不是一个单独的 MemoryAgent，而是一个能力层。

这是一个重要设计点：

- Orchestrator 决定做什么
- Retrieval 负责去外部找信息
- Validate 负责判断信息是否足够
- Memory 负责“存”和“取”历史信息

也就是说，Memory 更像基础设施，不像决策 Agent。

这样设计的原因很直接：

- Memory 不负责高层决策
- 它的职责清晰，就是 recall / write
- 如果强行做成独立 Agent，职责会和 Orchestrator、Retrieval 重叠，系统会更混乱

所以你在面试里可以直接说：

> 我没有把 Memory 单独做成一个 Agent，而是把它设计成检索系统旁边的能力层，因为它本质上不做策略决策，只做记忆读写与辅助召回。

## 5. 当前代码里的 Memory 实现

代码位置：`src/memory/memory_layer_v1.py`

当前实现是一个轻量版本，核心对象有两个：

### 5.1 `MemoryItem`

表示一条记忆，字段包括：

- `content`：记忆内容
- `source`：来源
- `timestamp`：时间戳
- `tags`：标签
- `metadata`：额外信息

这说明 Memory 里存的不是“神秘向量”，而是结构化条目。

### 5.2 `MemoryLayer`

当前有两层：

- `short_term`
- `long_term`

支持的操作主要有：

- `write()`：写入短期或长期记忆
- `recall()`：根据 query 回忆相关记忆
- `clear_short()`：清空短期
- `clear_long()`：清空长期

### 5.3 当前 recall 规则

当前版本用的是很简单的关键词匹配：

- 如果 query 出现在 memory content 中，就认为相关
- 相关条目按得分排序，返回 top_k

这说明当前 `memory_layer_v1.py` 更像一个“可运行的原型实现”，重点在于把接口和流程打通，不是最终的高性能版本。

## 6. 完整系统里更合理的 Memory 结构

如果从系统设计上讲，这个项目最合理的是三层记忆，而不是只分 short/long 两层。

### 6.1 第一层：短期会话记忆

存什么：

- 当前会话中的历史问题
- 当前任务已确认的中间结论
- 最近几轮检索摘要
- 当前任务中的实体指代关系

特点：

- 生命周期短
- 只服务当前任务或当前用户会话
- 容量受控，必要时淘汰旧条目

### 6.2 第二层：语义缓存

存什么：

- 过去检索过的问题与结果映射
- 常见问题的检索证据摘要
- 常见 Prompt 的中间产物

特点：

- 目标是降本增效
- 相似 query 可以直接复用历史结果
- 更像“检索缓存”，不是知识记忆本身

### 6.3 第三层：实体/知识记忆

存什么：

- 论文名、作者、模型名、年份、术语定义
- 已确认的实体关系
- 已验证过的长期稳定知识点

特点：

- 生命周期长
- 服务跨任务复用
- 更适合做结构化存储

所以你可以把完整系统的 Memory 概括成：

- 短期会话记忆：解决当前任务连续性
- 语义缓存：解决重复检索成本
- 实体知识记忆：解决跨任务知识复用

## 7. Memory 和 Context 的关系

这是面试里最容易被问到也最容易讲乱的地方。

正确理解是：

1. Memory 先存储在外部
2. 当前步骤开始前，系统根据 query 去 recall
3. recall 到的结果不会直接代替推理
4. recall 的结果会被压缩、筛选后拼进当前 Context
5. 大模型真正看到的是 Context，而不是整个 Memory 库

所以：

- Memory 是仓库
- Context 是装配好的工作台

### 7.1 一个具体例子

用户问题：

`请比较 BERT 和 RoBERTa 的预训练差异，并说明 RoBERTa 为什么去掉 NSP。`

这时系统会做几件事：

1. 用问题去 recall memory
2. 找到过去关于 “BERT pretraining / NSP / RoBERTa” 的历史条目
3. 把相关条目摘成简短摘要
4. 拼进当前 Context
5. 再进入 Retrieval 和 Validate

最终模型输入的可能是：

- question
- 当前 plan
- memory summary: “BERT 原始任务包含 MLM+NSP；RoBERTa 去掉 NSP，强化数据与训练策略”
- 当前检索证据
- 当前 validate 结果

这里你要注意：

- 进入大模型的是 memory summary，不一定是完整 memory item
- 这就是 Memory 到 Context 的转换过程

## 8. Memory 在完整工作流里出现在哪些步骤

### Step 0：用户问题进入系统

输入：

- `question`

输出：

- 初始 context

### Step 1：Orchestrator 生成 Plan

输入：

- `question`
- 初始 context

输出：

- `plan`

### Step 2：Memory Recall

输入：

- 当前 query 或 question
- recall 范围（short / long / all）
- top_k

输出：

- `memory_items`
- `memory_summary`

这一阶段的意义：

- 在正式检索前先看看历史里有没有能直接复用的线索
- 给检索 query 改写、实体消歧、槽位判断提供先验

### Step 3：Retrieval

输入：

- 原始 query
- plan 里的当前步骤要求
- memory_summary

输出：

- `raw_docs`
- `evidence_snippets`

### Step 4：Validate

输入：

- `evidence_snippets`
- `plan_rules`
- `memory_summary`
- 历史 snippets（可选）

输出：

- `sufficiency_score`
- `missing_slots`
- `conflicts`
- `suggested_action`

### Step 5：StateMachine 决策下一步

输入：

- validate 输出
- 当前阈值
- step_count

输出：

- `RETRIEVE` / `REPLAN` / `SYNTHESIZE`

### Step 6：Synthesis

输入：

- 最终证据
- memory 中已确认的背景信息

输出：

- `final_answer`

### Step 7：Memory Write

输入：

- 最终结论
- 高价值证据摘要
- 实体关系
- 来源信息

输出：

- 新增 memory item

这一阶段的意义：

- 为后续相似问题保留可复用信息
- 缩短下一次同类问题的检索路径

## 9. 这个系统里应该写入什么，不该写入什么

### 9.1 应该写入的内容

- 已被验证为可靠的结论摘要
- 高价值证据片段摘要
- 实体与别名映射
- 当前任务中的用户偏好
- 高复用术语定义

### 9.2 不应该直接写入的内容

- 未验证的检索原文
- 冲突中尚未判定真假的信息
- 一次性噪声信息
- 超长原始网页全文
- 纯粹为了当前一步存在的临时推理过程

原则很简单：

- Memory 里应该存“有复用价值且相对可信的信息”
- Context 里才放“当前一步需要处理的临时信息”

---

## 10. Memory 的写入策略

Memory 不能什么都写，不然很快就变成噪声堆积。

比较合理的写入规则是：

### 10.1 写入时机

- Validate 判定证据基本充分后
- Synthesis 生成最终答案后
- 一次任务完成时做总结性写入

### 10.2 写入条件

- 来源质量达标
- 证据冲突已解决或可接受
- 内容具备后续复用价值
- 不是简单重复已有 memory

### 10.3 写入内容形式

不要直接把长文本原封不动塞进去。

更合理的是写成结构化摘要，例如：

```json
{
  "content": "RoBERTa 在预训练阶段移除了 NSP，主要原因是该任务对性能提升有限，训练收益不明显。",
  "source": "paper:RoBERTa",
  "tags": ["pretraining", "roberta", "nsp"],
  "metadata": {
    "entity": "RoBERTa",
    "source_quality": 0.95,
    "verified": true
  }
}
```

## 11. Memory 的 recall 策略

当前代码用的是关键词匹配，但完整系统里更合理的是分层 recall。

### 11.1 第一层：精确匹配

适合：

- 术语
- 实体名
- 论文名
- 明确关键词

### 11.2 第二层：语义匹配

适合：

- 改写问题
- 同义表达
- 不同说法但同一个语义目标

### 11.3 第三层：标签过滤

适合：

- 按领域、任务类型、来源类型筛选
- 避免把不相关记忆召回进来

一个更合理的 recall 流程是：

1. 先按标签筛大类
2. 再按实体或关键词做精确筛选
3. 最后按语义相似度排序
4. 只返回少量高价值摘要进入 context

## 12. Context 应该怎么组装

你这个系统里，Context 不能无脑堆内容，而是要有优先级。

推荐的组装顺序：

1. 用户问题
2. 当前计划中的目标与当前步骤
3. 当前必须满足的槽位或约束
4. Memory recall 摘要
5. 当前检索证据
6. 历史 validate 结果摘要
7. 必要的用户偏好或历史背景

不推荐把下面这些直接大段拼进去：

- 所有历史对话全文
- 所有检索原文
- 所有 memory item 原文
- 所有失败中间步骤

因为这些内容非常容易把 Context 冲爆，而且噪声高。

## 13. Context Overflow 怎么处理

这是系统设计里的实际问题。

当历史越来越长时，不能一直把全部内容放进 Prompt。常见处理方式有：

### 13.1 摘要压缩

把长历史压成摘要，只保留：

- 已确认结论
- 仍未解决的问题
- 当前最相关的实体与约束

### 13.2 滚动窗口

只保留最近几步最相关的上下文，较早历史转入 memory。

### 13.3 分层保留

- 当前步骤必需信息：直接保留在 context
- 历史背景：写入 memory，按需 recall

### 13.4 强制裁剪

如果 context 超长：

- 优先裁掉低价值历史检索片段
- 保留 question、plan、slots、high-score evidence、validate output

## 14. Memory 和 RAG / 检索的关系

Memory 不是要替代 Retrieval。

它们关系是：

- Retrieval：去外部世界找新信息
- Memory：复用系统以前已经拿到并整理过的信息

所以这两者不是二选一，而是配合关系。

你可以把它理解成：

- 检索负责“开源”
- 记忆负责“节流”

在系统中通常是：

- 检索前先 recall memory，看看能不能少搜一点
- 检索后再写回 memory，让下次更快

---

## 15. Memory 和缓存的关系

这两个也经常被混。

### 15.1 缓存

更强调：

- 同样输入直接复用旧输出
- 目标是节省算力和时间
- 常见是 query -> result 的映射

### 15.2 Memory

更强调：

- 复用有意义的信息，而不只是复用结果
- 可以服务多轮推理和多步任务
- 内容往往更抽象、更结构化

所以你可以说：

- 缓存是 Memory 的一部分思路，但不等于完整的 Memory
- 缓存偏工程优化，Memory 偏系统认知连续性

## 16. 这个项目里最合适的 Memory 面试口径

你可以这样讲：

> 这个系统里我没有把 Memory 做成独立 Agent，而是做成检索系统旁边的能力层。它主要承担短期会话记忆、语义缓存和实体知识记忆三类功能。执行时先根据当前 query 从 memory recall 相关摘要，再把这些摘要拼入当前 context，辅助检索和验证；任务完成后，再把高价值且经过验证的信息写回 memory，用来降低后续重复检索成本，并维持多轮问答的一致性。

这段基本可以直接用于面试回答。

## 17. 基础知识点整理

这一部分是你必须掌握的基础概念。

### 17.1 什么是短期记忆

- 面向当前会话或当前任务
- 生命周期短
- 存最近几轮的关键信息

### 17.2 什么是长期记忆

- 面向跨任务复用
- 生命周期长
- 存高复用、高置信度知识

### 17.3 什么是语义缓存

- 根据语义相似性复用旧结果
- 目标是减少重复检索和重复生成

### 17.4 什么是实体记忆

- 记录模型、论文、作者、术语等实体相关信息
- 便于后续实体消歧和关系延续

### 17.5 什么是上下文窗口

- 大模型一次调用时能看到的 token 范围
- 不是无限的
- Context 设计本质上是在有限窗口里做信息优先级排序

### 17.6 为什么不能只靠上下文，不做 memory

- 上下文窗口有限
- 多轮历史太长放不下
- 重复信息会浪费 token
- 没法很好支持跨任务复用

## 18. 常见设计风险

### 18.1 记忆污染

问题：

- 错误信息被写入 memory
- 后续任务不断复用错误内容

解决：

- 只在 validate 通过后写入
- 给 memory item 增加 `verified/source_quality/timestamp`
- 冲突信息不直接入长期记忆

### 18.2 记忆过时

问题：

- 某些知识具有时效性
- 很久以前的内容拿来直接用可能错误

解决：

- 给 memory 加时间戳
- time-sensitive 任务优先要求新证据
- recall 时加入 freshness 过滤

### 18.3 召回噪声

问题：

- recall 太宽，把不相关历史拉进 context

解决：

- 限制 top_k
- 先做标签过滤
- 只注入摘要，不注入全文

### 18.4 上下文过长

问题：

- 什么都想带进去，结果注意力稀释

解决：

- 摘要压缩
- 分层保留
- 严格控制优先级

## 19. 面试官常问问题与回答

### Q1：你这个系统里的 Memory 是什么？

答：

Memory 是系统的外部记忆层，不是大模型参数的一部分，也不是一次 Prompt 本身。它负责保存历史任务中有复用价值的信息，在新的步骤开始前 recall 相关内容，并把 recall 结果拼入当前 context，辅助检索、验证和生成。

### Q2：Memory 和 Context 的区别是什么？

答：

Context 是当前这一次模型调用真正看到的输入内容，Memory 是系统外部保存的信息仓库。Memory 通过 recall 进入 context，但不等于 context 本身。可以理解成 Memory 是仓库，Context 是工作台。

### Q3：为什么不把 Memory 做成一个独立 Agent？

答：

因为它本质上不做策略决策，只做存取和辅助召回。如果做成独立 Agent，会和 Orchestrator、Retrieval 的职责发生重叠，系统会更复杂。把它做成能力层更合理。

### Q4：你们的 Memory 里存什么？

答：

主要存三类：当前会话中的关键中间结论，历史 query 的语义缓存，以及经过验证的实体或知识摘要。不会直接把大量未验证网页原文塞进 memory。

### Q5：什么信息会写入长期记忆？

答：

只有高复用、高置信度、经过 validate 基本确认的信息才会写入长期记忆，比如术语定义、论文信息、实体关系、稳定结论摘要。

### Q6：Recall 是怎么做的？

答：

当前代码里是关键词匹配的轻量实现，用于先跑通流程。更完整的版本会采用标签过滤 + 精确匹配 + 语义相似度排序，只返回少量高价值摘要进入 context。

### Q7：Memory 会不会引入错误传播？

答：

会，所以必须控制写入门槛。错误信息一旦被长期记住，后续就可能不断复用。解决方法是只在信息经过验证后写入，并且存来源质量、时间戳和验证标志。

### Q8：为什么不能只用 RAG，不做 Memory？

答：

因为 RAG 每次都从外部重新找信息，无法很好利用历史任务中已经确认过的内容。Memory 的价值在于复用历史高价值信息，降低重复检索成本，并保持多轮一致性。

### Q9：怎么处理上下文窗口不够的问题？

答：

不能把所有历史全文塞进 Prompt。做法是把历史信息摘要化，把真正高价值内容写入 memory，需要时再 recall 摘要进入当前 context，同时通过滚动窗口和强制裁剪控制长度。

### Q10：你如何判断一个 memory item 该不该被写入？

答：

我看四点：是否经过验证、是否有复用价值、来源是否可靠、是否只是已有内容的重复。满足这些条件才会写入，尤其长期记忆更严格。

### Q11：Memory 在这个系统里提升最大的是什么？

答：

提升最大的不是“答案瞬间更准”，而是三件事：减少重复检索、改善多轮一致性、降低 token 和 API 成本。

### Q12：当前代码的 Memory 是否已经是最终形态？

答：

不是。当前 `memory_layer_v1.py` 是轻量原型，重点是把 write/recall 接口和流程打通。完整系统会扩展为三层记忆，并加入更强的 recall 与压缩策略。

## 20. 一段可以直接背的总结

你可以这样总结这部分：

> 在这个系统里，Context 是一次模型调用时真正看到的信息，Memory 是系统外部保存的可复用历史信息。执行流程上，系统会先根据当前 query 从 memory recall 相关摘要，再把这些摘要和 plan、evidence、validate 结果一起拼进当前 context，供模型完成当前步骤推理。任务完成后，再把高价值、经过验证的结论写回 memory。这样做的核心价值是降低重复检索成本、维持多轮一致性，并缓解上下文窗口限制。Memory 我没有做成独立 Agent，而是作为检索系统旁边的能力层，因为它本质上只负责存取与辅助召回，不负责高层决策。
