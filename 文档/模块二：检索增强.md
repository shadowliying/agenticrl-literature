## 第一讲：RAG 基础概念

### 1.1 什么是 RAG？

**RAG = Retrieval-Augmented Generation**（检索增强生成）

```
普通 LLM：
问题 → LLM（只用训练时的知识）→ 回答
问题：知识截止日期、容易幻觉

RAG：
问题 → 检索相关文档 → 文档 + 问题一起给 LLM → 回答
优势：实时信息、有据可查、减少幻觉
```

**一句话**：先搜再答，让 LLM 带着"参考资料"回答问题。

---

### 1.2 为什么科研问答需要 RAG？

| 场景 | 不用RAG | 用RAG |
|------|---------|-------|
| "2024年阿里Q3营收" | LLM瞎编或说不知道 | 搜到真实数据再回答 |
| "最新的量子计算进展" | 只知道训练截止前的 | 能搜到最新论文/新闻 |
| "对比A和B公司财报" | 容易张冠李戴 | 分别搜到后准确对比 |

**核心价值**：让 LLM 从"凭记忆回答"变成"查资料回答"。

---

### 1.3 我们系统的 RAG 流程

```
┌─────────────────────────────────────────────────────────────────┐
│                      完整 RAG 流程                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  0. 缓存查询（Memory 模块）                                      │
│     关键词 → BGE 语义匹配 → 命中则跳过搜索                       │
│                                                                 │
│  1. 关键词生成（Orchestrator + Optimizer）                       │
│     问题 → 提取搜索关键词                                        │
│     ★ OrchestratorAgent 用 GRPO 微调的 Qwen2.5-7B               │
│     ★ OptimizerAgent 用 DeepSeek API                            │
│                                                                 │
│  2. 搜索执行（webSearch Tool）                                   │
│     关键词 → Bing/SerpAPI → 50条候选文档                         │
│     → 写入搜索缓存（下次相似查询可复用）                         │
│                                                                 │
│  3. 粗排（BGE-Reranker）                                        │
│     50条 → 相关性打分 → Top-20                                  │
│                                                                 │
│  4. 精排（SelectorAgent + DeepSeek API）                        │
│     Top-20 → LLM判断 → 8-10条                                   │
│                                                                 │
│  5. 充分性验证（SufficiencyValidatorAgent）                      │
│     摘要够吗？→ 不够则获取全文                                   │
│                                                                 │
│  6. 生成答案（AssistantAgent）                                   │
│     文档 + 问题 → 带引用的答案                                   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## 第二讲：两阶段检索架构（我们的核心设计）

### 2.1 完整流程图

```
问题："2024年中国GDP排名前5的城市"
        │
        ▼
┌─────────────────────────────────────┐
│ Stage 0: 缓存查询 (Memory)           │
│ ─────────────────────────────────── │
│ 技术：BGE 编码 + 余弦相似度           │
│ 逻辑：查询与已缓存关键词的相似度      │
│                                     │
│ if 相似度 > 0.85:                   │
│     命中缓存，直接返回结果           │
│     → 跳过 Stage 1，节省 API 成本   │
│ else:                               │
│     未命中，继续 Stage 1            │
└─────────────────────────────────────┘
        │ (未命中)
        ▼
┌─────────────────────────────────────┐
│ Stage 1: 召回 (Recall)               │
│ ─────────────────────────────────── │
│ 技术：Bing Search API / SerpAPI      │
│ 输入：搜索关键词                      │
│ 输出：50条候选文档                    │
│ 特点：快速、广泛召回                  │
│                                     │
│ 返回：                               │
│ [                                   │
│   {title: "2024城市GDP排名", ...},    │
│   {title: "中国经济增长分析", ...},    │
│   {title: "房价走势分析", ...},        │ ← 不相关，但被搜索引擎返回
│   ...                               │
│ ]                                   │
│                                     │
│ → 写入搜索缓存（供后续复用）          │
└─────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────┐
│ Stage 2: 精排 (Rerank)               │
│ ─────────────────────────────────── │
│ 步骤 2a: 用 BGE-Reranker 打分       │
│ 技术：BGE-Reranker-base (Cross-Encoder)
│ 处理：50条 → 相关性打分 → 按分数排序  │
│ 输出：Top-20                         │
│                                     │
│ 步骤 2b: 用 LLM 最终确认             │
│ 技术：DeepSeek API (via SelectorAgent)
│ Prompt: 哪些文档确实与问题相关？     │
│ 输出：8-10 条                        │
│                                     │
└─────────────────────────────────────┘
        │
        ▼
最终：8-10条高质量相关文档
```

### 2.2 为什么两阶段？

**单独用任一种都有问题**：

```
❌ 只用搜索引擎：
   - 快速，但排序根据点击量/SEO，不一定准
   - "双十一购物攻略"可能排在"GDP数据"前面

❌ 只用 Reranker：
   - 准确，但处理50条需要1秒，处理100万条需要好几个小时
   - 不现实

✅ 两阶段 + 缓存（我们的方案）：
   - Stage 0：先查缓存，命中则直接返回（节省 27% API）
   - Stage 1：搜索引擎快速召回50条
   - Stage 2：用Reranker精确排序这50条
   
   结果：精度高 + 速度快 + 成本低
```

## 第三讲：搜索策略（关键词生成和搜索类型）

### 3.1 三种搜索类型及技术实现

OrchestratorAgent（GRPO 微调的 Qwen2.5-7B）会根据问题特点选择不同的搜索策略：

| 类型 | 场景 | 示例 | 技术实现 |
|------|------|------|---------|
| **单步单次** | 单一实体，简单查询 | "特斯拉CEO是谁" | 1个关键词 → webSearch（Bing） |
| **单步并发** | 多个独立实体 | "阿里、京东、拼多多Q3财报" | N个关键词 → 并发 N 个 webSearch |
| **多步多次** | 前后有依赖 | "先查政策，再分析影响" | 串行调用 webSearch，前结果影响后查询 |

> **关键**：选择哪种搜索策略，是 OrchestratorAgent 的决策之一，也是 RL 训练的目标。

### 3.2 关键词生成的工作流

```
OrchestratorAgent 的工作（GRPO 微调的 Qwen2.5-7B）：
┌────────────────────────────────────────────┐
│ 输入：用户问题                              │
│ "分析2024年中国电商公司Q3财报对比"          │
│                                            │
│ 【先读取 Memory - 搜索缓存】                │
│ 查询 "电商 财报 2024" → 未命中              │
│                                            │
│ LLM 决策：                                  │
│ "提取这个问题的搜索关键词，要求：           │
│  1. 包含核心实体                           │
│  2. 包含时间限定                           │
│  3. 包含数据类型"                          │
│                                            │
│ 输出：                                     │
│ keywords = [                               │
│   "2024年Q3 阿里巴巴 财报",                 │
│   "2024年Q3 京东 财报",                    │
│   "2024年Q3 拼多多 财报"                    │

└────────────────────────────────────────────┘
                  │
                  ▼
OptimizerAgent 的优化（DeepSeek API）：
┌────────────────────────────────────────────┐
│ 输入：上述关键词列表                        │
│                                            │
│ LLM 分析：                                  │
│ • 关键词里没有提到"抖音"，但抖音电商在中国重要
│ • 可以加"统计局"提高权威性                 │
│                                            │
│ 输出（优化后）：                           │
│ keywords = [                               │
│   "2024年Q3 阿里巴巴 财报 净利润",         │
│   "2024年Q3 京东 财报 净利润",             │
│   "2024年Q3 拼多多 财报 净利润",           │
│   "2024年Q3 抖音电商 字节 盈利"  ← 新增  │
│ ]                                          │
└────────────────────────────────────────────┘
```

### 3.3 搜索执行（webSearch Tool）

**技术选型**：

| 引擎 | 优点 | 缺点 | 价格 | 我们的选择 |
|------|------|------|------|----------|
| **Bing** | 便宜，微软生态 | 中文效果一般 | $3/1000次 | 默认使用 |
| **SerpAPI (Google)** | 效果最好 | 贵 | $50/5000次 | fallback |

**选择逻辑**：
```
问题来了 → 先用 Bing（省成本）
          → Bing 结果相关度 < 0.5 或字数 < 50
          → 切换到 SerpAPI 重试
```

**搜索后写入缓存**：
```python
# 搜索完成后，写入 Memory 的搜索缓存
cache_key = bge_encode(keyword)  # BGE 编码
cache_value = search_results      # 搜索结果
redis.set(cache_key, cache_value, ttl=3600)  # 缓存 1 小时

# 下次相似查询（相似度 > 0.85）可直接复用
# 节省 27% 的搜索 API 调用
```

**并发搜索的实现**：

```python
# 对于"单步并发"类型，用 asyncio 并行请求
import asyncio
import aiohttp

async def concurrent_search(keywords):
    tasks = [search_one(kw) for kw in keywords]
    results = await asyncio.gather(*tasks)
    return results

# 效果：
# - 5个关键词串行：5 × 2秒 = 10秒
# - 5个关键词并行：约2秒（等待最慢的那个）
```

**搜索结果的两层去重**：

```
第一层：URL 去重（精确匹配）
────────────────────────────
seen_urls = set()
for result in results:
    if result['url'] not in seen_urls:
        seen_urls.add(result['url'])
        unique_results.append(result)

第二层：内容去重（语义匹配）
────────────────────────────
方法：BGE embedding + 相似度计算
代码：
  emb1 = embedding_model.encode(doc1)
  emb2 = embedding_model.encode(doc2)
  similarity = cosine_similarity(emb1, emb2)
  if similarity > 0.95:
      视为重复，保留排名靠前的

原因：同一篇文章可能被多网站转载，URL 不同但内容相同
```

## 第四讲：BGE-Reranker（精排序的核心）

### 4.1 Cross-Encoder vs Bi-Encoder

这是**高频面试题**，一定要搞清楚：

| 维度 | Bi-Encoder | Cross-Encoder (BGE-Reranker) |
|------|-----------|------------------------------|
| **工作方式** | Query和Doc分别编码，然后计算相似度 | Query和Doc拼接成一个序列，一起编码 |
| **计算过程** | `sim = cos(encode(Q), encode(D))` | `score = model([Q] [D])` |
| **速度** | 快（可提前编码所有Doc） | 慢（每次都要新编码） |
| **精度** | 一般（缺少交互信息） | 高（能捕捉深层交互） |
| **用途** | 粗排/召回 | **精排/重排序** ← 我们用这个 |

**为什么 Cross-Encoder 更准？**

```
例子：
Query: "阿里净利润"
Doc: "阿里巴巴本季度盈利表现突出"

Bi-Encoder：
- 单独编码 "阿里净利润" → [v1]
- 单独编码 "阿里巴巴本季度盈利..." → [v2]
- "净利润" 和 "盈利" 的向量可能不太接近
- 可能漏掉这条相关文档

Cross-Encoder：
- 一起编码 "[CLS] 阿里净利润 [SEP] 阿里巴巴本季度盈利... [SEP]"
- 能看到整个上下文，理解 "净利润" = "盈利"
- 给出 0.9 的高分
```

### 4.2 BGE-Reranker 的具体使用

**模型信息**：
- 名称：`BAAI/bge-reranker-base`
- 来源：北京智源人工智能研究院
- 优点：中文效果好、速度可接受、开源免费
- 量化方式：INT8 量化后推理速度提升 2 倍

**代码实现**：

```python
from FlagEmbedding import FlagReranker

# 初始化模型
reranker = FlagReranker(
    'BAAI/bge-reranker-base',
    use_fp16=True,  # 用 FP16 加速
    device="cuda"   # 用 GPU
)

# 计算分数
query = "2024年中国GDP排名前5的城市"
candidates = [
    "2024城市GDP排名：上海4.72万亿...",
    "中国经济增长分析报告",
    "房价走势预测"
    # ... 共50条
]

# 批量计算相关性分数
pairs = [[query, doc] for doc in candidates]
scores = reranker.compute_score(pairs)

# 按分数排序
ranked = sorted(zip(candidates, scores), key=lambda x: -x[1])
top_20 = ranked[:20]
```

**性能数据**：

```
原始性能：
- GPU 上单条 (query, doc) 对约 100ms
- 50 条文档：50 × 100ms = 5 秒

优化后：
- 批量处理 (batch_size=32)：1 秒
- INT8 量化：500ms
- 实际使用：处理 50 条约 1 秒
```

### 4.3 两阶段精排流程

```
Stage 2 的完整过程：

50条候选 (来自搜索引擎)
    │
    ├─ 阶段 2a：BGE-Reranker 打分排序
    │  输入：50条候选
    │  处理：计算 (query, doc) 相关性分数
    │  输出：按分数排序，取 Top-20
    │
    │  示例结果：
    │  Doc_1: 0.94 ✓ 相关
    │  Doc_2: 0.87 ✓ 相关
    │  Doc_3: 0.23 ✗ 不相关
    │
    └─ 阶段 2b：LLM 最终确认
       输入：Top-20 (来自Reranker)
       处理：SelectorAgent 用 DeepSeek-R1 判断
       Prompt：
         "以下文档中，哪些与问题相关？
          问题：2024年中国GDP排名前5城市
          文档列表：[...]
          返回相关文档的编号"
       输出：8-10 条最终相关文档
```

## 第五讲：充分性验证

### 5.1 什么是充分性验证？

**问题**：搜索结果的摘要（snippet）可能信息不全

```
问题："阿里2024Q3净利润是多少？"

搜索结果摘要（snippet）：
"阿里巴巴发布2024年Q3财报，业绩表现亮眼，超出市场预期..."

问题：没有具体数字！需要获取全文

SufficiencyValidator 的作用：
发现这个摘要不够充分，标记需要获取全文
```

### 5.2 SufficiencyValidatorAgent 的工作

```
输入：问题 + 筛选后的 8-10 条文档摘要

LLM 分析逻辑：
┌───────────────────────────────────────────────────┐
│ Step 1: 问题需要什么信息？                          │
│ "净利润是多少？" → 需要具体数字                     │
│                                                  │
│ Step 2: 每条摘要有没有这个信息？                    │
│ ✓ 摘要1: "净利润438亿元"      → 有数字，充分        │
│ ✗ 摘要2: "业绩表现亮眼"       → 没数字，需要全文    │
│ ✓ 摘要3: "同比增长5%"         → 有数字，充分        │
│                                                  │
│ Step 3: 输出                                       │
│ {                                                │
│   sufficient: [1, 3],     // 摘要充分的编号        │
│   need_fulltext: [2]      // 需要全文的编号        │
│ }                                                │
└───────────────────────────────────────────────────┘

输出：标记 [摘要2] 需要获取全文
```

### 5.3 获取全文的流程

```
SufficiencyValidator 识别出需要全文的文档
    │
    ▼
调用 urlParser Tool（Jina Reader API）
    │
    ▼
对需要全文的 URL 列表，并发调用 Jina Reader
    │
    ▼
获取网页正文内容
    │
    ▼
从全文中提取需要的信息（关键段落、数据）
    │
    ▼
更新到证据库

成本：
- 每个 URL 1-2 秒
- Jina Reader 免费额度 100 次/天
- 付费 $3/10000 请求
```

### 5.4 为什么不直接获取所有全文？

**成本分析**：

| 操作 | 耗时 | 成本 |
|------|------|------|
| 搜索返回摘要 | 已包含在搜索里 | 0 |
| 获取全文（urlParser × 10篇） | 10-20秒 | $0.003 |

**我们的策略**：
```
用摘要能回答 → 不取全文
用摘要不行 → 只取不行的那几篇全文

结果：
- 平均 50% 的任务不需要 urlParser
- 成本降低 50%
- 响应速度提升（不用等所有全文下载）
```

## 一、RAG 基础

### Q1：什么是 RAG？为什么要用它？

> **RAG = Retrieval-Augmented Generation**，检索增强生成
>
> 流程：问题 → 检索相关文档 → 文档+问题一起给LLM → 回答
>
> 为什么用：
> 1. **实时性**：LLM知识有截止日期，RAG能获取最新信息
> 2. **准确性**：有据可查，减少幻觉
> 3. **可追溯**：答案可以附带引用来源

---

### Q2：你们的 RAG 流程是怎样的？

> 7 个步骤：
> 0. **缓存查询**：先查 Memory 的搜索缓存，命中则跳过搜索
> 1. **关键词生成**：Orchestrator（GRPO微调Qwen2.5-7B）+ Optimizer（DeepSeek）生成搜索词
> 2. **搜索执行**：调用 Bing/SerpAPI 获取 50 条候选文档 → 写入缓存
> 3. **粗排**：BGE-Reranker 打分，取 Top-20
> 4. **精排**：SelectorAgent（DeepSeek）判断相关性，取 8-10 条
> 5. **充分性验证**：摘要不够则获取全文 (Jina Reader)
> 6. **生成答案**：文档 + 问题 → 带引用的答案
>
> **缓存收益**：节省 27% 的搜索 API 调用

---

### Q3：RAG 有什么局限性？你们怎么解决的？

> | 局限性 | 我们的解决方案 |
> |--------|---------------|
> | 搜不到相关文档 | Reorchestrator 动态调整关键词重试 |
> | 搜索结果不相关 | 两阶段检索（Bing+Reranker+LLM） |
> | 摘要信息不全 | SufficiencyValidator + 获取全文 |
> | 文档太长超上下文 | 截断 + 提取关键段落 |
> | 重复搜索浪费成本 | Memory 搜索缓存（语义匹配复用） |

## 二、两阶段检索（核心技术）

### Q4：你们的检索流程是怎样的？为什么分成两阶段？

> **我们的技术方案**：
> 
> Stage 0（缓存查询）：Memory 模块
> - 技术：BGE 编码 + 余弦相似度
> - 逻辑：相似度 > 0.85 则命中，直接返回
> - 收益：节省 27% API 调用
>
> Stage 1（召回）：Bing Search API / SerpAPI
> - 输入：搜索关键词
> - 输出：50 条候选文档
> - 特点：快速、广泛
> - 完成后写入缓存
>
> Stage 2（精排）：
> - 2a：BGE-Reranker (Cross-Encoder) 打分 → Top-20
> - 2b：SelectorAgent (DeepSeek API) 最终确认 → 8-10 条
>
> **为什么两阶段 + 缓存**：
> - 只用搜索引擎：排序根据点击量/SEO，不够准
> - 只用 Reranker：处理 50 条快，但处理百万文档太慢
> - 两阶段 + 缓存：精度高 + 速度快 + 成本低

---

### Q5：为什么选择 Bing 而不是 Google 直接用 SerpAPI？

> 成本考虑：
> - Bing：$3/1000次（便宜）
> - SerpAPI：$50/5000次（贵 15 倍）
>
> 我们的策略：
> ```
> if Bing 结果质量好：
>     使用 Bing 结果
> else:  # 相关度低或结果太少
>     切换到 SerpAPI 重试
> ```
>
> 这样既节省成本，又能保证质量

---

### Q6：多个关键词怎么并发搜索？为什么要并发？

> **实现**：asyncio + aiohttp
> ```python
> async def concurrent_search(keywords):
>     tasks = [search_one(kw) for kw in keywords]
>     results = await asyncio.gather(*tasks)
> ```
>
> **效果对比**：
> - 5 个关键词串行：5 × 2秒 = 10 秒
> - 5 个关键词并行：约 2 秒
>
> **原因**：搜索是 IO 密集型，多个请求同时发出，等待网络时不阻塞

---

### Q7：搜索缓存是怎么实现的？为什么能节省 27%？

> **实现**：
> - 存储：Redis
> - 键：关键词的 BGE embedding
> - 值：搜索结果
> - 匹配：余弦相似度 > 0.85 视为命中
>
> **为什么用语义匹配而不是精确匹配**：
> - "BERT 预训练" 和 "BERT pre-training" 是同一个意思
> - 精确匹配会 miss，语义匹配能命中
>
> **27% 怎么来的**：
> - 多轮对话中，用户追问往往和之前的问题相关
> - 例如：问完 "BERT 预训练" 再问 "MLM mask 比例"
> - 后者能命中前者的缓存

---

### Q8：搜索结果有去重吗？怎么去重的？

> **两层去重**：
>
> 第一层：URL 去重（精确匹配）
> - 同一个 URL 只保留一条
>
> 第二层：内容去重（语义匹配）
> - 用 BGE embedding 计算文档相似度
> - 相似度 > 0.95 视为重复
> - 保留排名靠前的
>
> **原因**：同一篇文章可能被多网站转载，URL 不同但内容相同

---

## 三、BGE-Reranker 重排序（高频重点）

### Q9：Bi-Encoder 和 Cross-Encoder 有什么区别？

> | 维度 | Bi-Encoder | Cross-Encoder |
> |------|-----------|---------------|
> | 工作方式 | Query和Doc分别编码，计算余弦相似度 | Query和Doc拼接后一起编码 |
> | 速度 | 快（可提前编码所有Doc） | 慢 |
> | 精度 | 一般 | 高 |
> | 用途 | 粗排/召回 | **精排/重排序** ← 我们用 |
>
> **为什么 Cross-Encoder 更准**：
> - 能看到 Query 和 Doc 的交互信息
> - 理解深层语义（例如"净利润" = "盈利"）

---

### Q10：为什么要用两阶段检索，不能只用 Reranker？

> **原因**：
> - Reranker 精度高但很慢
> - 50 条文档需要 1 秒
> - 100 万条文档需要好几个小时
>
> **两阶段方案**：
> 1. 搜索引擎快速从百万文档中找 50 条（1-2秒）
> 2. Reranker 精确排序这 50 条（1秒）
> 
> 结果：总耗时 2-3 秒，精度也高

---

### Q11：BGE-Reranker 是什么？为什么选它？

> **BGE = BAAI General Embedding**，北京智源通用向量模型
>
> 选择原因：
> 1. **中文优化**：智源针对中文微调，效果好
> 2. **开源免费**：model: `BAAI/bge-reranker-base`
> 3. **性能平衡**：精度和速度平衡好
> 4. **可量化**：INT8 量化后速度快 2 倍
>
> **使用**：
> ```python
> from FlagEmbedding import FlagReranker
> reranker = FlagReranker('BAAI/bge-reranker-base')
> scores = reranker.compute_score([[query, doc1], [query, doc2], ...])
> ```

---

### Q12：Reranker 之后还要 LLM 判断吗？为什么？

> **是的**。流程是：
> 1. **Reranker 粗排**：50 条 → Top-20（按相似度分数）
> 2. **LLM 精排**：Top-20 → 8-10 条（SelectorAgent，用 DeepSeek API）
>
> **为什么需要 LLM**：
> - Reranker 只看文本相似度
> - 不理解深层语义
>
> **例子**：
> - Query："苹果公司市值"
> - Doc："今年苹果丰收，价格下降"
> - Reranker：两个"苹果"都有，可能给高分
> - LLM：判断这是水果不是公司，给低分

---

### Q13：Reranker 性能怎么样？有优化吗？

> **原始性能**：
> - GPU 上单条 (query, doc) 对约 100ms
> - 50 条文档约 5 秒
>
> **我们的优化**：
> 1. **批量处理**：batch_size=32，1 秒处理 50 条
> 2. **GPU 加速**：CUDA，比 CPU 快 10 倍
> 3. **模型量化**：INT8，速度提升 2 倍
> 4. **缓存**：相同 query 结果缓存
>
> **最终**：处理 50 条约 1 秒

## 四、搜索策略

### Q14：三种搜索类型怎么区分？

> | 类型 | 场景 | 示例 | 技术实现 |
> |------|------|------|---------|
> | 单步单次 | 单一实体，简单查询 | "特斯拉CEO是谁" | 1 个关键词 → webSearch(Bing) |
> | 单步并发 | 多个独立实体 | "阿里、京东Q3财报" | N 个关键词 → 并发 N 个 webSearch |
> | 多步多次 | 前后有依赖 | "先查政策，再分析影响" | 串行 webSearch，前结果影响后 |
>
> **谁来决定**：OrchestratorAgent（GRPO 微调的 Qwen2.5-7B），这也是 RL 训练的目标之一。

---

### Q15：关键词生成有什么技巧？

> **好的关键词**：
> - 包含核心实体（"阿里巴巴"不是"某公司"）
> - 包含时间限定（"2024年Q3"）
> - 包含数据类型（"财报""净利润"）
>
> **优化策略**（OptimizerAgent 用 DeepSeek API）：
> - 补充遗漏的实体（"阿里、京东、拼多多"中没有"抖音"）
> - 添加权威来源词（"统计局""财报"）
> - 拆分过长的关键词

---

### Q16：搜索结果为空怎么办？

> 三种情况处理：
> 1. **关键词太专业**
>    - Optimizer 简化（例："后量子密码"拆成"量子计算"+"密码"）
>    - 重试
>
> 2. **确实搜不到**（冷门话题）
>    - 答案中说明"未找到相关信息"
>    - 不编造
>
> 3. **API 问题**
>    - 重试 3 次
>    - 切换备用引擎（Bing → SerpAPI）

---

## 五、充分性验证

### Q17：什么是充分性验证？为什么需要它？

> **问题**：搜索结果的摘要可能信息不全
>
> **例子**：
> - 问题："阿里Q3净利润是多少？"
> - 摘要："阿里巴巴业绩表现亮眼..." ← 没数字！
>
> **SufficiencyValidatorAgent（DeepSeek API）的作用**：
> - 判断摘要能否回答问题
> - 不能则标记需要获取全文（调 Jina Reader）

---

### Q18：怎么判断摘要信息是否充分？

> **LLM 分析**：
> 1. 问题需要什么信息？（具体数字/对比/趋势...）
> 2. 摘要有没有这些信息？
>
> **例子**：
> - ✓ "净利润 438 亿元" → 有数字，充分
> - ✗ "业绩表现亮眼" → 没数字，需要全文
> - ✓ "同比增长 5%" → 有数字，充分

---

### Q19：为什么不直接获取所有全文？

> **成本分析**：
> - 摘要：搜索结果自带，免费
> - 全文：调 Jina Reader API，有成本
>
> **我们的策略**：
> ```
> 摘要能回答 → 不取全文
> 摘要不行 → 只取需要的那几篇全文
> ```
>
> **结果**：
> - 50% 任务不需要 urlParser
> - 成本降低 50%
> - 响应速度更快

---

### Q20：获取全文用什么工具？为什么不自己爬？

> **工具**：Jina Reader API
>
> **为什么不自己爬**：
> 1. **网页结构千差万别**
>    - 新闻网站、博客、论坛结构都不同
>    - 自己维护爬虫规则太复杂
>
> 2. **JS 渲染问题**
>    - 很多现代网站内容是 JS 动态加载的
>    - 自己爬拿不到
>
> 3. **反爬措施**
>    - 验证码、频率限制
>    - Jina 已经处理好
>
> 4. **维护成本**
>    - 网站改版，爬虫就要更新
>    - Jina 持续维护

---

### Q21：Jina Reader 的成本是多少？

> **免费额度**：100 次/天
>
> **付费价格**：$3/10000 请求
>
> **我们的实际成本**：
> - 平均 50% 的任务需要 urlParser
> - 每个任务平均 2-3 个 URL
> - 100 个任务 = 150 次请求 = $0.045
> - 非常便宜

## 六、综合场景题

### Q22：如果用户问一个很专业的学术问题，Bing 效果不好怎么办？

> **可以扩展搜索源**：
> 1. **学术搜索**：Google Scholar、Semantic Scholar API
> 2. **论文数据库**：arXiv API
> 3. **专业数据库**：PubMed（医学）、Wind（金融）
>
> **MCP 的好处**：
> - 新增搜索源只需注册新 Tool
> - Agent 代码不用改
> - 系统自动路由

---

### Q23：如果 BGE-Reranker 排序错了怎么办？

> **可能的原因**：
> 1. 模型对某个领域知识不足
> 2. 问题表述歧义，模型理解错了
>
> **解决方案**：
> 1. **LLM 最终确认**（已在做）
> 2. **反馈学习**
>    - 收集用户反馈（哪些文档该排前面）
>    - 微调 Reranker 或用户反馈来校准
> 3. **多模型融合**
>    - 不只用 BGE，还用其他 Reranker
>    - 投票决策

---

### Q24：文档太长超过 LLM 上下文窗口怎么办？

> **三种策略**：
> 1. **截断**：只取前 N 个 token（最简单）
> 2. **分段**：切成多段分别处理，再合并
> 3. **摘要**：LLM 先生成摘要，再处理
>
> **我们的做法**：
> - 优先用搜索结果的摘要（天然短）
> - 获取全文时，提取关键段落而非全部
> - 如果还超过窗口，用策略 2

---

### Q25：怎么评估 RAG 的效果？

> **三个维度**：
> 1. **召回率**：相关文档有没有被搜到
> 2. **精排准确率**：排在前面的是不是真的相关
> 3. **最终答案质量**：引用的文档对不对，答案准不准
>
> **我们的指标**：
> - Top-5 命中率：58% → 82%（加入 Reranker 后）
> - 精排准确率：87%
> - 引用准确率：92%
