# 第一部分：知识讲解

---

## 第一讲：Agent 基础概念

### 1.1 什么是 Agent？

**一句话定义**：Agent = LLM + 工具调用能力 + 自主决策能力

```
普通 LLM：
用户问 → LLM答 → 结束

Agent：
用户问 → LLM思考"我需要做什么" → 调用工具 → 看结果 → 继续思考 → 可能再调工具 → 最终回答
```

**核心区别**：Agent 能"行动"，不只是"回答"。

---

### 1.2 单 Agent vs 多 Agent

**单 Agent 方案**：一个大 Prompt 包揽所有事

```
问题：
1. Prompt 太长，容易超出上下文窗口
2. 任务太杂，LLM容易顾此失彼
3. 出错了不知道是哪个环节的问题
```

**多 Agent 方案**：拆成多个小 Agent，各司其职

```
优势：
1. 单一职责，Prompt短而精准
2. 可以独立调试和优化
3. 部分环节可以并行
4. 易于扩展
```

**类比**：单 Agent 像一个人干所有活，多 Agent 像一个团队分工合作。

---

### 1.3 我们系统的 7 个 Agent

| Agent | 职责 | 输入 | 输出 |
|-------|------|------|------|
| **Orchestrator** | 任务规划 | 用户问题 | 是否搜索、搜索类型、关键词、是否代码 |
| **Optimizer** | 优化计划 | 原始计划 | 优化后的关键词 |
| **Selector** | 筛选文档 | 50条候选 | 8-10条相关 |
| **SufficiencyValidator** | 验证充分性 | 摘要列表 | 哪些需要全文 |
| **Reorchestrator** | 动态调整 | 当前状态 | 调整后的计划 |
| **CodeAgent** | 生成代码 | 需求+数据 | Python代码 |
| **Assistant** | 生成答案 | 所有证据 | 最终答案+引用 |

**各 Agent 用的模型**：

| Agent | 模型 | 说明 |
|-------|------|------|
| **OrchestratorAgent** | Qwen2.5-7B + LoRA（GRPO 微调） | 决策模型，自己部署 |
| 其他 6 个 Agent | DeepSeek API | 执行模型，调 API |

> 为什么只微调 OrchestratorAgent？因为它是"大脑"，决定整个流程走向。其他 Agent 职责单一，用 Prompt Engineering 就够了。

**设计思路**：按照人类做研究的流程拆分——先规划、再搜索、筛选、验证、必要时调整、写代码、最后汇总。

## 第二讲：Agent vs Tool 的区别

这是一个**高频考点**，很多人搞混。

### 2.1 本质区别

| | Agent | Tool |
|--|-------|------|
| **有没有 LLM** | ✅ 有，需要 LLM 推理 | ❌ 没有，纯代码执行 |
| **能否决策** | ✅ 能，根据情况选择行为 | ❌ 不能，只执行指定操作 |
| **输入** | 自然语言或结构化数据 | 结构化参数 |
| **输出** | 自然语言或结构化数据 | 结构化结果 |

### 2.2 我们系统的分类

```
Agent（有大脑，能思考）：
├── OrchestratorAgent
├── OptimizerAgent
├── SelectorAgent
├── SufficiencyValidatorAgent
├── ReorchestratorAgent
├── CodeAgent
└── AssistantAgent

Tool（没有大脑，只执行）：
├── webSearch      → 调 Bing/SerpAPI
├── urlParser      → 调 Jina Reader
└── codeRunner     → 调 Docker 沙箱
```

**记忆口诀**：Agent 决定"做什么"，Tool 负责"去执行"。

## 第三讲：Memory 模块

### 3.1 为什么需要 Memory？

没有 Memory 的问题：
- 用户追问"那 GPT 呢"，系统不知道在问什么
- 刚搜过"BERT 预训练"，又搜一遍，浪费 API
- 用户说"它的作者"，不知道"它"指谁

### 3.2 三层记忆架构

```
┌─────────────────────────────────────────────────────────────────────┐
│  1. 短期记忆 (Redis)                                                │
│  ════════════════════════════════════════════════════════════════  │
│  存储当前对话历史：                                                  │
│  [{"role": "user", "content": "BERT预训练"},                        │
│   {"role": "assistant", "content": "...", "sources": [...]}]        │
│                                                                     │
│  作用：支持多轮对话，理解上下文                                      │
├─────────────────────────────────────────────────────────────────────┤
│  2. 搜索缓存 (Redis + 语义匹配)                                      │
│  ════════════════════════════════════════════════════════════════  │
│  缓存已搜索的关键词和结果：                                          │
│  {"BERT pre-training": [搜索结果...]}                               │
│                                                                     │
│  命中逻辑：BGE 编码后相似度 > 0.85 即复用                            │
│  作用：减少重复搜索，节省 27% API 成本                               │
├─────────────────────────────────────────────────────────────────────┤
│  3. 实体记忆 (指代消解)                                              │
│  ════════════════════════════════════════════════════════════════  │
│  追踪对话中的实体：                                                  │
│  {"它": "BERT", "这篇论文": "Attention Is All You Need"}            │
│                                                                     │
│  作用：理解"它的参数量"指的是 BERT 的参数量                          │
└─────────────────────────────────────────────────────────────────────┘
```

### 3.3 Memory 在流程中的位置

```
用户问题 → 【读取 Memory】→ OrchestratorAgent 决策 → ... → 【写入 Memory】→ 返回答案
            ↑                                              ↑
         读缓存、解析指代                              写缓存、更新实体
```

**关键**：Memory 贯穿整个流程，不是独立模块。

│                                                                  │
│ 【先读取 Memory】                                                 │
│ • 短期记忆：空（新对话）                                          │
│ • 搜索缓存：查询 "GDP 城市 排名" → 未命中                         │
│ • 实体记忆：空                                                    │
│                                                                  │
│ 输入: "分析2024年中国GDP前5城市，画柱状图"                         │
│                                                                  │
│ LLM 分析:                                                        │
│ • "GDP数据" → 需要实时信息 → need_search = true                  │
│ • "画柱状图" → 需要代码 → need_code = true                       │
│ • 单一主题 → search_type = "single"                              │
│                                                                  │
│ 输出:                                                            │
│ {                                                                │
│   need_search: true,                                             │
│   search_type: "single",                                         │

│   need_code: true                                                │
│ }                                                                │
└──────────────────────────────────────────────────────────────────┘
                              ↓
┌──────────────────────────────────────────────────────────────────┐
│ Step 2: OptimizerAgent                                           │
├──────────────────────────────────────────────────────────────────┤
│ 输入: keywords = ["2024年中国城市GDP排名前五"]                    │
│                                                                  │
│ LLM 分析: 关键词OK，但可以更精准                                  │
│                                                                  │
│ 输出: ["2024年中国城市GDP排名 统计局"]                            │
│       (加了"统计局"提高权威性)                                    │
└──────────────────────────────────────────────────────────────────┘
                              ↓
┌──────────────────────────────────────────────────────────────────┐
│ Step 3: webSearch (Tool) + 写入缓存                               │
├──────────────────────────────────────────────────────────────────┤

│                                                                  │
│ 结果示例:                                                        │

│   ...                                                            │
│ ]                                                                │
│                                                                  │
│ 【写入 Memory - 搜索缓存】                                        │
│ {"2024年中国城市GDP排名前五": [上述结果]}                         │

└──────────────────────────────────────────────────────────────────┘
                              ↓
┌──────────────────────────────────────────────────────────────────┐
│ Step 4: SelectorAgent + BGE-Reranker                             │
├──────────────────────────────────────────────────────────────────┤
│ 两阶段筛选:                                                       │
│                                                                  │
│ 阶段1: BGE-Reranker 打分排序                                      │
│   Doc1: 0.94 (高相关)                                            │
│   Doc2: 0.87 (相关)                                              │
│   Doc3: 0.23 (不相关 - 房价)                                      │
│                                                                  │
│ 阶段2: LLM 最终确认                                               │
│   从 Top-10 中选出真正相关的                                      │
│                                                                  │
│ 输出: 5 条相关文档                                                │
└──────────────────────────────────────────────────────────────────┘
                              ↓
┌──────────────────────────────────────────────────────────────────┐
│ Step 5: SufficiencyValidatorAgent                                │
├──────────────────────────────────────────────────────────────────┤
│ 检查每条摘要是否有具体数据:                                        │
│                                                                  │

## 第五讲：MCP 协议

### 4.1 为什么需要 MCP？

**没有 MCP 之前的问题**：

```python
# Agent 代码里直接写工具调用
class MyAgent:
    def search(self, keyword):
        # 直接调 Bing API
        response = requests.get(f"https://api.bing.com/search?q={keyword}")
        return response.json()
```

问题：
1. Agent 和 Tool 紧耦合
2. 换搜索引擎要改 Agent 代码
3. 每个 Agent 都要写一遍调用逻辑

**有了 MCP 之后**：

```python
# Agent 只管调用，不管实现
class MyAgent:
    def search(self, keyword):
        return mcp_client.call("webSearch", {"keyword": keyword})
```

好处：
1. Agent 不需要知道 Tool 怎么实现
2. 换搜索引擎只改 MCP Server，Agent 不用动
3. 统一的调用接口

### 4.2 MCP 是什么？

**MCP = Model Context Protocol**

- 由 Anthropic（Claude 的公司）2024 年底提出
- 开放标准，基于 JSON-RPC 2.0
- 目标：成为 LLM 工具调用的"USB 接口"

### 4.3 MCP 架构

```
┌─────────────┐
│   Agent     │  ← 只管调用，不管实现
└──────┬──────┘
       │ MCP Client
       │ (JSON-RPC 2.0)
       ↓
┌─────────────┐
│ MCP Server  │  ← 注册所有工具，路由调用
├─────────────┤
│ webSearch   │ → Bing API / SerpAPI
│ urlParser   │ → Jina Reader
│ codeRunner  │ → Docker 沙箱
└─────────────┘
```

### 4.4 MCP 消息格式

```json
// 1. 查询有什么工具
请求: {"method": "tools/list"}
响应: {"tools": [{"name": "webSearch", "description": "..."}, ...]}

// 2. 调用工具
请求: {
  "method": "tools/call",
  "params": {
    "name": "webSearch",
    "arguments": {"keyword": "xxx"}
  }
}
响应: {
  "result": {"content": [{"type": "text", "text": "[结果...]"}]}
}
```

## 第六讲：三个核心 Tool

### 5.1 webSearch（搜索引擎）

| 引擎 | 优点 | 缺点 | 成本 |
|------|------|------|------|
| Bing | 便宜，微软生态 | 中文效果一般 | $3/1000次 |
| SerpAPI | Google效果好 | 贵 | $50/5000次 |

**选择策略**：默认 Bing，效果不好时 fallback 到 SerpAPI

### 5.2 urlParser（URL 解析）

用 **Jina Reader** 而不是自己爬：
- 网页结构千差万别，自己解析太麻烦
- Jina 能处理 JS 渲染的页面
- API 简单：传 URL，返回正文

### 5.3 codeRunner（代码执行）

用 **Docker 沙箱**，5 层安全：

| 措施 | 作用 |
|------|------|
| 容器隔离 | 代码无法影响主机 |
| 资源限制 | CPU 1核，内存 512MB |
| 超时机制 | 60秒强制终止 |
| 网络禁用 | 防止下载恶意程序 |
| 只读文件系统 | 防止篡改系统文件 |

## 第七讲：关键设计决策

### 6.1 为什么 Selector 和 SufficiencyValidator 分开？

虽然都是"筛选"，但目标不同：

| | Selector | SufficiencyValidator |
|--|----------|---------------------|
| 问的问题 | 这篇和问题相关吗？ | 摘要信息够详细吗？ |
| 输入 | 50条文档 | 8-10条摘要 |
| 输出 | 相关的文档 | 需要全文的文档ID |

**例子**：
- "阿里Q3财报"文章 → Selector 判断：相关 ✓
- 但摘要只说"业绩亮眼" → Validator 判断：信息不够，要全文

### 6.2 Reorchestrator 什么时候触发？

**触发时机**：执行完一轮搜索+筛选后

**作用**：检查当前进度，发现问题及时调整

**例子**：
```
问题："对比苹果和华为手机销量"

第一轮搜索后：
- 苹果数据 ✓ 找到了
- 华为数据 ✗ 没找到

Reorchestrator 决策：
→ 补充搜索 "华为手机全球出货量 IDC"
```

### 6.3 代码执行失败怎么自动修复？

**错误反馈循环**，最多 3 次：

```
生成代码 → 执行 → 报错 "ModuleNotFoundError: seaborn"
                      ↓
把报错给 LLM → 生成修复版（改用 matplotlib）→ 执行 → 成功！
```

## 一、Agent 架构设计

### Q1：你的系统有几个Agent？分别是什么？

> 7个Agent：
> 1. **OrchestratorAgent**：分析问题，判断是否需要搜索和代码，生成关键词
> 2. **OptimizerAgent**：优化关键词，补充遗漏
> 3. **SelectorAgent**：配合BGE-Reranker筛选相关文档
> 4. **SufficiencyValidatorAgent**：判断摘要信息是否足够
> 5. **ReorchestratorAgent**：动态调整后续计划
> 6. **CodeAgent**：生成Python代码，失败时自动修复
> 7. **AssistantAgent**：汇总信息，生成最终答案

---

### Q2：为什么要拆成7个Agent，而不是用一个大Agent？

> 三个原因：
> 1. **单一职责**：每个Agent只做一件事，Prompt更短更精准
> 2. **可调试**：出问题能定位到具体Agent，单独优化
> 3. **可扩展**：新增能力只需加Agent，不影响已有的
>
> 单Agent的问题：Prompt超长、职责混乱、调试困难

---

### Q3：Agent和Tool有什么区别？

> | 维度 | Agent | Tool |
> |------|-------|------|
> | 有没有LLM | 有 | 没有 |
> | 能否决策 | 能 | 不能 |
> | 例子 | Orchestrator、Selector | webSearch、codeRunner |
>
> **口诀**：Agent决定"做什么"，Tool负责"去执行"

---

### Q4：7个Agent是怎么通信的？

> 采用**编排器模式**：
> - OrchestratorAgent是入口，生成整体计划
> - 像流水线：每个Agent处理完把结果传给下一个
> - 通过消息队列传递JSON格式数据
> - ReorchestratorAgent可以中途修改计划

---

### Q5：如果某个Agent挂了怎么办？

> 三层容错：
> 1. **重试**：LLM返回格式不对，最多重试3次
> 2. **降级**：Optimizer失败→用原始计划；CodeAgent失败→只返回文字
> 3. **熔断**：超过30秒没响应，跳过并记录日志

---

### Q6：为什么Selector和SufficiencyValidator要分开？

> 目标不同：
> - **Selector**：判断文档和问题**相不相关**
> - **SufficiencyValidator**：判断摘要**够不够详细**
>
> 例子："阿里Q3财报"文章相关，但摘要只说"业绩亮眼"没数字→需要全文

---

### Q7：ReorchestratorAgent什么时候触发？

> 触发：执行完一轮搜索+筛选后
>
> 例子：问"对比苹果和华为销量"
> - 第一轮：苹果数据✓，华为数据✗
> - Reorchestrator决策：补充搜索"华为手机全球出货量 IDC"
>
> 作用：动态发现信息缺口，主动补救

---

### Q8：OrchestratorAgent 用什么模型？为什么只微调它？

> **模型**：Qwen2.5-7B-Instruct + LoRA（GRPO 微调）
>
> **为什么只微调它**：
> 1. 它是"大脑"，决定整个流程走向（调谁、什么时候停）
> 2. 决策质量直接影响效率和效果
> 3. 其他 Agent 职责单一，Prompt Engineering 就够了
>
> **其他 Agent**：都用 DeepSeek API，按 Token 计费

---

### Q9：Memory 模块有哪三层？

> 1. **短期记忆**（Redis）：当前对话历史，支持多轮对话
> 2. **搜索缓存**（Redis + BGE 语义匹配）：缓存搜索结果，相似度>0.85 复用
> 3. **实体记忆**：指代消解，"它"→"BERT"
>
> **收益**：缓存节省 27% API 调用

## 二、Agent 协作流程

### Q10：描述一次完整的问答流程

> 以"分析2024年中国GDP前5城市，画柱状图"为例：
>
> 1. **Orchestrator**：need_search=true, need_code=true, 生成关键词
> 2. **Optimizer**：优化关键词
> 3. **webSearch**：返回10条结果
> 4. **Selector+Reranker**：筛选出5条相关
> 5. **SufficiencyValidator**：2条需要全文
> 6. **urlParser**：获取全文
> 7. **Reorchestrator**：数据齐全，进入代码阶段
> 8. **CodeAgent**：生成matplotlib代码
> 9. **codeRunner**：Docker执行，返回图片
> 10. **Assistant**：生成答案+图表+引用

---

### Q11：三种搜索类型怎么区分？

> | 类型 | 场景 | 示例 |
> |------|------|------|
> | 单步单次 | 单一实体，简单事实 | "特斯拉CEO是谁" |
> | 单步并发 | 多个独立实体 | "阿里、京东、拼多多Q3财报" |
> | 多步多次 | 前后有依赖 | "先查政策，再分析影响" |

---

### Q12：搜索结果为空怎么办？

> 1. **关键词太长**：Optimizer简化后重试
> 2. **确实搜不到**：答案中说明"未找到相关信息"
> 3. **API问题**：重试3次，切换备用引擎

---

### Q13：Agent之间的数据格式是什么？

> 结构化JSON，例如Orchestrator输出：
> ```json
> {
>   "need_search": true,
>   "search_type": "single_concurrent",
>   "keywords": ["阿里Q3财报", "京东Q3财报"],
>   "need_code": true
> }
> ```
> 保证措施：Prompt给示例、JSON解析校验、字段校验、兜底默认值

### Q14：并发搜索怎么实现的？

> 用`asyncio` + `aiohttp`并行请求：
> - 5个关键词串行：5×2秒=10秒
> - 5个关键词并行：约2秒
>
> 搜索是IO密集型，多个请求同时发出，等待时不阻塞

---

### Q15：代码执行失败怎么自动修复？

> 错误反馈循环，最多3次：
> ```
> 生成代码 → 报错"ModuleNotFoundError: seaborn"
>     ↓
> 把报错给LLM → 修复（改用matplotlib）→ 成功
> ```
> 3次都失败：放弃代码，只返回文字答案

## 三、MCP 协议

### Q16：什么是MCP？为什么用它？

> **MCP = Model Context Protocol**，Anthropic 2024年提出的开放协议
>
> 作用：标准化LLM和工具的交互
>
> 好处：
> 1. **解耦**：Agent不需要知道Tool怎么实现
> 2. **标准化**：统一JSON-RPC格式
> 3. **可扩展**：新增工具只需注册，Agent不用改
>
> 类比：MCP是"USB接口"，任何设备插上就能用

---

### Q17：MCP和OpenAI Function Calling有什么区别？

> | 对比项 | Function Calling | MCP |
> |--------|-----------------|-----|
> | 提出者 | OpenAI | Anthropic |
> | 开放性 | 私有，只能用OpenAI | 开放标准 |
> | 协议 | 自定义 | JSON-RPC 2.0 |
> | 生态 | 封闭 | 社区贡献 |
>
> 选MCP原因：项目用DeepSeek不是OpenAI，MCP解耦更彻底

---

### Q18：MCP的消息格式？

> ```json
> // 查询工具
> 请求: {"method": "tools/list"}
> 响应: {"tools": [{"name": "webSearch", ...}]}
>
> // 调用工具
> 请求: {"method": "tools/call", "params": {"name": "webSearch", "arguments": {"keyword": "xxx"}}}
> 响应: {"result": {"content": [{"type": "text", "text": "[结果]"}]}}
> ```

---

### Q19：MCP Server怎么部署的？

> 三种方式：
> 1. **同进程**（我目前的）：简单，延迟低
> 2. **本地Socket**：Server独立进程
> 3. **远程HTTP**：Server在远程，适合多Agent共享
>
> 生产建议用2或3，可以独立扩缩容

---

### Q20：MCP Server挂了怎么办？

> 1. **健康检查**：定期心跳检测
> 2. **超时重试**：10秒超时，重试2次
> 3. **降级**：webSearch挂→切换引擎；codeRunner挂→跳过代码
> 4. **告警**：连续失败超阈值，发通知

---

## 四、工具层实现

### Q21：搜索用什么引擎？为什么？

> 两个：**Bing** 和 **SerpAPI（Google）**
>
> | 引擎 | 优点 | 缺点 | 价格 |
> |------|------|------|------|
> | Bing | 便宜 | 中文一般 | $3/1000次 |
> | SerpAPI | 效果好 | 贵 | $50/5000次 |
>
> 策略：默认Bing，效果不好fallback到SerpAPI

---

### Q22：代码执行怎么保证安全？

> Docker沙箱，5层措施：
> 1. **容器隔离**：每次新建，用完销毁
> 2. **资源限制**：CPU 1核，内存512MB
> 3. **超时**：60秒强制终止
> 4. **禁网**：容器无法访问网络
> 5. **只读**：只有/tmp可写

---

### Q23：URL解析为什么用Jina Reader？

> 自己爬的问题：网页结构千差万别、JS渲染、反爬、维护成本高
>
> Jina优势：专门做这个、支持JS渲染、API简单

---

### Q24：搜索结果有去重吗？

> 两层：
> 1. **URL去重**：精确匹配
> 2. **内容去重**：BGE计算相似度>0.95视为重复
>
> 原因：同一篇文章可能被多网站转载

---

### Q25：Docker冷启动慢怎么办？

> 1. **容器池预热**：提前创建10个空闲容器
> 2. **镜像优化**：轻量基础镜像+预装库
> 3. **Keep-Alive**：同会话复用容器
>
> 优化后：首次2秒，后续<500ms

---

### Q26：用户问题不需要搜索怎么处理？

> Orchestrator判断：
> - "特斯拉股价"→需要搜索
> - "勾股定理是什么"→不需要
>
> 不需要搜索的流程：
> ```
> 问题 → Orchestrator(need_search=false) → 直接到Assistant → 答案
> ```
