# 🏗️ Agentic RL 科研检索系统 - 完整架构手册

---

## 一、系统概述

> 一个基于**多 Agent 协作 + 强化学习**的科研问答系统，采用 **MCP 协议**标准化工具调用，能够自动联网搜索、筛选文献、执行代码、生成报告。

---

## 二、7 个 Agent 及其职责

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                                                                             │
│                            7 个 Agent 分工                                  │
│                                                                             │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │                                                                     │   │
│  │  1. OrchestratorAgent（编排器）                                     │   │
│  │     ────────────────────────────────────────────────────────────   │   │
│  │     职责：任务规划的总指挥                                           │   │
│  │     输入：用户问题                                                   │   │
│  │     输出：                                                          │   │
│  │       - 是否需要搜索（是/否）                                        │   │
│  │       - 搜索类型（单步单次/单步并发/多步多次）                        │   │
│  │       - 是否需要代码（是/否）                                        │   │
│  │       - 关键词列表                                                   │   │
│  │       - 执行计划                                                    │   │
│  │                                                                     │   │
│  │  ─────────────────────────────────────────────────────────────────  │   │
│  │                                                                     │   │
│  │  2. OptimizerAgent（优化器）                                        │   │
│  │     ────────────────────────────────────────────────────────────   │   │
│  │     职责：优化搜索流程                                               │   │
│  │     输入：Orchestrator 生成的执行计划                                │   │
│  │     处理：                                                          │   │
│  │       - 关键词太宽泛？→ 精简                                        │   │
│  │       - 关键词有遗漏？→ 补充                                        │   │
│  │       - 步骤可以合并？→ 优化                                        │   │
│  │     输出：优化后的执行计划                                           │   │
│  │                                                                     │   │
│  │  ─────────────────────────────────────────────────────────────────  │   │
│  │                                                                     │   │
│  │  3. SelectorAgent（选择器）                                         │   │
│  │     ────────────────────────────────────────────────────────────   │   │
│  │     职责：从搜索结果中筛选相关文档                                    │   │
│  │     输入：50条候选文档（来自搜索引擎）                                │   │
│  │     处理：                                                          │   │
│  │       - BGE-Reranker 打分排序                                       │   │
│  │       - LLM 判断相关性                                              │   │
│  │       - 综合筛选 Top-K                                              │   │
│  │     输出：8-10 条高相关文档                                         │   │
│  │                                                                     │   │
│  │  ─────────────────────────────────────────────────────────────────  │   │
│  │                                                                     │   │
│  │  4. SufficiencyValidatorAgent（充分性验证器）                        │   │
│  │     ────────────────────────────────────────────────────────────   │   │
│  │     职责：判断摘要信息是否足够回答问题                                │   │
│  │     输入：问题 + 筛选后的文档摘要                                    │   │
│  │     处理：逐条分析摘要                                               │   │
│  │       - √ 充分：包含具体数据                                        │   │
│  │       - × 不足：只有概述，缺细节                                    │   │
│  │     输出：                                                          │   │
│  │       - 充分的文档列表                                              │   │
│  │       - 需要获取全文的文档 ID                                       │   │
│  │                                                                     │   │
│  │  ─────────────────────────────────────────────────────────────────  │   │
│  │                                                                     │   │
│  │  5. ReorchestratorAgent（重编排器）                                  │   │
│  │     ────────────────────────────────────────────────────────────   │   │
│  │     职责：根据中间结果动态调整后续计划                                │   │
│  │     输入：当前已获取的信息 + 原执行计划                               │   │
│  │     处理：分析当前进度，发现问题                                      │   │
│  │       - 数据不全？→ 补充搜索                                        │   │
│  │       - 方向跑偏？→ 调整关键词                                      │   │
│  │       - 已经够了？→ 跳过后续步骤                                    │   │
│  │     输出：调整后的执行计划                                           │   │
│  │                                                                     │   │
│  │  ─────────────────────────────────────────────────────────────────  │   │
│  │                                                                     │   │
│  │  6. CodeAgent（代码生成器）                                          │   │
│  │     ────────────────────────────────────────────────────────────   │   │
│  │     职责：生成并调试 Python 代码                                     │   │
│  │     输入：问题 + 收集到的数据                                        │   │
│  │     处理：                                                          │   │
│  │       - 理解代码需求（画图/计算/分析）                               │   │
│  │       - 生成 Python 代码                                            │   │
│  │       - 执行失败则根据报错修复（最多3次）                             │   │
│  │     输出：可执行的 Python 代码                                       │   │
│  │                                                                     │   │
│  │  ─────────────────────────────────────────────────────────────────  │   │
│  │                                                                     │   │
│  │  7. AssistantAgent（助手）                                          │   │
│  │     ────────────────────────────────────────────────────────────   │   │
│  │     职责：汇总所有信息，生成最终答案                                  │   │
│  │     输入：问题 + 所有证据 + 代码执行结果                              │   │
│  │     处理：                                                          │   │
│  │       - 整理证据                                                    │   │
│  │       - 生成结构化答案                                              │   │
│  │       - 添加引用标记 [1][2][3]                                      │   │
│  │       - 附上图表                                                    │   │
│  │     输出：完整的回答 + 图表 + 引用来源                               │   │
│  │                                                                     │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
│  注意：搜索、URL解析、代码执行是 Tool（工具），不是 Agent                     │
│        通过 MCP 协议调用                                                    │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 四、MCP 协议详解

### 4.1 什么是 MCP

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                                                                             │
│                     MCP = Model Context Protocol                            │
│                        模型上下文协议                                        │
│                                                                             │
│  由 Anthropic（Claude 的公司）2024年底提出的开放协议                         │
│  目的：标准化 LLM 与外部工具/数据源的交互方式                                 │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  之前的问题：                                                                │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  • OpenAI 用 Function Calling                                       │   │
│  │  • Claude 用 Tool Use                                               │   │
│  │  • LangChain 用 Tool                                                │   │
│  │  • 每个工具实现方式都不一样                                          │   │
│  │  → 难以复用、难以扩展、生态碎片化                                    │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
│  MCP 解决方案：                                                             │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  • 统一的工具描述格式（JSON Schema）                                  │   │
│  │  • 统一的调用协议（JSON-RPC 2.0）                                    │   │
│  │  • 标准的 Server/Client 架构                                         │   │

### 5.1 为什么需要 RL

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                                                                             │
│                        为什么需要强化学习？                                  │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │

│  │  • 不需要人工设计复杂规则                                           │   │

### 5.2 MDP 建模详解

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                                                                             │
│                    马尔可夫决策过程 (MDP) 建模                               │
│                                                                             │
│  MDP = (S, A, P, R, γ)                                                     │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │                                                                     │   │
│  │  S - State（状态空间）                                               │   │
│  │  ════════════════════════════════════════════════════════════════   │   │
│  │                                                                     │   │
│  │  状态 s_t 由以下部分组成，总维度 1024：                              │   │
│  │                                                                     │   │
│  │  ┌───────────────────────────────────────────────────────────────┐ │   │
│  │  │ 1. 问题语义向量 (768维)                                       │ │   │
│  │  │    q_emb = BGE_encode(question)                               │ │   │
│  │  │    用 BGE-base-zh 将问题编码为稠密向量                         │ │   │
│  │  └───────────────────────────────────────────────────────────────┘ │   │
│  │                                                                     │   │
│  │  ┌───────────────────────────────────────────────────────────────┐ │   │
│  │  │ 2. 证据聚合向量 (128维)                                        │ │   │
│  │  │    evidence_emb = MeanPool([BGE_encode(doc) for doc in docs]) │ │   │
│  │  │    所有已收集文档的 embedding 平均池化后降维                    │ │   │
│  │  └───────────────────────────────────────────────────────────────┘ │   │
│  │                                                                     │   │
│  │  ┌───────────────────────────────────────────────────────────────┐ │   │
│  │  │ 3. 历史动作序列 (25维)                                         │ │   │
│  │  │    action_history = [one_hot(a_{t-5}), ..., one_hot(a_{t-1})] │ │   │
│  │  │    最近5步动作的 one-hot 编码拼接 (5个动作 × 5步 = 25维)       │ │   │
│  │  └───────────────────────────────────────────────────────────────┘ │   │
│  │                                                                     │   │
│  │  ┌───────────────────────────────────────────────────────────────┐ │   │
│  │  │ 4. 进度特征 (103维)                                            │ │   │
│  │  │    - step_count: 当前步数 / 最大步数                           │ │   │
│  │  │    - search_count: 已搜索次数 / 最大搜索次数                   │ │   │
│  │  │    - doc_count: 已获取文档数 / 最大文档数                      │ │   │
│  │  │    - info_sufficiency: 信息充分性得分 (LLM判断, 0-1)           │ │   │
│  │  │    - code_executed: 是否已执行过代码 (0/1)                     │ │   │
│  │  │    - cache_hit_rate: 记忆缓存命中率                            │ │   │
│  │  │    - ... 其他特征填充到103维                                   │ │   │
│  │  └───────────────────────────────────────────────────────────────┘ │   │
│  │                                                                     │   │
│  │  总维度: 768 + 128 + 25 + 103 = 1024                               │   │
│  │                                                                     │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │                                                                     │   │
│  │  A - Action（动作空间）                                              │   │
│  │  ════════════════════════════════════════════════════════════════   │   │
│  │                                                                     │   │
│  │  离散动作空间，共 5 个高层动作：                                     │   │
│  │                                                                     │   │
│  │  ┌─────────────────────────────────────────────────────────────┐   │   │
│  │  │ Action 0: SEARCH                                            │   │   │
│  │  │ 描述：搜索新的信息                                           │   │   │
│  │  │ 执行：Policy选中 → LLM生成关键词 → 调用webSearch工具         │   │   │
│  │  │ 适用：信息不足时                                             │   │   │
│  │  └─────────────────────────────────────────────────────────────┘   │   │
│  │                                                                     │   │
│  │  ┌─────────────────────────────────────────────────────────────┐   │   │
│  │  │ Action 1: READ_FULL                                         │   │   │
│  │  │ 描述：获取某文档的全文                                        │   │   │
│  │  │ 执行：Policy选中 → LLM选择文档ID → 调用urlParser工具         │   │   │
│  │  │ 适用：摘要信息不够详细时                                      │   │   │
│  │  └─────────────────────────────────────────────────────────────┘   │   │
│  │                                                                     │   │
│  │  ┌─────────────────────────────────────────────────────────────┐   │   │
│  │  │ Action 2: CODE                                              │   │   │
│  │  │ 描述：生成并执行Python代码                                    │   │   │
│  │  │ 执行：Policy选中 → LLM生成代码 → 调用codeRunner工具          │   │   │
│  │  │ 适用：需要计算、画图、数据处理时                              │   │   │
│  │  └─────────────────────────────────────────────────────────────┘   │   │
│  │                                                                     │   │
│  │  ┌─────────────────────────────────────────────────────────────┐   │   │
│  │  │ Action 3: ANSWER                                            │   │   │
│  │  │ 描述：生成最终答案，结束任务                                  │   │   │
│  │  │ 执行：Policy选中 → LLM生成答案 → 任务结束                    │   │   │
│  │  │ 适用：信息已经充分时                                         │   │   │
│  │  └─────────────────────────────────────────────────────────────┘   │   │
│  │                                                                     │   │
│  │  ┌─────────────────────────────────────────────────────────────┐   │   │
│  │  │ Action 4: REFINE                                            │   │   │
│  │  │ 描述：重新规划，调整策略                                      │   │   │
│  │  │ 执行：Policy选中 → LLM分析当前状态 → 调整后续计划            │   │   │
│  │  │ 适用：发现方向有问题需要调整时                                │   │   │
│  │  └─────────────────────────────────────────────────────────────┘   │   │
│  │                                                                     │   │
│  │  关键设计：RL 决定 what to do，LLM 决定 how to do                  │   │
│  │                                                                     │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │                                                                     │   │
│  │  R - Reward（奖励函数）                                              │   │
│  │  ════════════════════════════════════════════════════════════════   │   │
│  │                                                                     │   │
│  │  r_t = α·Q(quality) + β·E(efficiency) + γ·I(info_gain)             │   │
│  │                                                                     │   │
│  │  超参数: α=1.0, β=0.3, γ=0.2                                       │   │
│  │                                                                     │   │
│  │  ─────────────────────────────────────────────────────────────────  │   │
│  │                                                                     │   │
│  │  1. 答案质量 Q（终止时计算，主要奖励）                               │   │
│  │  ┌─────────────────────────────────────────────────────────────┐   │   │
│  │  │                                                             │   │   │
│  │  │  Q = 0.6 × Rouge_L(answer, reference)                       │   │   │
│  │  │    + 0.4 × GPT_score(answer, question) / 5.0                │   │   │
│  │  │                                                             │   │   │
│  │  │  - Rouge_L: 衡量答案与参考答案的文本重叠度                   │   │   │
│  │  │  - GPT_score: 用 GPT-4 从 1-5 评分答案质量                  │   │   │
│  │  │                                                             │   │   │
│  │  └─────────────────────────────────────────────────────────────┘   │   │
│  │                                                                     │   │
│  │  2. 效率惩罚 E（每步计算，鼓励用更少步骤）                           │   │
│  │  ┌─────────────────────────────────────────────────────────────┐   │   │
│  │  │                                                             │   │   │
│  │  │  action_cost = {                                            │   │   │
│  │  │      SEARCH:    -0.02,   # 搜索消耗 API                     │   │   │
│  │  │      READ_FULL: -0.05,   # 全文获取更贵                     │   │   │
│  │  │      CODE:      -0.03,   # 代码执行消耗资源                 │   │   │
│  │  │      ANSWER:     0.00,   # 回答不扣分                       │   │   │
│  │  │      REFINE:    -0.01,   # 规划消耗时间                     │   │   │
│  │  │  }                                                          │   │   │
│  │  │                                                             │   │   │
│  │  │  E = action_cost[action]                                    │   │   │
│  │  │                                                             │   │   │
│  │  └─────────────────────────────────────────────────────────────┘   │   │
│  │                                                                     │   │
│  │  3. 信息增益 I（SEARCH/READ_FULL 时计算）                           │   │
│  │  ┌─────────────────────────────────────────────────────────────┐   │   │
│  │  │                                                             │   │   │
│  │  │  new_emb = BGE_encode(new_docs)                             │   │   │
│  │  │  old_emb = state.evidence_embedding                         │   │   │
│  │  │  similarity = cosine_similarity(new_emb, old_emb)           │   │   │
│  │  │                                                             │   │   │
│  │  │  I = 1.0 - similarity   # 相似度低 = 新信息多 = 增益高      │   │   │
│  │  │                                                             │   │   │
│  │  │  作用：鼓励获取真正新的信息，避免重复搜索                    │   │   │
│  │  │                                                             │   │   │
│  │  └─────────────────────────────────────────────────────────────┘   │   │
│  │                                                                     │   │
│  │  4. 代码执行奖励（CODE 动作时）                                      │   │
│  │  ┌─────────────────────────────────────────────────────────────┐   │   │
│  │  │                                                             │   │   │
│  │  │  if code_success:                                           │   │   │
│  │  │      bonus = +0.1                                           │   │   │
│  │  │  else:                                                      │   │   │
│  │  │      bonus = -0.05                                          │   │   │
│  │  │                                                             │   │   │
│  │  └─────────────────────────────────────────────────────────────┘   │   │
│  │                                                                     │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

### 5.4 GRPO 训练算法详解

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                                                                             │
│                    GRPO (Group Relative Policy Optimization)                │
│                                                                             │
│  DeepSeek 在训练 R1 时提出的算法，用于直接对 LLM 进行强化学习对齐            │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │                                                                     │   │
│  │  核心思想：对同一 Prompt 生成多个 Response，用组内排名估计优势       │   │
│  │                                                                     │   │
│  │  ─────────────────────────────────────────────────────────────────  │   │
│  │                                                                     │   │
│  │  与 PPO 的区别：                                                     │   │
│  │  • PPO 需要 Critic 网络估计 V(s)，GRPO 不需要                       │   │
│  │  • PPO 用 GAE 估计 advantage，GRPO 用组内相对排名                   │   │
│  │  • GRPO 更适合 LLM 场景（生成式任务）                               │   │
│  │                                                                     │   │
│  │  与 DPO 的区别：                                                     │   │
│  │  • DPO 是离线算法，需要预先准备好偏好对数据                         │   │
│  │  • GRPO 是在线算法，边生成边训练                                    │   │
│  │  • GRPO 可以学习更复杂的多步决策                                    │   │
│  │                                                                     │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  训练流程（一次迭代）：                                                      │
│                                                                             │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │                                                                     │   │
│  │  Step 1: 生成多个 Response                                          │   │
│  │  ════════════════════════════════════════════════════════════════   │   │
│  │                                                                     │   │
│  │  对同一个 Prompt（状态描述），让 LLM 生成 N=4 个不同的 Response：    │   │
│  │                                                                     │   │
│  │  Prompt: "用户问题: BERT预训练方法？当前状态: 已搜索0次..."         │   │
│  │                                                                     │   │
│  │  Response_1: "A. SEARCH\n理由：需要先搜索相关论文..."  → R_1 = 0.8  │   │
│  │  Response_2: "D. ANSWER\n答案：BERT是..."             → R_2 = 0.2  │   │
│  │  Response_3: "A. SEARCH\n理由：信息不足..."           → R_3 = 0.75 │   │
│  │  Response_4: "C. CODE\n生成代码..."                   → R_4 = 0.1  │   │
│  │                                                                     │   │
│  │  R_i 是该 Response 执行后获得的奖励                                 │   │
│  │                                                                     │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │                                                                     │   │
│  │  Step 2: 计算组内相对优势                                            │   │
│  │  ════════════════════════════════════════════════════════════════   │   │
│  │                                                                     │   │
│  │  rewards = [0.8, 0.2, 0.75, 0.1]                                    │   │
│  │  mean = 0.46, std = 0.33                                            │   │
│  │                                                                     │   │
│  │  A_1 = (0.8 - 0.46) / 0.33 = +1.03   ← 好 Response，增加概率       │   │
│  │  A_2 = (0.2 - 0.46) / 0.33 = -0.79   ← 差 Response，降低概率       │   │
│  │  A_3 = (0.75 - 0.46) / 0.33 = +0.88  ← 较好，增加概率              │   │
│  │  A_4 = (0.1 - 0.46) / 0.33 = -1.09   ← 最差，大幅降低概率          │   │
│  │                                                                     │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │                                                                     │   │
│  │  Step 3: 更新 LLM 参数（LoRA）                                       │   │
│  │  ════════════════════════════════════════════════════════════════   │   │
│  │                                                                     │   │
│  │  Loss = - Σ_i A_i · log P(Response_i | Prompt)                      │   │
│  │                                                                     │   │
│  │  直觉理解：                                                          │   │
│  │  • A_i > 0: 增加该 Response 的生成概率                              │   │
│  │  • A_i < 0: 降低该 Response 的生成概率                              │   │
│  │                                                                     │   │
│  │  经过训练，LLM 学会：                                                │   │
│  │  • 在"已搜索0次"的状态下，优先选择 SEARCH                           │   │
│  │  • 在"信息充分"的状态下，优先选择 ANSWER                            │   │
│  │  • 避免在不需要代码时选择 CODE                                      │   │
│  │                                                                     │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**核心工作**：
- **多 Agent 协作框架**：设计 7 个功能 Agent 分工协作，包括任务编排、流程优化、文档筛选、充分性验证、动态重规划、代码生成、答案撰写，基于 MCP 协议实现 Agent 与工具层的标准化交互
- **强化学习决策优化**：将任务流程建模为 MDP，设计 1024 维状态向量融合问题语义、证据聚合与历史轨迹，定义 5 类高层动作由 Policy Network 决策；设计多目标奖励函数综合答案质量、效率成本与信息增益；基于 GRPO 算法训练策略网络，采用组内相对排名估计 advantage 无需 Critic 网络
- **检索增强与记忆机制**：引入 BGE-Reranker 对候选文献重排序，设计三层记忆模块支持对话历史追踪、检索缓存复用与实体指代消解

**项目成果**：构造 800 余条科研问答数据，涵盖事实检索、多步推理、数据分析等场景，RL 策略相比规则基线将任务完成率从 68% 提升至 79%，检索重排使 Top-5 相关性命中率从 58% 提升至 82%，记忆缓存使 API 调用减少 27%，端到端响应时间降低 34%

## 十、面试 Q&A

### Agent 部分

**Q：7个Agent具体怎么分工的？**

> "7个Agent各司其职：Orchestrator 做任务规划，判断需不需要搜索和代码；Optimizer 优化搜索关键词；Selector 配合 BGE-Reranker 筛选相关文档；SufficiencyValidator 判断摘要够不够详细；Reorchestrator 动态调整后续计划；CodeAgent 生成代码；AssistantAgent 生成最终答案。搜索本身不是Agent，是通过MCP调用的Tool。"

**Q：MCP是什么？为什么用它？**

> "MCP 是 Anthropic 提出的开放协议，用于标准化 LLM 和工具的交互。好处是解耦——Agent 不需要知道工具怎么实现，只要按 MCP 格式调用。新增工具只要实现 MCP 接口就能接入，扩展性很好。"

### RL 部分

**Q：为什么用RL？**

> "因为科研问答是序贯决策问题，每一步要决定是继续搜索还是回答。规则太死，有些问题搜1次就够，有些要搜5次。用RL可以从数据中学习最优策略，根据当前状态自动决策。"

**Q：状态怎么设计的？**

> "1024维向量，四部分：768维的问题语义向量用BGE编码；128维的证据聚合向量是所有文档embedding的池化；25维的历史动作是最近5步的one-hot；剩下的是进度特征，比如步数、搜索次数、信息充分性得分。"

**Q：GRPO和PPO有什么区别？**

> "核心区别是 GRPO 不需要 Critic。PPO 要训练 Critic 估计 V(s)，但 Critic 很难拟合准确。GRPO 的做法是对同一个问题采样多条轨迹，用组内相对排名估计 advantage。数学上是无偏估计，实现更简单，DeepSeek 训练 R1 就是用这个方法。"

**Q：奖励函数怎么设计的？**

> "多目标加权：质量是主要奖励，用Rouge和GPT评分；效率是惩罚，每次API调用扣分；信息增益鼓励获取新信息，用新旧文档的语义相似度估计。权重通过验证集调优，确保不会为了省步骤牺牲质量。"

**Q：训练数据哪来的？**

> "三个来源：300条人工构造的，覆盖检索、推理、分析等场景；250条从GAIA、HotpotQA等公开benchmark翻译改造；250条用GPT-4生成再人工校验。总共800多条，按7:1:1.5划分训练、验证、测试集。"
