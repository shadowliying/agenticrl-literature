#### Q1: 一句话介绍你的项目？

**答**：这是一个用强化学习优化的科研检索 Agent 系统。核心创新是用 GRPO 算法微调 Qwen2.5-7B 作为决策模型，让它学会在检索过程中做出最优决策，相比规则基线提升了 11% 的完成率，同时减少了 33% 的搜索次数。

#### Q2: 做这个项目遇到的最大挑战是什么？

**答**：最大的挑战是**奖励函数的设计**。

**问题**：
- 最初只用最终用户满意度作为奖励，导致奖励稀疏，模型学不动
- 后来加了太多中间奖励，模型学会了"刷分"但实际效果差

**解决过程**：
1. 先分析了 100 条轨迹，理解什么是"好的决策"
2. 设计了三维度奖励：质量(α=1.0) + 效率(β=0.3) + 信息增益(γ=0.2)
3. 用消融实验验证每个奖励项的贡献
4. 最终找到了平衡点

**收获**：奖励函数设计是 RL 最难的部分，需要结合业务理解和实验验证。

### 5.2 技术深度问题

#### Q6: 为什么用 GRPO 而不是 PPO？

**答**：

| 对比 | PPO | GRPO |
|------|-----|------|
| 需要 Critic？ | 需要额外训练一个价值网络 | 不需要 |
| 优势计算 | A = Q - V（需要估计 V） | A = (R - 均值) / 标准差（组内比较） |
| 显存需求 | 约 60GB | 约 30GB |
| 实现复杂度 | 较高 | 较低 |

选 GRPO 的原因：
1. **资源限制**：A100-40G 跑 PPO 会 OOM，GRPO 刚好够用
2. **与 LLM 兼容**：GRPO 是 DeepSeek 专门为 LLM 微调设计的
3. **实现简单**：trl 库支持好

---

#### Q7: LoRA 的 r 和 alpha 是怎么选的？

**答**：

**r=16, alpha=32**

选择依据：
1. **r 的选择**：
   - r=8 太小，容量不够
   - r=32 太大，训练慢
   - r=16 是经验值，平衡容量和效率

2. **alpha 的选择**：
   - 经验公式：alpha = 2 × r
   - 这样缩放因子 alpha/r = 2，梯度稳定

3. **验证**：
   - 对比了 r=8/16/32，发现 r=16 在验证集上最优

---

#### Q8: 奖励函数的三个系数是怎么调的？

**答**：

**α=1.0, β=0.3, γ=0.2**

调参过程：
1. **初始设置**：α=1, β=1, γ=1（等权重）
2. **问题**：模型过度追求效率，牺牲质量
3. **调整**：提高质量权重，降低效率权重
4. **最终**：通过网格搜索找到 α=1.0, β=0.3, γ=0.2

验证方法：
```
α:β:γ     | 完成率 | 平均步数 | 备注
1:1:1     | 72%    | 2.1      | 步数少但质量差
1:0.1:0.1 | 78%    | 4.5      | 质量好但步数多
1:0.3:0.2 | 79%    | 2.8      | 最佳平衡 ✓
```

#### Q9: Memory 的缓存命中阈值 0.85 是怎么来的？

**答**：

**实验得出的最佳阈值**。

```
阈值  | 命中率 | 误命中率 | 说明
0.95 | 12%    | 1%      | 太严格，命中太少
0.90 | 18%    | 3%      | 偏严格
0.85 | 27%    | 5%      | 最佳平衡 ✓
0.80 | 35%    | 12%     | 误命中太多
0.75 | 42%    | 20%     | 不可接受
```

选择 0.85 的原因：
- 命中率 27% 已经能显著节省成本
- 误命中率 5% 可以接受（用户基本察觉不到）

#### Q10: 如果缓存返回了错误结果怎么办？

## MDP 是什么？

**MDP = Markov Decision Process（马尔可夫决策过程）**

是强化学习的**数学框架**，用来描述"在不确定环境中做序贯决策"的问题。

### MDP 五元组

$$MDP = (S, A, P, R, \gamma)$$

| 符号 | 名称 | 含义 |
|------|------|------|
| **S** | 状态空间 (State) | 环境可能处于的所有状态 |
| **A** | 动作空间 (Action) | 智能体可以采取的所有动作 |
| **P** | 转移概率 (Transition) | 执行动作后，状态如何变化 |
| **R** | 奖励函数 (Reward) | 执行某动作后获得的奖励 |
| **γ** | 折扣因子 (Gamma) | 未来奖励的重要程度（0-1） |

### 马尔可夫性质

**下一个状态只取决于当前状态和动作，与历史无关**：

$$P(S_{t+1} | S_t, A_t, S_{t-1}, A_{t-1}, ...) = P(S_{t+1} | S_t, A_t)$$

通俗理解：**"过去的事不影响未来，只有现在决定未来"**

## 本项目的 MDP 建模

### S：状态空间

**当前检索的"局面"是什么？**

```
状态 S = {
    query:           用户问题（文本）
    search_count:    已搜索次数（0, 1, 2, ...）
    result_quality:  当前结果质量（"无"/"差"/"一般"/"较好"/"好"）
    evidence:        已收集的证据摘要
    cache_hit:       是否命中缓存（True/False）
    history:         最近几轮对话
    entities:        识别出的实体（用于指代消解）
}
```

**在本项目中的实现**：状态被编码成**文本 Prompt** 给 LLM：

```
你是一个科研文献检索助手，需要决定下一步动作。

【用户问题】
BERT 的预训练方法是什么？

【当前状态】
- 已搜索次数: 1
- 当前结果质量: 一般
- 缓存命中: 否

【已有检索结果摘要】
找到 5 篇相关文章，但缺少 MLM 细节...

【可选动作】
1. SEARCH: 发起新搜索
2. REFINE: 优化搜索词重新搜索
3. READ_FULL: 深读某篇全文
4. ANSWER: 生成最终答案
5. CODE: 执行代码

请选择下一步动作:
```

### A：动作空间

**智能体可以做什么？**

| 动作 | 含义 | 触发时机 |
|------|------|----------|
| `SEARCH` | 发起新的网络搜索 | 信息不足，需要更多资料 |
| `REFINE` | 优化搜索词重新搜索 | 搜索结果质量差 |
| `READ_FULL` | 深读某篇文章全文 | 摘要不够，需要细节 |
| `ANSWER` | 生成最终答案 | 信息充分，可以回答 |
| `CODE` | 生成/执行代码 | 用户要求画图、计算等 |

### P：状态转移

**执行动作后，状态怎么变化？**

```
P(S' | S, A) = 执行动作 A 后，从状态 S 转移到 S' 的概率

示例：
- 状态 S: search_count=0, quality="无"
- 动作 A: SEARCH
- 状态 S': search_count=1, quality="较好"（如果搜到好结果）
         或 search_count=1, quality="差"（如果搜不到）
```

**本项目的特点**：
- 转移**部分随机**：搜索结果质量不确定
- 但大部分是**确定的**：search_count 一定 +1

### R：奖励函数

**这个动作好不好？**

$$R = \alpha \cdot Q + \beta \cdot E + \gamma \cdot I$$

| 奖励项 | 权重 | 计算方式 |
|--------|------|----------|
| Q (质量) | α=1.0 | 答案准确性、用户满意度 |
| E (效率) | β=0.3 | -0.05 × 搜索次数，缓存命中 +0.1 |
| I (信息增益) | γ=0.2 | 新覆盖的关键词数量 |

**具体奖励设计**：

```python
def compute_reward(state, action, result):
    reward = 0.0
    
    # 效率惩罚（每个动作都有成本）
    action_cost = {
        "SEARCH": -0.05,
        "REFINE": -0.05,
        "READ_FULL": -0.08,
        "ANSWER": 0.0,
        "CODE": -0.03,
    }
    reward += action_cost[action]
    
    # 质量奖励（最终回答时）
    if action == "ANSWER":
        if user_satisfied:
            reward += 1.0
        elif partially_correct:
            reward += 0.5
    
    # 缓存命中奖励
    if result.get("cache_hit"):
        reward += 0.1
    
    # 信息增益
    if action in ["SEARCH", "READ_FULL"]:
        new_info = len(result.get("new_keywords", []))
        reward += 0.1 * min(new_info, 3)
    
    return reward
```

### γ：折扣因子

**未来奖励有多重要？**

$$\gamma = 0.99$$

- γ = 0：只看当前奖励（短视）
- γ = 1：未来和现在同等重要
- γ = 0.99：略微偏好早点拿到奖励

**本项目用 0.99**：因为我们希望模型学会"为了最终的好答案，前期多搜几次是值得的"。

## 训练时的质量评估（三种方法）

### 方法 1：规则判断（简单场景）

```python
def rule_based_quality(query, answer, search_results):
    """规则评估答案质量"""
    score = 0.0
    
    # 1. 答案长度合理
    if 100 < len(answer) < 2000:
        score += 0.2
    
    # 2. 引用了搜索结果中的来源
    sources_cited = sum(1 for s in search_results if s['title'] in answer)
    if sources_cited >= 2:
        score += 0.3
    
    # 3. 关键词覆盖（query 中的关键词出现在答案中）
    query_keywords = extract_keywords(query)
    covered = sum(1 for kw in query_keywords if kw in answer)
    score += 0.3 * (covered / len(query_keywords))
    
    # 4. 没有"我不知道"等拒答
    if "抱歉" not in answer and "无法回答" not in answer:
        score += 0.2
    
    return score  # 0-1 之间
```

### 方法 2：LLM-as-Judge（更准确）

```python
def llm_evaluate_quality(query, answer, reference=None):
    """用 LLM 评估答案质量"""
    
    prompt = f"""你是一个答案质量评估专家。

用户问题: {query}

系统回答: {answer}

{"参考答案: " + reference if reference else ""}

请从以下维度评分（每项 0-1 分）：
1. 准确性：答案是否事实正确
2. 完整性：是否覆盖问题的所有方面
3. 相关性：是否切题

只输出一个 0-1 之间的总分，不要输出其他内容。"""
    
    response = evaluator_llm.generate(prompt, max_tokens=10)
    
    try:
        score = float(response.strip())
        return max(0, min(1, score))  # 限制在 0-1
    except:
        return 0.5  # 解析失败给默认分
```

### 方法 3：与参考答案对比（有标注时）

```python
def reference_based_quality(answer, reference_answer, key_points):
    """与参考答案对比"""
    
    # 1. ROUGE-L 相似度
    rouge_score = compute_rouge_l(answer, reference_answer)
    
    # 2. 关键点命中率
    hits = sum(1 for kp in key_points if kp.lower() in answer.lower())
    key_point_score = hits / len(key_points)
    
    # 加权
    return 0.4 * rouge_score + 0.6 * key_point_score
```

## 本项目实际用的方案

**规则（70%）+ LLM 评估（30%）**

```python
def compute_quality_reward(state, action, result):
    """训练时的质量奖励计算"""
    
    if action != "ANSWER":
        return 0.0  # 非回答动作，质量奖励为 0
    
    query = state["query"]
    answer = result["answer"]
    search_results = state["evidence"]
    
    # ===== 规则部分 (70%) =====
    rule_score = 0.0
    
    # 答案非空且长度合理
    if answer and 50 < len(answer) < 3000:
        rule_score += 0.3
    
    # 引用了搜索结果
    if any(s["title"][:20] in answer for s in search_results[:3]):
        rule_score += 0.3
    
    # 覆盖了 query 关键词
    keywords = jieba.analyse.extract_tags(query, topK=5)
    covered = sum(1 for kw in keywords if kw in answer)
    rule_score += 0.4 * (covered / max(len(keywords), 1))
    
    # ===== LLM 评估部分 (30%) =====
    llm_score = llm_evaluate_quality(query, answer)
    
    # ===== 加权求和 =====
    Q = 0.7 * rule_score + 0.3 * llm_score
    
    return Q
```

## 可能的追问

**Q: 用 LLM 评估 LLM 的输出，不会有偏差吗？**

> "会有一定偏差，所以我们：
> 1. LLM 评估只占 30%，不是主导
> 2. 用不同的 LLM 做评估（训练用 Qwen，评估用 DeepSeek）
> 3. 定期人工抽检，校准 LLM 评估的准确性
> 
> 这是 LLM-as-Judge 的常见做法，OpenAI 和 Anthropic 也这么用。"

**Q: 为什么不全用 LLM 评估？**

> "两个原因：
> 1. **成本**：每个 sample 都调一次 LLM 太贵
> 2. **速度**：训练时要快速迭代，规则判断几乎零延迟
> 
> 规则处理 80% 的简单情况，LLM 处理 20% 需要语义理解的情况。"

**Q: 如果模拟奖励和真实用户反馈差很多怎么办？**

> "这确实是风险。我们的应对：
> 1. **上线前**：人工评估 50 条，确认模拟奖励和人类判断相关性 > 0.8
> 2. **上线后**：收集真实反馈，如果差异大就更新奖励函数
> 3. **持续学习**：用真实反馈数据做 fine-tuning 迭代"

## 补充：完整的奖励计算代码

```python
def compute_reward(state, action, result, is_terminal=False):
    """完整的奖励函数"""
    
    # ===== 1. 效率奖励 E (每步都有) =====
    action_cost = {
        "SEARCH": -0.05,
        "REFINE": -0.05, 
        "READ_FULL": -0.08,
        "CODE": -0.03,
        "ANSWER": 0.0,
    }
    E = action_cost.get(action, 0)
    
    # 缓存命中奖励
    if result.get("cache_hit"):
        E += 0.2
    
    # ===== 2. 信息增益 I (搜索/阅读时) =====
    I = 0.0
    if action in ["SEARCH", "READ_FULL", "REFINE"]:
        new_keywords = result.get("new_keywords", [])
        I = 0.1 * min(len(new_keywords), 3)
    
    # ===== 3. 质量奖励 Q (回答时) =====
    Q = 0.0
    if action == "ANSWER" and is_terminal:
        # 规则评估
        rule_score = rule_based_quality(
            state["query"], 
            result["answer"],
            state["evidence"]
        )
        
        # LLM 评估（可选，训练时可能关闭以加速）
        if USE_LLM_EVAL:
            llm_score = llm_evaluate_quality(state["query"], result["answer"])
            Q = 0.7 * rule_score + 0.3 * llm_score
        else:
            Q = rule_score
    
    # ===== 加权求和 =====
    alpha, beta, gamma = 1.0, 0.3, 0.2
    reward = alpha * Q + beta * E + gamma * I
    
    return reward
```
已汇总会话历史记录## 多维度奖励设计详解

我们项目的奖励函数采用**三维度加权设计**：

$$R_{total} = \alpha \cdot R_{quality} + \beta \cdot R_{efficiency} + \gamma \cdot R_{info\_gain}$$

其中权重：$\alpha=1.0$，$\beta=0.3$，$\gamma=0.2$

---

### 📊 维度一：质量奖励 $R_{quality}$（权重 1.0）

**目标**：确保最终答案的准确性和完整性

**计算方式**：规则评分（70%）+ LLM 评分（30%）

```python
def compute_quality_reward(answer, query, retrieved_docs):
    # 规则评分 (0-1)
    rule_score = 0.0
    
    # 1. 引用检查：答案是否引用了检索到的文献
    if has_citations(answer, retrieved_docs):
        rule_score += 0.25
    
    # 2. 完整性：是否覆盖了问题的关键方面
    key_aspects = extract_key_aspects(query)
    coverage = count_covered(answer, key_aspects) / len(key_aspects)
    rule_score += 0.25 * coverage
    
    # 3. 长度合理性：不能太短也不能太长
    length_score = length_penalty(answer, min_len=200, max_len=2000)
    rule_score += 0.20 * length_score
    
    # LLM 评分 (0-1)
    llm_score = llm_as_judge(query, answer, retrieved_docs)
    
    # 综合
    return 0.7 * rule_score + 0.3 * llm_score
```

**评分细则**：
| 指标 | 权重 | 评判标准 |
|------|------|----------|
| 引用规范 | 25% | 答案中是否正确引用了文献来源 |
| 问题覆盖 | 25% | 是否回答了问题的所有关键方面 |
| 长度合理 | 20% | 200-2000字符为合理区间 |
| LLM评判 | 30% | DeepSeek 对答案质量的综合评分 |

---

### ⚡ 维度二：效率奖励 $R_{efficiency}$（权重 0.3）

**目标**：鼓励用更少的步骤完成任务，避免无效检索

**计算方式**：

```python
def compute_efficiency_reward(trajectory):
    num_steps = len(trajectory)
    num_search = count_action(trajectory, "SEARCH")
    num_refine = count_action(trajectory, "REFINE")
    
    # 基础效率分：步数越少越好
    if num_steps <= 3:
        step_score = 1.0
    elif num_steps <= 5:
        step_score = 0.8
    elif num_steps <= 8:
        step_score = 0.5
    else:
        step_score = 0.2  # 惩罚过长的探索
    
    # 搜索效率：有效搜索比例
    if num_search > 0:
        useful_search = count_useful_search(trajectory)  # 返回了有价值结果的搜索
        search_efficiency = useful_search / num_search
    else:
        search_efficiency = 0.0
    
    # 避免无意义的 REFINE 循环
    refine_penalty = max(0, 1 - 0.2 * max(0, num_refine - 2))
    
    return 0.4 * step_score + 0.4 * search_efficiency + 0.2 * refine_penalty
```

**设计思想**：
- ✅ 3步内完成 → 满分
- ⚠️ 5-8步 → 轻微惩罚
- ❌ 超过8步 → 明显惩罚
- ❌ 重复REFINE超过2次 → 惩罚（说明策略在"打转"）

---

### 📈 维度三：信息增益奖励 $R_{info\_gain}$（权重 0.2）

**目标**：鼓励每一步都带来新的有价值信息

**计算方式**：

```python
def compute_info_gain_reward(trajectory, memory_state):
    total_gain = 0.0
    
    for i, step in enumerate(trajectory):
        if step.action == "SEARCH":
            # 检索到的文档与已有知识的新颖度
            new_docs = step.result
            existing_knowledge = memory_state.get_all_docs()
            
            novelty = compute_novelty(new_docs, existing_knowledge)
            relevance = compute_relevance(new_docs, step.query)
            
            # 新颖且相关才是好的信息增益
            step_gain = novelty * relevance
            total_gain += step_gain
            
            # 更新 memory
            memory_state.add_docs(new_docs)
            
        elif step.action == "READ_FULL":
            # 精读带来的深度信息
            full_content = step.result
            summary = memory_state.get_summary(step.doc_id)
            
            # 全文比摘要多了多少有价值信息
            depth_gain = compute_depth_gain(full_content, summary)
            total_gain += depth_gain * 0.5  # 精读权重稍低
    
    # 归一化到 [0, 1]
    return min(1.0, total_gain / len(trajectory))
```

**核心指标**：
| 指标 | 含义 |
|------|------|
| Novelty（新颖度）| 检索结果与已有知识的差异程度 |
| Relevance（相关性）| 检索结果与当前问题的相关程度 |
| Depth Gain（深度增益）| 精读全文相比摘要带来的额外信息 |

---

### 🎯 为什么这样设计权重？

```
质量(1.0) >> 效率(0.3) > 信息增益(0.2)
```

**权重设计理由**：

1. **质量最重要（1.0）**
   - 这是科研问答系统的核心目标
   - 答案质量差，其他做得再好也没意义

2. **效率次之（0.3）**
   - 用户体验：快速响应
   - 成本控制：减少 API 调用
   - 但不能为了效率牺牲质量

3. **信息增益辅助（0.2）**
   - 防止"无效检索"（搜了但没用）
   - 鼓励探索新知识
   - 权重最低，因为这是过程指标而非结果指标

### 🔄 奖励计算时机

```python
def compute_episode_reward(trajectory, final_answer, query):
    """
    一个完整 episode 结束后计算总奖励
    """
    # 只有 ANSWER 动作后才计算完整奖励
    if trajectory[-1].action != "ANSWER":
        return -1.0  # 未完成任务的惩罚
    
    # 三维度奖励
    r_quality = compute_quality_reward(final_answer, query, ...)
    r_efficiency = compute_efficiency_reward(trajectory)
    r_info_gain = compute_info_gain_reward(trajectory, ...)
    
    # 加权求和
    total_reward = 1.0 * r_quality + 0.3 * r_efficiency + 0.2 * r_info_gain
    
    # 归一化到合理范围
    return total_reward  # 范围大约 [0, 1.5]
```

### 📋 面试回答模板

> **面试官**："说说你们的奖励函数是怎么设计的？"

**回答**：

"我们采用**三维度加权奖励**：$R = 1.0 \cdot Q + 0.3 \cdot E + 0.2 \cdot I$

- **Q（质量）权重最高**，用规则评分（引用、覆盖、长度）占70%，加上LLM-as-Judge占30%来评估
- **E（效率）权重0.3**，鼓励用更少步骤完成，惩罚超过8步或反复REFINE的行为
- **I（信息增益）权重0.2**，评估每次检索带来的新颖且相关的信息量

权重这样设计是因为：**质量是目标，效率是约束，信息增益是过程优化**。

训练时没有真实用户反馈，所以质量评分是**模拟的**——规则保证基本面，LLM保证语义理解。上线后会用真实反馈做持续优化。"
