## 📚 Part 1: 基础知识讲解

### 1. 为什么科研检索需要 RL？

传统检索系统是**规则驱动**的：
```
if 结果不够 → 重新搜索
if 结果太多 → 过滤
```

问题：规则无法覆盖所有场景，且无法学习用户偏好。

**RL 的价值**：让系统学会"什么时候该搜索、什么时候该深挖、什么时候该停止"。

| 对比 | 规则系统 | RL 系统 |
|------|----------|---------|
| 决策依据 | 人工规则 | 学习到的策略 |
| 适应性 | 固定 | 自适应 |
| 优化目标 | 难以量化 | Reward 函数 |
| 复杂场景 | 规则爆炸 | 自动处理 |

### 2. MDP 建模：把检索过程变成决策问题

#### 2.1 什么是 MDP？

**马尔可夫决策过程（MDP）** 是 RL 的数学框架：

```
MDP = (S, A, P, R, γ)

S: 状态空间 - 当前检索的"局面"是什么
A: 动作空间 - 可以采取什么操作
P: 转移概率 - 执行动作后状态如何变化
R: 奖励函数 - 这个动作好不好
γ: 折扣因子 - 未来奖励的重要程度
```

#### 2.2 本项目的 MDP 建模

```
┌─────────────────────────────────────────────────────────────┐
│                     状态 State (1024维)                      │
├─────────────────────────────────────────────────────────────┤

### 4. GRPO 算法详解

#### 4.1 为什么选择 GRPO？

| 算法 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| PPO | 稳定、成熟 | 需要 Critic 网络 | 通用 RL |
| DPO | 简单、无需 RL | 只能做偏好学习 | LLM 对齐 |
| **GRPO** | 无需 Critic、适合 LLM | 相对较新 | **LLM Agent** |

**GRPO (Group Relative Policy Optimization)** 是 DeepSeek 提出的算法：
- 不需要 Critic 网络（省一半参数）
- 用组内相对排名替代绝对价值估计
- 特别适合 LLM-based Agent

#### 4.2 GRPO 核心思想

```
传统 PPO：
  Advantage = Q(s,a) - V(s)  ← 需要训练 Critic 网络估计 V(s)

GRPO：
  Advantage = (R - mean(R_group)) / std(R_group)  ← 用组内统计量替代
```

**直观理解**：
- 采样一组动作（比如 8 个）
- 计算每个动作的 Reward
- 高于平均的动作增加概率，低于平均的减少概率

#### 4.3 GRPO 算法伪代码（LLM 微调版本）

```python
def grpo_update(model, tokenizer, prompts, group_size=4):
    """
    GRPO 训练 LLM 的核心逻辑
    - model: Qwen2.5-7B + LoRA
    - prompts: 状态描述的文本
    - group_size: 每个 prompt 采样多少个 response
    """
    for prompt in prompts:
        # 1. 采样一组 response（动作选择 + 理由）
        responses = []
        for _ in range(group_size):
            output = model.generate(prompt, do_sample=True, temperature=0.7)
            responses.append(output)
        
        # 2. 计算每个 response 的 Reward
        rewards = []
        for response in responses:
            action = parse_action(response)  # 从 response 中解析出动作
            reward = execute_and_evaluate(action)  # 执行动作并评估
            rewards.append(reward)
        
        # 3. 计算组内相对优势
        mean_r = np.mean(rewards)
        std_r = np.std(rewards) + 1e-8
        advantages = [(r - mean_r) / std_r for r in rewards]
        
        # 4. 策略梯度更新（只更新 LoRA 参数）
        for response, advantage in zip(responses, advantages):
            log_prob = compute_log_prob(model, prompt, response)
            loss = -log_prob * advantage
            loss.backward()
        
        optimizer.step()
```

#### 4.4 与 PPO/DPO 的关键区别

| 算法 | Advantage 计算 | 参考模型 | 适用场景 |
|------|---------------|---------|----------|
| PPO | $A = r + \gamma V(s') - V(s)$ | 需要 Critic 网络 | 通用 RL |
| DPO | 隐式（偏好对比） | 需要参考模型 | 偏好对齐 |
| **GRPO** | $A = \frac{r - \mu_G}{\sigma_G}$ | **无需额外模型** | **LLM Agent** |

**GRPO 的优势**：
```python
# DPO 需要冻结参考模型计算 KL 散度
loss_dpo = -log(sigmoid(beta * (log_pi - log_pi_ref)))

# GRPO 直接用组内统计量，无需参考模型
advantages = (rewards - rewards.mean()) / rewards.std()
loss_grpo = -log_probs * advantages
```

### 5. 奖励函数设计

#### 5.1 多目标奖励

```python
def compute_reward(trajectory):
    reward = 0.0
    
    # 1. 结果质量奖励
    if user_satisfied:
        reward += 1.0
    elif found_relevant_paper:
        reward += 0.5
    
    # 2. 效率惩罚
    reward -= 0.1 * search_count      # 搜索成本
    reward -= 0.05 * api_calls        # API 调用成本
    reward -= 0.01 * total_tokens     # Token 成本
    
    # 3. 时间惩罚
    if elapsed_time > 30:  # 超过 30 秒
        reward -= 0.3
    
    # 4. 多样性奖励
    if len(unique_sources) >= 3:
        reward += 0.2
    
    return reward
```

#### 5.2 奖励塑形（Reward Shaping）

```python
def shaped_reward(state, action, next_state):
    # 基础奖励
    base_reward = compute_reward(...)
    
    # 塑形奖励：引导探索
    shaping = 0.0
    
    # 鼓励早期多搜索
    if state['search_count'] < 2 and action == 'web_search':
        shaping += 0.1
    
    # 鼓励后期收敛
    if state['search_count'] >= 3 and action == 'generate_answer':
        shaping += 0.1
    
    # 惩罚重复动作
    if action == state['last_action']:
        shaping -= 0.1
    
    return base_reward + shaping
```

### 6. 决策模型结构（Qwen2.5-7B + LoRA）

```python
from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import get_peft_model, LoraConfig, TaskType

def build_decision_model():
    """
    构建决策模型：Qwen2.5-7B + LoRA
    """
    # 1. 加载基座模型
    base_model = AutoModelForCausalLM.from_pretrained(
        "Qwen/Qwen2.5-7B-Instruct",
        torch_dtype=torch.bfloat16,
        device_map="auto",
    )
    tokenizer = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-7B-Instruct")
    
    # 2. 配置 LoRA
    lora_config = LoraConfig(
        task_type=TaskType.CAUSAL_LM,
        r=16,                         # LoRA 秩
        lora_alpha=32,                # 缩放系数
        target_modules=[              # 应用 LoRA 的层
            "q_proj", "k_proj", "v_proj", "o_proj",
            "gate_proj", "up_proj", "down_proj"
        ],
        lora_dropout=0.05,
    )
    
    # 3. 应用 LoRA
    model = get_peft_model(base_model, lora_config)
    model.print_trainable_parameters()
    # 输出: trainable params: 20,971,520 || all params: 7,615,616,000 || trainable%: 0.275%
    
    return model, tokenizer


# 状态编码为文本 Prompt
STATE_PROMPT_TEMPLATE = """
你是一个科研文献检索助手，需要决定下一步动作。

【用户问题】
{query}

【当前状态】
- 已搜索次数: {search_count}
- 已深读文章数: {deep_read_count}
- 已用时间: {elapsed_time}秒

【已有检索结果】
{search_results}

【可选动作】
1. SEARCH: 发起新的网络搜索
2. READ_FULL: 深入阅读某篇文章全文
3. CODE: 执行代码（数据分析、绘图等）
4. ANSWER: 生成最终答案
5. REFINE: 优化搜索词后重新搜索

请选择下一步动作，并说明理由。格式：
动作: <动作名称>
理由: <决策理由>
"""

def decide_action(model, tokenizer, state):
    """
    用 LLM 做决策
    """
    prompt = STATE_PROMPT_TEMPLATE.format(**state)
    
    inputs = tokenizer(prompt, return_tensors="pt").to(model.device)
    outputs = model.generate(
        **inputs,
        max_new_tokens=100,
        do_sample=True,
        temperature=0.7,
    )
    
    response = tokenizer.decode(outputs[0], skip_special_tokens=True)
    action = parse_action(response)  # 解析出动作
    reason = parse_reason(response)  # 解析出理由
    
    return action, reason
```

#### 3.2 数据收集方法

> **本项目选择：自动标注（规则 70% + LLM 30%）+ 人工校验 10%**

**为什么不用纯人工标注？**
- 成本高：标注 1 条轨迹需要 5-10 分钟，1000 条需要 80+ 人时
- 主观性强：不同标注员对"好动作"的理解不同
- 本项目方案：自动标注为主，人工只做质量抽检

**本项目的自动标注方案（确定版）**：

```python

    def label_reward(self, state, action, result) -> float:
        reward = 0.0
        
        # ========== 规则部分 (70% 权重) ==========
        rule_reward = 0.0
        
        # 规则 1: 搜索有效性
        if action == "web_search":
            if len(result.get('hits', [])) > 0:
                rule_reward += 0.3  # 搜到结果
                if result['hits'][0]['score'] > 0.7:
                    rule_reward += 0.2  # 高质量结果
            else:
                rule_reward -= 0.2  # 搜不到结果
        
        # 规则 2: 深度研究有效性
        if action == "deep_research":
            if result.get('extracted_info'):
                rule_reward += 0.4  # 提取到有用信息
        
        # 规则 3: 生成答案时机
        if action == "generate_answer":
            if state['search_count'] >= 2 and state['avg_score'] > 0.6:
                rule_reward += 0.3  # 时机合适
            elif state['search_count'] == 0:
                rule_reward -= 0.5  # 没搜就答，扣分
        
        # 规则 4: 效率惩罚
        rule_reward -= 0.05 * state['search_count']  # 搜索成本
        
        # ========== LLM 评估部分 (30% 权重) ==========
        llm_prompt = f"""你是一个检索决策评估专家。

用户问题: {state['query']}
当前状态: 已搜索 {state['search_count']} 次，最高相关分 {state.get('max_score', 0):.2f}
采取动作: {action}
动作结果: {str(result)[:500]}

请评估这个决策的质量，只输出 0.0-1.0 之间的分数，不要输出其他内容。
评分标准：
- 1.0: 完美决策，时机和选择都很好
- 0.7: 良好决策，基本合理
- 0.4: 一般决策，有改进空间
- 0.1: 差的决策，明显不合适"""
        
        llm_response = self.llm.generate(llm_prompt, max_tokens=10)
        try:
            llm_reward = float(llm_response.strip())
            llm_reward = max(0.0, min(1.0, llm_reward))  # 限制范围
        except:
            llm_reward = 0.5  # 解析失败用默认值
        
        # ========== 加权求和 ==========
        reward = 0.7 * rule_reward + 0.3 * llm_reward
        
        return reward
```

def compute_rule_reward(state, action):
    """规则奖励（70% 权重）"""
    reward = 0.0
    
    # 1. 搜索动作奖励
    if action == "SEARCH":
        if state['search_count'] < 3:
            reward += 0.2  # 前期鼓励搜索
        else:
            reward -= 0.1  # 后期惩罚过多搜索
    
    # 2. 深度阅读奖励
    if action == "READ_FULL":
        if state['has_relevant_results']:
            reward += 0.3  # 有好结果时才深读
        else:
            reward -= 0.2  # 没结果瞎读

        elif state['search_count'] == 0:
            reward -= 0.5  # 没搜就答
    
    # 4. 效率惩罚
    reward -= 0.02 * state['search_count']
    
    return reward

## 🎯 Part 3: 面试题库

### 基础概念题

#### Q1: 解释一下 GRPO 和 PPO 的区别，为什么本项目选择 GRPO？

**参考答案**：

**核心区别在于优势估计方法**：

| 方面 | PPO | GRPO |
|------|-----|------|
| **Advantage 计算** | A = Q(s,a) - V(s) | A = (R - μ) / σ（组内相对） |
| **需要 Critic** | ✅ 需要 | ❌ 不需要 |
| **参数量** | 2 倍（Policy + Critic） | 1 倍（只有 Policy） |
| **训练稳定性** | 高 | 中等 |
| **适用场景** | 通用 RL | LLM Agent |

**GRPO 的直观理解**：
```
PPO:  这个动作的价值是 0.8，平均价值是 0.5，所以优势是 +0.3
GRPO: 同一个 prompt 采样 4 个 response，这个 response 排第 1，所以给正反馈
```

**为什么选 GRPO**：
1. **无需 Critic**：省一半参数，省一半训练成本
2. **与 LLM 原生兼容**：GRPO 是 DeepSeek 为 LLM 微调场景设计的
3. **跳过 SFT**：可以直接从 base model 开始 RL 训练
4. **实现简单**：用 trl 库几行代码搞定

**GRPO 的缺点**：
- 需要采样多个 response（显存和时间成本）

#### Q3: LoRA 微调中 r 和 alpha 参数怎么选？本项目用的多少？

**参考答案**：

**本项目配置**：`r=16, lora_alpha=32`

| 参数 | 含义 | 本项目值 | 调参建议 |
|------|------|----------|----------|
| `r` | LoRA 秩（低秩分解的维度） | 16 | 8-64，越大容量越大 |
| `lora_alpha` | 缩放系数 | 32 | 通常设为 2×r |
| `target_modules` | 应用 LoRA 的层 | q/k/v/o_proj | attention 层最重要 |
| `lora_dropout` | Dropout 概率 | 0.05 | 0-0.1 |

**参数量计算**：
```python
# Qwen2.5-7B 的 attention 层
# 每层: q_proj, k_proj, v_proj, o_proj 各 4096×4096 = 16M
# LoRA 参数: 2 × r × d = 2 × 16 × 4096 = 131K per module
# 32 层 × 4 模块 × 131K ≈ 17M 参数
# 加上 gate/up/down_proj ≈ 20M 可训练参数
```

**调参经验**：
- `r=8`: 轻量，适合资源受限
- `r=16`: 平衡点，多数场景够用
- `r=32+`: 容量大，适合复杂任务
- `alpha/r = 2`: 经验公式，保持梯度稳定
       │     │    └──────── 对话历史压缩
       │     └───────────── 检索结果质量
       └─────────────────── Query 语义向量
```

**各部分作用**：

1. **Query 语义向量（768 维）**：
   - 来源：BGE-base-zh 编码
   - 作用：理解用户问的是什么
   - 影响决策：技术问题 → 倾向 web_search，闲聊 → 倾向 generate_answer

2. **检索结果质量（64 维）**：
   - 包含：Top-K 分数、分数分布、来源多样性、时效性
   - 作用：判断当前结果够不够好
   - 影响决策：分数低 → refine_query，分数高 → generate_answer

3. **对话历史（128 维）**：
   - 来源：最近 3 轮对话的压缩表示
   - 作用：理解上下文和用户意图变化
   - 影响决策：用户追问 → deep_research，新话题 → web_search

4. **任务进度（64 维）**：
   - 包含：搜索次数、耗时、Token 消耗、缓存命中
   - 作用：控制成本和效率
   - 影响决策：搜索太多次 → 倾向停止

**为什么用 BGE 而不是其他模型**：
- 中文优化好
- 768 维是性价比最高的（512 太小，1024 冗余）

#### Q3: 奖励函数如何设计？如何平衡质量和效率？

**参考答案**：

**多目标奖励设计**：

```python
reward = (
    quality_reward      # 结果质量，权重 0.6
    + efficiency_reward # 效率，权重 0.3
    + diversity_reward  # 多样性，权重 0.1
)
```

**质量奖励**：
```python
quality_reward = 0
if user_satisfied:  # 用户点赞
    quality_reward = 1.0
elif answer_covers_key_points:  # LLM 判断覆盖关键点
    quality_reward = 0.5
elif found_relevant_source:  # 找到相关文献
    quality_reward = 0.2
```

**效率奖励**（实际是惩罚）：
```python
efficiency_reward = 0
efficiency_reward -= 0.1 * search_count  # 每次搜索扣分
efficiency_reward -= 0.05 * api_calls    # 每次 API 调用扣分
if elapsed_time > 30:
    efficiency_reward -= 0.3  # 超时惩罚
```

**平衡方法**：

1. **加权求和**：调整权重，如 0.6 质量 + 0.3 效率
2. **阈值约束**：效率必须 > 某阈值，否则质量不计分
3. **Pareto 优化**：多目标优化，找 Pareto 前沿

**实验调参**：
```
权重        | 行为表现
--------------------------
质量:效率=9:1 | 反复搜索，不管成本
质量:效率=5:5 | 适度搜索，快速收敛
质量:效率=1:9 | 搜一次就停，质量差
推荐: 6:3:1  | 平衡点
```

#### Q5: 如何处理奖励稀疏问题？

**参考答案**：

**问题**：只有最终回答被用户评价时才有明确奖励，中间步骤奖励是 0。

**解决方案**：

1. **Reward Shaping**：
```python
def shaped_reward(state, action, next_state):
    intrinsic_reward = 0
    
    # 搜索返回结果 → 小奖励
    if action == "web_search" and len(next_state['results']) > 0:
        intrinsic_reward += 0.1
    
    # 结果质量提升 → 奖励
    if next_state['avg_score'] > state['avg_score']:
        intrinsic_reward += 0.2
    
    # 覆盖新的关键词 → 奖励
    new_coverage = next_state['covered_keywords'] - state['covered_keywords']
    intrinsic_reward += 0.1 * len(new_coverage)
    
    return intrinsic_reward
```

2. **逆向奖励传播**：
```python
# 把最终奖励按折扣传递给前序步骤
def backward_reward(trajectory, final_reward, gamma=0.99):
    discounted = final_reward
    for step in reversed(trajectory):
        step['reward'] += discounted
        discounted *= gamma
```

3. **好奇心奖励（Curiosity）**：
```python
# 鼓励探索新状态
def curiosity_reward(state, next_state):
    novelty = 1 - cosine_similarity(state, visited_states)
    return 0.1 * novelty
```

**最佳实践**：组合使用，但不要让塑形奖励主导：
```python
total_reward = 0.7 * true_reward + 0.3 * shaped_reward
```

```

**职责分工**：

| 能力 | RL Agent | LLM |
|------|----------|-----|
| **决策** | ✅ 选择动作 | ❌ |
| **语言理解** | ❌ | ✅ 理解 query |
| **文本生成** | ❌ | ✅ 生成答案 |
| **学习用户偏好** | ✅ 从反馈学习 | ❌（不更新参数） |
| **成本控制** | ✅ 控制何时调用 | ❌ |

**为什么不直接让 LLM 决策？**

1. **成本**：LLM 推理贵，RL 策略网络便宜 1000 倍
2. **可控性**：RL 的动作空间有限，不会"胡言乱语"
3. **可学习**：RL 可以从用户反馈中学习，LLM（不微调）不行

**类比**：
- RL Agent = 项目经理（决定做什么）
- LLM = 工程师（执行具体任务）

#### Q14: 如果不用 RL，有什么替代方案？优劣对比？

**参考答案**：

| 方案 | 实现方式 | 优点 | 缺点 |
|------|----------|------|------|
| **规则系统** | if-else 决策树 | 简单、可解释 | 无法适应、规则爆炸 |
| **监督学习** | 标注 (state, best_action) | 数据效率高 | 需要大量标注 |
| **LLM 直接决策** | Prompt: "下一步做什么？" | 零样本、灵活 | 贵、不稳定、难优化 |
| **RL** | 从反馈中学习 | 自适应、可优化 | 训练复杂 |

**各方案适用场景**：

```
项目初期：规则系统（快速验证）
有标注数据：监督学习（简单有效）
追求极致体验：RL（持续优化）
探索期：LLM 决策（零样本尝试）
```

**混合方案（推荐）**：

```python
def select_action(state):
    # 1. 规则兜底
    if state['search_count'] > 10:
        return "generate_answer"  # 强制停止
    
    # 2. RL 决策
    action = rl_policy(state)
    
    # 3. 规则校验
    if not is_valid(action, state):
        action = rule_based_fallback(state)
    
    return action

# A/B 测试
def ab_test(n_users=1000, n_days=7):
    results = {"rule": [], "rl": []}
    
    for user in users:
        # 随机分组
        group = "rule" if hash(user) % 2 == 0 else "rl"
        
        for query in user.queries:
            if group == "rule":
                result = rule_agent.answer(query)
            else:
                result = rl_agent.answer(query)
            
            # 收集指标
            results[group].append({
                "satisfaction": get_user_feedback(),
                "steps": result.steps,
                "cost": result.api_calls * 0.007,
                "latency": result.time,
            })
    
    # 统计检验
    for metric in ["satisfaction", "steps", "cost", "latency"]:
        rule_vals = [r[metric] for r in results["rule"]]
        rl_vals = [r[metric] for r in results["rl"]]
        
        t_stat, p_value = ttest_ind(rule_vals, rl_vals)
        print(f"{metric}: rule={np.mean(rule_vals):.3f}, rl={np.mean(rl_vals):.3f}, p={p_value:.4f}")
